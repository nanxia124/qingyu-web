# 轻域 AI 数据库与多租户需求规范

版本：0.1（需求规划稿）  
状态：待确认，暂不用于建表和迁移

## 1. 文档目的

这份文档先把“系统要保存什么、谁拥有这些数据、谁能看和改”说清楚，再进入数据库建表。

大白话：数据库不是把所有信息混在一起。每类信息都有自己的归属、权限、保存时间和删除规则。

## 2. 系统边界

### 2.1 现有系统的分工

| 系统 | 负责内容 | 说明 |
|---|---|---|
| Appwrite | 注册、登录、密码、会话、基础用户身份 | 用户登录密码由 Appwrite 保存，业务库不重复保存明文密码 |
| PostgreSQL | 业务数据、团队、权限、订阅、资产、历史、互动、审计 | 本文规划的主业务数据库 |
| 文件存储 | 图片、视频、源文件、缩略图 | 数据库只保存文件 ID、地址和元数据，不直接塞入大文件 |
| Redis（后续） | 缓存、限流、短期任务状态 | 不是事实数据，丢失后可以重新生成 |

### 2.2 数据归属原则

1. **用户身份由 Appwrite 拥有**。PostgreSQL 只保存对应的 `appwrite_user_id`。
2. **业务事实由 PostgreSQL 拥有**。例如订阅是否有效、资产属于哪个团队、谁有权限。
3. **文件内容由文件存储拥有**。PostgreSQL 记录文件的归属和状态。
4. **前端不能决定权限**。前端只负责显示，最终权限必须由服务端判断。
5. **一个事实只保存一份**。其他页面看到的数据通过查询或事件同步，不能各自复制一套。

## 3. 核心概念

| 术语 | 专业解释 | 大白话 |
|---|---|---|
| Tenant | 租户，数据隔离的最大业务边界 | 一个团队或一个个人空间 |
| Workspace | 工作空间，用户实际工作的容器 | 用户或团队的“房间” |
| RBAC | 基于角色的权限控制 | 先给人分配角色，再由角色决定能做什么 |
| ABAC | 基于属性的权限控制 | 还要看资源属于谁、状态是什么、用户在哪个团队 |
| Aggregate | 聚合，必须一起保证一致性的业务对象 | 一次操作中必须同时正确的一组数据 |
| Soft Delete | 软删除 | 先标记删除，必要时还能恢复 |
| Audit Log | 审计日志 | 记录谁在什么时候做了什么 |
| Idempotency | 幂等 | 用户重复点一次和点十次，结果不能重复扣费或重复创建 |

## 4. 数据隔离模型

系统采用“个人空间 + 团队空间”的模型。

```text
Appwrite User
    └── user_account
          ├── personal_workspace（个人空间）
          └── team_membership → team → team_workspace（团队空间）
```

### 4.1 数据归属字段

所有业务表必须根据情况包含以下字段：

| 字段 | 类型建议 | 含义 |
|---|---|---|
| `id` | UUID | 这条记录自己的唯一编号 |
| `workspace_id` | UUID | 数据属于哪个个人或团队空间 |
| `owner_user_id` | UUID / Appwrite ID | 个人数据的拥有者 |
| `team_id` | UUID，可为空 | 数据属于哪个团队 |
| `created_at` | timestamptz | 创建时间 |
| `updated_at` | timestamptz | 最近修改时间 |
| `deleted_at` | timestamptz，可为空 | 软删除时间；为空表示没有删除 |
| `version` | integer | 并发修改版本，防止覆盖别人刚改的内容 |

规则：`workspace_id` 是主要隔离字段。任何查询都必须带上当前用户有权访问的 `workspace_id`，不能只按 `id` 查询。

## 4B. 表分组总览

| 分组 | 表 | 这组数据解决什么问题 | 数据拥有者 |
|---|---|---|---|
| 身份 | `user_account`、`user_preferences` | 认识用户和保存用户偏好 | 用户模块 |
| 空间 | `workspace`、`team` | 区分个人数据和团队数据 | 空间模块 |
| 组织 | `team_membership`、`department`、`job_title`、`team_invitations` | 管理成员、部门、岗位和入职离职 | 团队模块 |
| 权限 | `roles`、`permissions`、`role_permissions`、`user_roles`、`access_policies` | 决定谁可以做什么 | 权限模块 |
| 订阅 | `plans`、`subscriptions`、`orders`、`payments`、`usage_records` | 方案、付款和额度消耗 | 计费模块 |
| 生成 | `generation_tasks`、`generation_outputs` | 记录生成请求和结果 | 生成模块 |
| API | `api_providers`、`api_credentials`、`models` | 管理模型和供应商 | API 配置模块 |
| 资产 | `assets`、`asset_versions`、`asset_shares`、`asset_references` | 保存、分享和复用结果 | 资产模块 |
| 互动 | `asset_likes`、`asset_comments`、`moderation_records` | 点赞、评论和审核 | 互动模块 |
| 治理 | `audit_logs`、`notifications`、`outbox_events` | 追踪操作、发送通知、保证事件不丢 | 平台治理模块 |

## 4C. 看表字段的统一格式

以后每张表都按下面的表格说明，不直接凭感觉建字段。

| 列名 | 专业含义 | 大白话 | 是否必填 | 关系或限制 |
|---|---|---|---|---|
| `id` | 主键 | 这条数据的身份证号 | 是 | 全局唯一 |
| `workspace_id` | 租户隔离键 | 这条数据属于哪个空间 | 业务表必填 | 外键指向 `workspace.id` |
| `created_by` | 创建者 | 谁创建的 | 业务表必填 | 外键指向用户 |
| `created_at` | 创建时间 | 什么时候产生 | 是 | 服务器统一生成 |
| `updated_at` | 修改时间 | 最近什么时候改过 | 是 | 每次修改自动更新 |
| `deleted_at` | 软删除时间 | 是否被放进回收站 | 否 | 不直接物理删除 |
| `version` | 乐观锁版本 | 防止两个人互相覆盖修改 | 是 | 每次更新加一 |

任何新增表都必须回答：它属于哪个分组、谁拥有、谁能读、谁能写、什么时候删除、是否需要审计。

## 5. 用户与身份模块

### 5.1 `user_account` 用户业务档案

Appwrite 负责认证；本表负责业务资料。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 系统内部用户编号 |
| `appwrite_user_id` | varchar(64)，唯一 | Appwrite 用户编号 |
| `email` | citext | 展示和联系邮箱，不作为密码来源 |
| `display_name` | varchar(100) | 昵称 |
| `avatar_file_id` | UUID，可为空 | 头像文件 |
| `locale` | varchar(16) | 语言，如 `zh-CN` |
| `timezone` | varchar(64) | 时区 |
| `status` | enum | `active`、`suspended`、`deleted` |
| `last_login_at` | timestamptz | 最近登录时间 |
| `created_at` | timestamptz | 首次进入系统时间 |

密码不在 PostgreSQL 保存。不能保存明文密码，也不能把 Appwrite 的密码复制过来。

### 5.2 `user_preferences` 用户偏好

主题、语言、默认模型、通知设置等可修改偏好单独存放，避免把用户主档案做成一张“万能表”。

### 5.3 登录安全

登录会话、密码重置、邮箱验证由 Appwrite 负责。PostgreSQL 只记录必要的业务事件，例如登录时间、封禁状态和安全审计摘要。

## 6. 个人空间、团队与组织

### 6.1 `workspace` 工作空间

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 空间编号 |
| `type` | enum | `personal` 或 `team` |
| `team_id` | UUID，可为空 | 团队空间对应的团队 |
| `owner_user_id` | UUID，可为空 | 个人空间的用户 |
| `name` | varchar(120) | 空间名称 |
| `status` | enum | `active`、`archived`、`deleted` |
| `created_at` | timestamptz | 创建时间 |

约束：`personal` 空间必须有 `owner_user_id`；`team` 空间必须有 `team_id`，不能两者都空。

### 6.2 `team` 团队

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 团队编号 |
| `name` | varchar(120) | 团队名称 |
| `slug` | varchar(80)，唯一 | 团队短名称，用于 URL |
| `owner_user_id` | UUID | 团队所有者 |
| `plan_id` | UUID | 当前订阅方案 |
| `status` | enum | `active`、`suspended`、`deleted` |
| `created_at` | timestamptz | 创建时间 |

### 6.3 `team_membership` 团队成员关系

一名用户可以加入多个团队，一个团队可以有多个用户。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 成员关系编号 |
| `team_id` | UUID | 团队 |
| `user_id` | UUID | 用户 |
| `role_id` | UUID | 当前角色 |
| `department_id` | UUID，可为空 | 所属部门 |
| `job_title_id` | UUID，可为空 | 岗位 |
| `status` | enum | `invited`、`active`、`suspended`、`left` |
| `joined_at` | timestamptz，可为空 | 入职或加入时间 |
| `left_at` | timestamptz，可为空 | 离职或退出时间 |
| `invited_by` | UUID，可为空 | 邀请人 |

唯一约束：同一个用户在同一个团队只能有一条有效成员关系。

### 6.4 `department` 部门与 `job_title` 岗位

部门支持 `parent_id`，可以形成“公司 → 设计部 → 视觉组”的层级。岗位只描述职位，不直接等于权限；权限通过角色分配。

### 6.5 入职、离职与邀请

用 `team_invitations` 记录邀请链接、邀请邮箱、有效期、接受人和状态。离职不立即删除历史数据，而是把成员状态改为 `left`，保留历史操作归属。

## 7. 角色与权限

### 7.1 权限分层

权限分三层：

1. **功能权限**：能不能使用某个功能，例如生成图片、删除资产、管理成员。
2. **资源权限**：能不能操作某条具体数据，例如只能改自己创建的资产。
3. **范围权限**：能操作个人数据、部门数据、团队数据，还是全平台数据。

### 7.2 主要表

| 表 | 用途 |
|---|---|
| `roles` | 角色，如 Owner、Admin、Editor、Viewer |
| `permissions` | 原子权限，如 `asset.read`、`asset.delete` |
| `role_permissions` | 角色和权限的对应关系 |
| `user_roles` | 个人在全局或团队中的角色 |
| `permission_overrides` | 特殊用户的临时允许或禁止 |
| `access_policies` | 资源范围规则，如只能访问本部门 |

建议初始角色：

| 角色 | 大白话 |
|---|---|
| `owner` | 团队老板，可以管理全部内容和成员 |
| `admin` | 管理员，可以管理团队和大部分业务数据 |
| `editor` | 编辑者，可以创建、编辑和分享内容 |
| `viewer` | 查看者，只能查看被允许的数据 |
| `member` | 普通成员，使用团队分配给他的功能 |

权限判断必须在服务端完成：用户是否登录、是否属于团队、角色是否允许、资源是否属于当前范围、订阅是否有效，都要一起判断。

## 8. 订阅、额度与计费

### 8.1 方案与订阅

| 表 | 作用 |
|---|---|
| `plans` | 方案定义，如免费版、专业版、团队版 |
| `plan_features` | 方案能使用哪些功能 |
| `plan_quotas` | 方案包含多少图片、视频、Agent 次数或存储空间 |
| `subscriptions` | 某个用户或团队当前订阅 |
| `subscription_events` | 开通、续期、升级、降级、取消和退款记录 |
| `payment_customers` | 第三方支付平台的客户编号 |
| `orders` | 订单事实 |
| `payments` | 实际支付结果 |

### 8.2 订阅归属

订阅必须明确归属对象：`user_id` 或 `team_id` 只能有一个有效值。个人订阅只能影响个人空间，团队订阅只能影响团队空间。

### 8.3 使用量

`usage_records` 保存每次实际消耗：用户、团队、空间、功能、模型、数量、单位、请求编号、结果和时间。额度汇总可以缓存，但每次扣减必须有可追溯的原始记录。

防重复：每次消耗带 `idempotency_key`，同一个请求重试不能重复扣额度。

## 9. 生成任务与历史记录

### 9.1 `generation_tasks` 生成任务

| 字段 | 说明 |
|---|---|
| `id` | 任务编号 |
| `workspace_id` | 任务归属空间 |
| `created_by` | 发起人 |
| `task_type` | 图片、视频、音频、文本或 Agent |
| `provider` | 实际调用的模型供应商 |
| `model` | 模型名称 |
| `prompt` | 用户输入；敏感内容需按策略脱敏 |
| `status` | `queued`、`running`、`succeeded`、`failed`、`cancelled` |
| `request_id` | 外部请求幂等编号 |
| `error_code` | 失败原因编号 |
| `started_at` / `finished_at` | 开始和结束时间 |

### 9.2 `generation_outputs` 生成结果

一条任务可以有多个结果。结果表保存文件 ID、缩略图、尺寸、模型版本、生成参数摘要和内容安全状态。

原始提示词和结果文件属于用户隐私，默认只能被有权限的用户看到。

## 10. 资产库与复用

### 10.1 `assets` 资产

资产可以属于个人空间，也可以属于团队空间。不要通过“复制一份数据”来分享，应该使用引用关系。

关键字段：`workspace_id`、`created_by`、`file_id`、`asset_type`、`title`、`visibility`、`source_generation_id`、`status`。

### 10.2 分享与复用

| 表 | 作用 |
|---|---|
| `asset_shares` | 把资产分享给团队、部门、指定成员或公开链接 |
| `asset_references` | 记录某个项目或任务复用了哪个资产 |
| `asset_versions` | 记录资产修改版本 |
| `collections` | 用户或团队建立的收藏夹 |
| `collection_items` | 收藏夹中的资产引用 |

复用时保留“来源资产”和“新资产”的关系，后续可以追溯、撤销分享和统计复用次数。

## 11. 点赞、评论与互动

### 11.1 `asset_likes`

唯一约束：同一用户对同一资产只能有一条点赞记录。取消点赞使用删除或软删除，但统计要可重算。

### 11.2 `asset_comments`

支持 `parent_id` 形成回复。字段包括作者、资产、评论内容、审核状态、删除时间和编辑时间。评论删除后保留“已删除”占位，避免破坏回复链。

### 11.3 内容安全

评论、公开资产和分享链接要有 `moderation_status`：`pending`、`approved`、`rejected`。审核结果由服务端保存，前端不能自行绕过。

## 12. API 配置与模型目录

### 12.1 API 供应商配置

`api_providers` 保存供应商名称、接口地址、启用状态和能力；`api_credentials` 保存加密后的密钥引用，不在普通查询中返回完整 Key。

### 12.2 模型目录

`models` 保存模型名称、供应商、能力类型、输入输出限制、价格规则和启用状态。模型列表是后台配置产生的业务数据，前端只能读取公开字段。

密钥读取必须经过后台服务，不能直接返回给浏览器，也不能写入日志。

## 13. 审计、通知与系统记录

### 13.1 `audit_logs`

记录高风险动作：登录、改权限、邀请成员、删除资产、改 API Key、改订阅、退款、导出数据。

字段建议：操作者、团队、动作、资源类型、资源 ID、成功或失败、请求 ID、IP 摘要、User-Agent 摘要、前后值摘要、时间。

### 13.2 `notifications`

保存站内通知和阅读状态，例如邀请、生成完成、评论回复、额度不足和订阅即将到期。

### 13.3 `outbox_events`

业务写入和事件记录放在同一个事务里，避免“数据库写成功但通知没发出去”。后台任务再从 outbox 投递通知、统计或索引。

## 14. 删除、隐私和生命周期

1. 普通删除先使用 `deleted_at`，保留恢复窗口。
2. 用户注销后，身份由 Appwrite 删除或禁用；业务数据按保留策略匿名化或删除。
3. 团队离职成员的历史生成记录不改作者，保留审计意义；个人隐私数据按策略处理。
4. 文件删除必须先确认数据库没有有效引用，再删除对象存储文件。
5. 订单、支付、额度和审计记录不能因为用户点“删除账号”就直接消失。
6. 生成结果和原始提示词需要设置保留期限，避免无限增长。

## 15. 索引与容量规划

第一批必须有的索引：

- `user_account(appwrite_user_id)` 唯一索引；
- `team_membership(team_id, user_id)` 唯一索引；
- 所有业务表的 `workspace_id` 索引；
- `generation_tasks(workspace_id, created_at)`；
- `assets(workspace_id, created_at)`；
- `asset_comments(asset_id, created_at)`；
- `usage_records(workspace_id, created_at)`；
- `audit_logs(team_id, created_at)`。

大表按月份或时间范围分区要等真实数据量达到阈值后再做，不能一开始就把所有表复杂化。

## 15A. 自建 PostgreSQL 到腾讯云托管 PostgreSQL 的迁移规范

当前数据库是装在轻量服务器上的自建 PostgreSQL。以后迁移到腾讯云托管 PostgreSQL 时，目标是“换数据库位置，不换业务规则”。

### 15A.1 必须保持不变的部分

| 内容 | 要求 |
|---|---|
| 表名和字段名 | 迁移前后保持一致 |
| 主键和外键 | 保持一致，不重新生成业务编号 |
| 枚举和状态 | 保持一致，例如 `active`、`deleted` |
| API 接口 | 前端不需要因为换数据库而改接口 |
| 权限规则 | 不因数据库搬家而改变 |
| 时间和时区 | 统一使用 UTC 存储，展示时转换 |

### 15A.2 必须避免的写法

- 不把业务数据写死在服务器路径中；
- 不依赖某台机器的本地用户名；
- 不使用只在某个环境存在的临时表；
- 不把文件放进数据库二进制字段；
- 不让前端直接连接 PostgreSQL；
- 不把密码、API Key 和数据库连接串提交到 GitHub；
- 不用手工改表代替 Migration；
- 不把 `localhost` 写死在业务代码里，数据库地址必须来自环境变量。

### 15A.3 连接配置标准

应用只读取环境变量，不读取开发电脑上的固定配置：

```text
DB_HOST=
DB_PORT=5432
DB_NAME=qingyu
DB_USER=
DB_PASSWORD=
DB_SSL_MODE=
DB_POOL_MIN=
DB_POOL_MAX=
```

大白话：以后从本机数据库搬到腾讯云托管数据库，只改服务器配置，不改业务代码。

### 15A.4 迁移步骤

```text
开发环境建表
    ↓
执行 Migration
    ↓
写入测试数据
    ↓
运行权限、订阅、资产和生成流程测试
    ↓
自建 PostgreSQL 作为当前环境
    ↓
腾讯云托管 PostgreSQL 建立同版本空库
    ↓
备份并恢复数据库
    ↓
修改 DB_HOST 等环境变量
    ↓
运行健康检查和业务验收
    ↓
保留旧库只读观察
    ↓
确认稳定后再下线旧库
```

### 15A.5 回滚方法

迁移前必须有完整备份和恢复演练。切换失败时，只恢复旧的数据库连接配置，应用回到旧库；不能通过删除新库来当作回滚。

## 15B. PostgreSQL Migration 文件规范

每次表结构变更必须有版本化文件，例如：

```text
database/migrations/
├── 0001_create_users_and_workspaces.sql
├── 0002_create_teams_and_memberships.sql
├── 0003_create_roles_and_permissions.sql
├── 0004_create_billing_and_usage.sql
├── 0005_create_generations_and_assets.sql
└── 0006_create_audit_and_outbox.sql
```

Migration 必须满足：

1. 可以在一台空 PostgreSQL 上从零执行；
2. 同一版本不能重复执行；
3. 失败时能定位是哪一步；
4. 生产环境执行前先在测试库演练；
5. 高风险变更要有回滚或兼容期；
6. 不把真实用户数据写进 Migration 文件。

## 15C. 数据库环境分层

| 环境 | 用途 | 数据要求 |
|---|---|---|
| `local` | 开发者电脑 | 测试数据，可随时重建 |
| `staging` | 上线前验证 | 脱敏数据，模拟生产配置 |
| `production` | 正式用户 | 真实数据，必须备份和审计 |

不同环境至少使用不同数据库名、不同账号和不同密码。开发环境不能连接生产数据库。

## 16. 必须确认的产品规则

下面这些问题在正式建表前必须确认：

1. 一个用户最多可以创建几个个人或团队空间？
2. 一个用户能否同时拥有多个团队？
3. 团队订阅由团队所有者购买，还是成员也能购买？
4. 成员离职后，他创建的资产归个人、归团队，还是按创建时选择决定？
5. 团队资产是否默认所有成员可见？
6. 公开分享链接是否允许匿名访问？是否需要过期时间？
7. 点赞和评论是否需要审核？
8. 生成结果和提示词保存多久？
9. 用户注销后，订单、审计和团队历史保留多久？
10. 图片、视频和源文件存在哪个对象存储？

## 17. 实施顺序

### P0：先保证核心闭环

用户档案、个人空间、团队、成员关系、角色权限、API 配置、模型目录、生成任务、资产和基本审计。

### P1：补齐业务运营

订阅、额度、订单、支付、团队邀请、部门岗位、收藏、点赞、评论、通知和分享链接。

### P2：增强规模能力

Outbox 事件、Redis 缓存、队列、全文搜索、分区表、数据仓库、报表和高可用备份。

## 18. 验收标准

这份需求通过后，至少应能回答：

- 每一条数据属于哪个用户、团队和空间；
- 一个用户能否读取这条数据；
- 谁可以创建、修改、分享和删除它；
- 重复请求是否会重复扣额度或重复创建；
- 用户离职、团队删除和账号注销后数据怎么处理；
- PostgreSQL、Appwrite、文件存储各自保存什么；
- 后续升级到 10 万用户时，哪些部分可以扩容，哪些部分需要拆分。

本规范确认前，不创建正式 Migration，不迁移 SQLite 数据，也不修改线上服务连接方式。
