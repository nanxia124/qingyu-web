版本：0.4。状态：核心多租户边界、RLS、复合归属约束、设备会话和主要业务接口已实现并通过当前验证；完整双账号跨团队验收和所有前端页面切换仍需继续补齐。返回 [总览](01-数据库与多租户总览.md)。

### 这是什么
规定每个数据归谁管、两个用户之间的数据怎么隔开，张三的图不能让李四看到。

### 用户怎么用
- 用户注册后有个人空间，加入团队后能切到团队空间
- 退出团队后团队的东西还在但他不能再看
- 分享图给别人，别人只能看不能改原文件
- 换账号登录，前一个账号的作品不会留在浏览器里

### 现在长什么样
- ✅ 94 张表里 46 张开了行级权限，跨用户数据看不到
- ✅ 跨团队串数据会被数据库直接拒绝
- ⏳ 跨团队分享、离职自动清理还在做

## 1. 一项事实只有一个权威来源

“权威来源”就是两处显示不一致时，以谁为准。缓存只能从这里重建。

1. **<span style="font-size:18px;color:#fff">每个数字只在一个地方保存。比如”你还剩多少额度”这个数字，全系统只在一处记录，生图页、会员页、作品页要看都从这一处取，不各自存一份；哪天两个页面对不上了，就以这一处为准重新同步。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">“权威来源”就是两处显示不一致时以谁为准；缓存只能从权威来源重建。</span>



2. **<span style="font-size:18px;color:#fff">你登录的密码归登录服务管，我们这边只记一个编号指向它，不另存一份密码；而”你是不是会员、这张图归谁”这些业务信息，归我们自己的订阅记录管。你是不是会员，以订阅记录为准，不是你自己说有会员就算有。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">登录身份与密码归 Appwrite（user_accounts.appwrite_user_id 唯一）；业务事实如订阅有效性、资产归属、权限归 PostgreSQL。</span>



3. **<span style="font-size:18px;color:#fff">下面这张表给每一样东西指定唯一的保存位置：密码归谁、套餐价格归谁、你买了啥套餐归谁、实际用了多少归谁、图片文件存在哪归谁，一行一行登记清楚。不能笼统地说”都差不多”。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">下表逐行登记每个事实的权威表与关联字段限制：用户资料归 user_accounts、偏好归 user_preferences、空间归 workspaces、成员身份归 team_memberships、角色归 role_bindings、套餐归 plans/plan_versions、订阅归 subscriptions、用量与额度归 usage_records/quota_ledger、文件位置归 file_objects、资产内容归 asset_versions/asset_files、项目内容归 canvas_nodes/canvas_connections、任务历史归 generation_tasks/agent_threads。</span>

| 事实 | 权威来源 | 关联字段与限制 |
|---|---|---|
| 登录身份与密码 | Appwrite | user_accounts.appwrite_user_id 唯一；普通业务外键只用内部 UUID |
| 用户资料 | user_accounts | email 是联系资料，不用邮箱自动合并账号 |
| 用户偏好 | user_preferences | user_id 唯一；语言、主题等不是团队数据 |
| 个人或团队空间 | workspaces | type 与 owner_user_id、team_id 互斥；每人一个个人空间，每团队一个团队空间作为初期方案 |
| 团队所有者 | teams.owner_user_id | 必须是有效成员；转交所有权在短事务中完成；禁止最后所有者直接离职 |
| 团队成员身份 | team_memberships | (team_id,user_id) 唯一；部门和岗位必须属于同一团队 |
| 成员功能角色 | role_bindings | (workspace_id,user_id,role_id) 唯一；成员表不再保存 role_id |
| 所有者权限 | teams.owner_user_id 派生 | owner 是派生身份，不能另存可独立修改的 owner 角色绑定；其他角色按 role_bindings 读取 |
| 套餐定义与历史价格 | plans、plan_versions | 发布后的版本不可直接覆盖；功能和额度规则关联 plan_version_id |
| 空间当前订阅 | subscriptions | workspace_id、plan_version_id；每空间一个基础订阅槽，历史写 subscription_events；teams 不存 plan_id |
| 使用量与额度 | usage_records、quota_ledger | 前者记录实际使用，后者记录额度变化；不能同时作为两套可改余额 |
| 原始文件位置 | file_objects | provider、bucket、object_key、version_id（可空）、checksum、size_bytes、mime_type；不是永久签名 URL |
| 资产内容 | asset_versions、asset_files | assets 保存业务身份；asset_files 关联版本和 file_objects；不并存第二套 assets.file_id |
| 项目内容 | canvas_nodes、canvas_connections | 均关联 workspace_id、project_id；项目快照是派生版本，不另设独立写入口 |
| 任务和 Agent 历史 | generation_tasks、agent_threads 等 | 有归属、有状态、有版本；连接断开不代表任务已取消 |

平台模型目录、套餐目录、管理员身份属于平台管理范围，不强加 workspace_id。组织表以 team_id 约束；用户偏好以 user_id 约束。数据归属必须按表登记，不能笼统地说“所有表都一样”。

4. **<span style="font-size:18px;color:#fff">不是每条数据都归属于某个空间。全平台通用的目录（比如有哪些套餐、有哪些模型）归平台统一管，不属于任何用户或团队；用户自己的偏好（深色模式、语言）只跟着这个人走，不跟着团队走。但不属于任何空间绝不等于谁都能看。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">平台模型目录、套餐目录、管理员身份不强加 workspace_id；组织表以 team_id 约束，用户偏好以 user_id 约束；归属按表登记，不能笼统说所有表都一样。</span>

## 2. 防串数据的七道检查

| 位置 | 必须做到 | 大白话 |
|---|---|---|
| 登录入口 | 服务端验证身份，再映射内部 user_id；不信任请求体传来的操作者 | 不能自己填一个别人编号就变成别人 |
| 空间选择 | 前端仅提出 workspace_id；服务端检查拥有者、有效成员、封禁和操作权限 | 切换空间不是获得权限 |
| 数据访问 | 空间业务的读、写、批量操作、导出均限定已授权空间；创建归属由服务端赋值 | 不止查看时隔离，保存时也要隔离 |
| 数据关联 | 同空间父表设 UNIQUE(workspace_id,id)，子表用复合外键同时约束 workspace_id 和 parent_id | 不允许 A 空间的结果挂到 B 空间的任务 |
| 缓存与浏览器 | 私有缓存键包含环境、workspace_id、资源和权限版本；用户私有内容再带 user_id；登出和换账号清理内存及分区缓存 | 同一浏览器换账号不能看到上个账号的作品 |
| 后台任务与消息 | 持久化任务携带服务端写入的空间、用户、资源编号；执行时重新验权；SSE/消息重连、回放、审批都检查线程权限 | 后台和 Agent 不能绕过网页的门锁 |
| 文件和同步 | 文件读取先验证业务引用和权限，再签发短期地址；同步范围由账号和空间限定 | 猜到地址、恢复旧同步文件都不等于有权限 |

复合外键例子：generation_outputs(workspace_id,task_id) 必须指向 generation_tasks(workspace_id,id)。连接线两端还必须属于同一个 project_id；评论父记录必须属于同一个 asset_id。组织记录引用部门时同时校验 team_id。仅有 UUID 或单列外键不能保证这些业务关系。

按行限制读取和写入的数据库策略称为 RLS。空间业务表采用默认拒绝策略，并分别覆盖读和写；应用账号不是表所有者、超级用户，也不能有 BYPASSRLS。迁移账号与应用账号分离。每个事务设置经服务端验证的空间上下文，并在事务结束清除，测试连接池复用不会继承上个用户的空间。上下文是应用提供的第二层防线，不能代替入口认证。

用户档案、平台表、组织表分别使用所属领域规则；不能因没有 workspace_id 就默认公开。RLS 所有者绕过和外键行为以 [PostgreSQL 官方文档](https://www.postgresql.org/docs/16/ddl-rowsecurity.html) 为准。

1. **<span style="font-size:18px;color:#fff">光确认编号对不对还不够，还得确认这条数据确实属于那个空间。比如一张生成出来的图，系统不光查”任务编号对不对”，还要查”这张图和这个任务是不是同一个空间的”。不能把用户A空间里的图，挂到用户B空间的任务下面；就连一条评论回复另一条评论，两条评论也必须是同一张图底下的。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">复合外键例子：generation_outputs(workspace_id,task_id) 必须指向 generation_tasks(workspace_id,id)；连接线两端必须同 project_id；评论父子必须同 asset_id；组织引用部门时同时校验 team_id；单列 UUID/外键不足以保证业务关系。</span>



2. **<span style="font-size:18px;color:#fff">数据访问还有一层默认拒绝：默认谁都不能读写，只有你登录后系统在当前请求里标明”这个人现在在哪个空间”，才允许访问那个空间的数据；请求结束后就清掉这个空间标记，不会把上一个用户的空间标记留给下一个请求。而且这层默认拒绝只是第二道防线，前面的登录验证该查还得查。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">RLS（行级安全）：空间业务表默认拒绝、分别覆盖读写；应用账号非表所有者/超级用户、无 BYPASSRLS；迁移账号与应用账号分离；每事务 SET LOCAL 经服务端验证的空间上下文，事务结束清除，连接池复用不串上下文；上下文是第二道防线，不代替入口认证。</span>



3. **<span style="font-size:18px;color:#fff">用户资料、全平台公共信息、组织架构这几类数据，各有各的访问规则，不能因为一条数据上没标注所属空间就当成”谁都能看”。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">用户档案、平台表、组织表分别使用所属领域规则；不能因没有 workspace_id 就默认公开；RLS 所有者绕过与外键行为以 PostgreSQL 16 官方文档为准。</span>

## 3. 分享、复用和离职的明确边界

| 操作 | 所有权变化 | 撤销或离职后 |
|---|---|---|
| 个人资产授权团队查看 | 不变；asset_shares 记录源资产、目标空间、权限、到期和撤销状态 | 撤销后停止新访问；已下载文件不能远程收回 |
| 在团队项目引用个人资产 | 通过显式分享授权桥接，不伪造源资产的 workspace_id | 引用保留来源编号，展示为无权访问，不能继续签发文件地址 |
| 复制为团队独立资产 | 创建团队资产版本和受控文件副本，记录来源；须有复制权限 | 不随来源分享撤销而删除；复制规则需在产品中明示 |
| 在团队空间生成 | 任务与结果归团队，created_by 保留实际作者 | 成员离职后团队保留内容，成员权限撤销 |
| 在个人空间生成 | 任务与结果归个人 | 不因加入团队自动把个人内容交给团队 |

普通外键只允许同空间关联。跨空间共享只能经 asset_shares 等专用授权关系：源对象外键验证存在，目标空间外键验证存在，服务端验证源方有分享权和目标方有使用权。读服务只返回被授权字段，不为分享临时开放整个源空间。

离职事务至少更新成员状态、撤销角色绑定和临时授权、提升权限版本。消息订阅主动断开；后续任务与审批重新验权。已发短期文件链接在到期前可能仍可访问；要求立即撤销的资源必须经下载代理逐次校验。任务停止和外部调用结算分开处理。

1. **<span style="font-size:18px;color:#fff">你把个人空间的图分享给团队看，分享后图的所有权还是你的，团队成员只能查看，不能修改你的原图；团队成员如果想要一份独立的图，需要单独复制一份存到团队空间。你撤销分享后，团队成员就不能再看了，但已经下载到他设备里的那张你远程收不回来。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">个人资产授权团队查看：所有权不变，asset_shares 记录源/目标空间、权限、到期、撤销状态；撤销后停止新访问，已下载文件不可远程收回；复制为团队资产须有复制权限并记录来源。</span>



2. **<span style="font-size:18px;color:#fff">默认情况下，数据只能在同一个空间里互相关联。真要跨空间分享，必须经过专门的授权流程：系统先查你愿不愿意分享、对方有没有资格使用，两边都确认才放行；而且授权后对方只能看到被授权的那几样，不会把你整个空间的内容都开放。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">普通外键只允许同空间关联；跨空间共享只能经 asset_shares 等专用授权：源/目标外键各自验证存在，服务端验证源方分享权与目标方使用权；读服务只返回被授权字段，不临时开放整个源空间。</span>



3. **<span style="font-size:18px;color:#fff">成员离开团队时，系统会马上收回他的访问权限、撤销他的角色、断开他的消息订阅。但他以前做的图、写的评论还留在团队里，作者名字也不抹掉，保留记录。已经发出去的临时访问链接，在过期前可能还能打开，所以特别重要的资源得每次访问都重新验一次身份。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">离职事务至少更新成员状态、撤销角色绑定与临时授权、提升权限版本；消息订阅主动断开；后续任务与审批重新验权；已发短期链接到期前可能仍可访问，要求立即撤销的资源经下载代理逐次校验；任务停止与外部调用结算分开处理。</span>

## 4. 常用调用方式与适度设计

前端调用业务接口，不能直接查询数据库。初期使用模块化单体：一个后端内按业务分目录，不为每类表部署独立服务。同步事务由应用服务编排，各模块通过自己的服务写表；只有异步通知、可靠任务派发等需要 Outbox。

| 场景 | 建议接口契约 | 返回与限制 |
|---|---|---|
| 资产列表 | GET /workspaces/{id}/assets?cursor=...&limit=... | 返回摘要、next_cursor，不带原图、全部历史或密钥 |
| 保存节点 | PATCH /workspaces/{id}/projects/{projectId}/nodes/{nodeId} | 携带旧 version；冲突返回 409 和当前版本，不静默覆盖 |
| 发起生成 | POST /workspaces/{id}/generation-tasks | 带幂等键；返回已持久化的 task_id 和排队状态 |
| 读取结果 | GET /workspaces/{id}/generation-tasks/{taskId} | 重新验权；包含结果摘要和受控下载入口 |
| 文件访问 | GET /workspaces/{id}/files/{fileId}/download | 检查有效资产或任务引用、权限和文件状态 |

统一错误语义：401 未登录；403 没有操作权限；404 资源不存在或不能披露其存在；409 版本/状态/幂等冲突；429 限流。不能在失败分支展示“保存成功”。已接入的路由遵守这套语义；尚未切换到 PostgreSQL 的页面仍按待实现处理，不能仅凭表结构宣称已完成。

节点类型专用参数可存带 schema_version 的 JSONB，需字段校验、大小上限、升级转换和默认值。需要外键、唯一性、索引查询、计费计算的字段使用明确列。节点配置不为“看起来规范”强行拆表，拖拽不逐像素写数据库；按节点批量增量保存并处理版本冲突。

1. **<span style="font-size:18px;color:#fff">你点网页上的按钮，是网页把请求交给后台处理，网页自己不能直接读取后台数据。初期也不拆成多个互相独立的小服务，就是一个后台按业务分模块。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">前端调用业务接口，不直连数据库；初期模块化单体，单后端按业务分目录；同步事务由应用服务编排，各模块通过自有服务写表；只有异步通知、可靠任务派发才用 Outbox。</span>



2. **<span style="font-size:18px;color:#fff">下面这些就是网页和后台之间约定好的几种操作：查作品列表、保存画布节点、发起生图、看结果、下载文件。每种操作做什么、要带什么参数、做完返回什么都写清楚了——比如保存节点时你得带着”我看到的是第几版”，要是别人刚改过，就直接告诉你”版本对不上”，绝不偷偷把别人的覆盖了。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">接口契约：资产列表 GET /workspaces/{id}/assets（游标分页、不返原图）；保存节点 PATCH 携带旧 version，冲突返回 409；发起生成 POST 带幂等键返回 task_id；读取结果 GET 重新验权；文件下载 GET 校验引用与权限。</span>



3. **<span style="font-size:18px;color:#fff">办不成事就明说办不成：没登录、没权限、东西不存在、版本冲突、点太快被限流，各有各的提示。绝对不能明明失败了还弹个“保存成功”骗你。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">统一错误语义：401 未登录、403 无权限、404 不存在或不披露、409 版本/状态/幂等冲突、429 限流；失败分支不得展示保存成功；未切换到 PostgreSQL 的页面按待实现处理。</span>



4. **<span style="font-size:18px;color:#fff">画布上每个节点的具体设置，可以先存在一起，不用一上来就拆成几十个字段；但真要用来查询、用来计算额度的东西，必须单独列清楚。拖动画布时不要拖一下就存一次，攒一批再一起保存。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">节点专用参数可存带 schema_version 的 JSONB，需字段校验、大小上限、升级转换与默认值；需外键/唯一/索引/计费的字段用明确列；不为“看起来规范”强行拆表；拖拽不逐像素写库，按节点批量增量保存并处理版本冲突。</span>

## 5. 文件与扩展治理

file_objects 建议公共字段为 id、workspace_id、storage_provider、bucket、object_key、storage_version_id、checksum、size_bytes、mime_type、status、created_at。状态至少 pending、ready、deleting、deleted；数据库提交和文件上传不是一个事务。上传确认后才允许引用 ready 文件；失败上传由清理任务回收。

删除先阻止新引用，再延迟清理；清理前重查有效引用和恢复窗口。删除失败可重试。数据库备份不包含对象文件，必须独立备份和校验。长期密钥保存加密引用并记录 key_version，解密钥匙不能与密文一同放入普通备份或浏览器。

| 新功能上线前登记项 | 必填内容 |
|---|---|
| 模块和事实 | 属于哪个模块、现有表能否复用、谁是唯一写入者 |
| 数据字典 | 字段中文含义、英文名、类型、必填、默认值、外键、唯一性、索引、保留时间 |
| 范围与权限 | 用户/空间/组织/平台哪一类；角色、分享、删除和导出规则 |
| 兼容升级 | 新旧应用兼容期、JSON 版本、增量脚本和回滚条件 |
| 数据生命周期 | 文件、日志、软删除、匿名化、账务保留及恢复规则 |
| 验收 | 跨账号、跨空间、重复请求、并发、失败恢复、性能和迁移测试 |

初期不统一给所有表加软删除和 version。可编辑业务实体才需要版本；账务流水只追加冲正，不通过修改和软删除纠错。系统动作记录 actor_type 和可空 actor_user_id，不能为了满足 created_by 必填伪造一个用户。

1. **<span style="font-size:18px;color:#fff">图片视频这些大文件存在专门的存储里，记录里只存”第几号文件、多大、是什么类型、传完没有”。文件状态分几种：刚传、传好、正在删、已删。上传文件和写记录不是同时成功的——只有确认文件真传上去了，才允许别人引用它；传失败的会有定时任务清理掉。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">file_objects 字段：id、workspace_id、storage_provider、bucket、object_key、storage_version_id、checksum、size_bytes、mime_type、status（pending/ready/deleting/deleted）、created_at；DB 提交与文件上传非同一事务；只有 ready 文件可被引用；失败上传由清理任务回收。</span>



2. **<span style="font-size:18px;color:#fff">删文件时先标记”停止使用”，过一会再真正删除，删之前还要再确认一遍没人在用。数据记录和实际文件要各自备份，不能只备份记录不备份文件。访问密钥要加密存储，解密用的密钥不能和加密后的数据放在同一个备份里。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">删除先阻止新引用再延迟清理，清理前重查有效引用与恢复窗口，失败可重试；DB 备份不含对象文件，文件须独立备份校验；长期密钥存加密引用并记 key_version，解密钥匙不与密文同放普通备份或浏览器。</span>



3. **<span style="font-size:18px;color:#fff">以后每加一个新功能，上线前都得填这张“登记表”：归哪个部门管、每个字段啥意思、谁能看谁能改、老版本怎么过渡、东西留多久、要做哪些测试。填不齐不让上。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">新功能上线前登记项：模块与事实归属、数据字典（字段含义/类型/必填/默认/外键/唯一/索引/保留期）、范围与权限、兼容升级、数据生命周期、验收（跨账号/跨空间/重复请求/并发/失败恢复/性能/迁移）。</span>



4. **<span style="font-size:18px;color:#fff">不是每张表都需要软删除和版本号。能编辑的内容才需要版本号防止两个人互相覆盖；额度流水只准往后追加、不准改之前的记录，错了就补一笔反向记录冲销。系统自己做的事，如实记是”系统操作”，不能为了填字段硬造一个假用户。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">初期不统一加软删除与 version；可编辑业务实体才需版本；账务流水只追加冲正，不改不软删纠错；系统动作记 actor_type 和可空 actor_user_id，不为 created_by 必填伪造用户。</span>
