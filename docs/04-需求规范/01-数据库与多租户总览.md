## 2. 系统边界

### 2.1 目标系统的分工（不代表当前已实现）

| 系统 | 负责内容 | 说明 |
|---|---|---|
| Appwrite | 注册、登录、密码、会话、基础用户身份 | 用户登录密码由 Appwrite 保存，业务库不重复保存明文密码 |
| PostgreSQL | 业务数据、团队、权限、订阅、资产、历史、互动、审计 | 本文规划的主业务数据库 |
| 文件存储 | 图片、视频、源文件、缩略图 | 数据库只保存文件 ID、地址和元数据，不直接塞入大文件 |
| Redis（后续） | 缓存、限流、短期任务状态 | 不是事实数据，丢失后可以重新生成 |

### 2.2 数据归属原则

1. **<span style="font-size:18px;color:#fff">账号密码由专门管登录的地方保存，我们这边只记一个编号，知道这人对应那边的谁。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">用户身份由 Appwrite 拥有，PostgreSQL 只保存 appwrite_user_id。</span>


2. **<span style="font-size:18px;color:#fff">你是不是会员、这张图归你还是归团队、谁能打开它，这些由我们自己的系统记着、以系统记录为准。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">业务事实由 PostgreSQL 拥有，如订阅有效性、资产归属、权限。</span>


3. **<span style="font-size:18px;color:#fff">你生成的图片本身放在专门存图的地方，系统只记录这张图存在哪、归谁所有，不把图片本身塞进记录里。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">文件内容由文件存储拥有，PostgreSQL 记录文件归属和状态。</span>


4. **<span style="font-size:18px;color:#fff">你不是会员，网页上"会员专属"按钮本来是灰的，懂技术的人能改网页把它点亮，但点了也没用，我们服务器一查你不是会员直接拒绝。所以能不能用，是服务器说了算。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">前端不能决定权限，只负责显示，最终权限由服务端判断。</span>


5. **<span style="font-size:18px;color:#fff">同一个数字只在一个地方记，比如你的剩余额度，生图页、会员页、作品页要看都去读这同一个数字，不各自抄一份，这样你在哪个页面看到的额度都一样，不会出现几个页面对不上。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">一个事实只保存一份，其他页面通过查询或事件同步。</span>

## 3. 核心概念

| 术语 | 专业解释 | 大白话 |
|---|---|---|
| Tenant | 租户，数据隔离的最大业务边界 | 一个团队或一个个人空间 |
| Workspace | 工作空间，用户实际工作的容器 | 用户或团队的“房间” |
| RBAC | 基于角色的权限控制 | 先给人分配角色，再由角色决定能做什么 |
| ABAC | 基于属性的权限控制 | 还要看资源属于谁、状态是什么、用户在哪个团队 |
| Aggregate | 聚合，必须一起保证一致性的业务对象 | 一次操作中必须同时正确的一组数据 |
| Soft Delete | 软删除 | 先标记删除，必要时还能恢复 |
| Audit Log | 审计日志 | 记录谁在什么时候做了什么 |
| Idempotency | 幂等 | 用户重复点一次和点十次，结果不能重复扣费或重复创建 |

## 4. 数据隔离模型

系统采用“个人空间 + 团队空间”的模型。

**<span style="font-size:18px;color:#fff">每个人有自己的个人空间，也能加入团队共用的团队空间。你在个人空间里画的图只有你能看，上传到团队空间的图团队成员才能一起用，两个空间的内容互不相通。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">系统采用“个人空间 + 团队空间”的模型。</span>

```text
Appwrite User
    └── user_accounts
          ├── personal_workspace（个人空间）
          └── team_memberships → teams → team workspace（团队空间）
```

### 4.1 数据归属字段

空间业务表按下表包含归属字段；用户、组织、平台目录和审计等表按各自领域规则，不强行塞同一个字段。

| 字段 | 类型建议 | 含义 |
|---|---|---|
| `id` | UUID | 这条记录自己的唯一编号 |
| `workspace_id` | UUID | 数据属于哪个个人或团队空间 |
| `owner_user_id` | UUID | 指向内部 user_accounts.id；不混用外部身份 ID |
| `team_id` | UUID，按组织表需要 | 通常由 workspaces 推导，业务表不重复保存；必要冗余必须有一致性约束 |
| `created_at` | timestamptz | 创建时间 |
| `updated_at` | timestamptz | 最近修改时间 |
| `deleted_at` | timestamptz，可为空 | 软删除时间；为空表示没有删除 |
| `version` | integer | 并发修改版本，防止覆盖别人刚改的内容 |

规则：`workspace_id` 是主要隔离字段。任何查询都必须带上当前用户有权访问的 `workspace_id`，不能只按 `id` 查询。

**<span style="font-size:18px;color:#fff">查任何数据都必须先带上当前所在的空间编号，不能只凭一条记录自己的编号就去查。不然拿着别人的记录编号就能看到别人的内容。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">规则：workspace_id 是主要隔离字段。任何查询都必须带上当前用户有权访问的 workspace_id，不能只按 id 查询。</span>

## 4C. 看表字段的统一格式

以后每张表都按下面的表格说明，不直接凭感觉建字段。

| 列名 | 专业含义 | 大白话 | 是否必填 | 关系或限制 |
|---|---|---|---|---|

## 5. 用户与身份模块

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 系统内部用户编号 |
| `appwrite_user_id` | varchar(64)，唯一 | Appwrite 用户编号 |
| `email` | text | 展示邮箱；身份唯一性由 Appwrite 确定，不额外依赖 citext 扩展 |
| `display_name` | varchar(100) | 昵称 |

| `timezone` | varchar(64) | 时区 |

### 5.2 `user_preferences` 用户偏好

主题、语言、默认模型、通知设置等可修改偏好单独存放，避免把用户主档案做成一张“万能表”。

**<span style="font-size:18px;color:#fff">你的昵称、邮箱这些固定身份信息单独存，深色模式、默认模型这类个人偏好设置也单独存。不要把所有东西都挤在一起，改个皮肤颜色还要动用户主信息。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">主题、语言、默认模型、通知设置等可修改偏好单独存放，避免把用户主档案做成一张“万能表”。</span>

### 5.3 登录安全

登录会话、密码重置、邮箱验证由 Appwrite 负责。PostgreSQL 只记录必要的业务事件，例如登录时间、封禁状态和安全审计摘要。

**<span style="font-size:18px;color:#fff">登录验证、密码重置、邮箱确认全由专门管登录的地方负责，我们这边只记必要的业务记录，比如登录时间、账号状态和安全摘要。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">登录会话、密码重置、邮箱验证由 Appwrite 负责。PostgreSQL 只记录必要的业务事件，例如登录时间、封禁状态和安全审计摘要。</span>

### 5.4 身份桥接与首次初始化

后端必须验证 Appwrite 身份凭据，不能拿客户端提交的 userId 或邮箱直接换发业务令牌。通过唯一 appwrite_user_id 幂等创建 user_accounts 和个人空间，处理两个并发首次登录以及创建中断重试。业务请求只使用内部 UUID，并检查账号和空间状态。

## 7. 角色与权限

### 7.1 权限分层

权限分三层：

1. **功能权限**：能不能使用某个功能，例如生成图片、删除资产、管理成员。
2. **资源权限**：能不能操作某条具体数据，例如只能改自己创建的资产。
3. **范围权限**：能操作个人数据、部门数据、团队数据，还是全平台数据。

**<span style="font-size:18px;color:#fff">权限分三层依次判断：先问你能不能用这个功能（比如能不能生图），再问你能不能动这一件具体东西（比如只能改自己的图），最后问你能看多大范围（比如只能看本部门，还是整个团队都能看）。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">权限分三层：功能权限、资源权限、范围权限。</span>

#### 防串数据、重试、查询与删除

**<span style="font-size:18px;color:#fff">关联时必须确认内容属于正确空间；失败重试不能多出一份文件。文件已经传好但登记失败，要能补登记或清理。删除时先检查还有哪些地方在使用，不能让其他项目突然打不开。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">新关系采用 (资源id, workspace_id) 复合外键并配套服务端授权和 RLS，父表提供对应唯一约束。当前同空间关系不得绕过外键做跨空间共享；跨空间分享继续走 asset_shares 授权，独立复制按第 10.1 节办理。跨空间任务输入若需要直接复用，必须另行设计包含分享授权凭据的关系，不能把他人 file_id 直接插入同空间表。</span>

1. 先登记待写入文件、稳定对象键及来源关系，再写 COS；校验内容后在数据库事务内登记必要关联并标记 ready。COS 写入与数据库事务不视为同一事务；确认上传对象存在、内容一致时重试补登记，不重复生成 ID。超时或状态不明时先核查，禁止直接当作失败删对象。
2. 清理与上传前缀对应的未完成文件、失败文件及孤立对象需要对账流程；不能仅依靠事务回滚，也不允许转存服务器硬盘。清理期限需另行确认。
3. 新关联资源使用 file_objects.status=ready 才能投入业务；pending 的生成输出仅供后台追踪，不得展示为成功。批次部分失败须逐文件反馈，生成任务结算沿用计费一致性规则，文件状态不直接代表扣费结果。
4. 按空间、类别、来源、状态、创建时间组合查询，规划索引 (workspace_id, media_type, source_kind, status, created_at DESC)；另为 upload_batch_id、source_file_id 和各关系反向查询建立索引，最终按实际查询验证。保留已有存储位置唯一约束，写入幂等键不能代替物理位置唯一性。
5. 删除前核查 asset_files、generation_outputs、generation_inputs、agent_attachments、派生文件及经资产关联的项目和集合；区分第 10.6 节活动占用与历史引用，不能仅因存在历史外键永久禁止清理，也不能跳过活动占用直接删 COS 原文件。新增引用与删除采用同一资源锁定和状态校验，避免检查后又新增引用。只有 COS 删除确认后才标记 deleted，失败保留待清理状态和错误原因。

**<span style="font-size:18px;color:#fff">这次确定的是字段设计，文件保存程序还没有改变。后续要用不同类型的内容实际验证分类、分组、重复重试和权限隔离，确认都正确再标记完成。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">验收矩阵需覆盖生成图片/视频/音频/文本、新参考附件、已有素材作为参考、手动混合上传、预览文件；验证目录与字段映射、同名不同文件、同键重试及冲突、批次部分失败、COS 成功但登记失败、跨空间拒绝、改分组不改对象键、引用未释放时禁止物理删除。迁移、接口及测试尚未实施。</span>

## 14. 删除、隐私和生命周期

1. 普通删除先使用 `deleted_at`，保留恢复窗口。
2. 用户注销后，身份由 Appwrite 删除或禁用；业务数据按保留策略匿名化或删除。

## 15A. 自建 PostgreSQL 到腾讯云托管 PostgreSQL 的迁移规范

当前数据库是装在轻量服务器上的自建 PostgreSQL。以后迁移到腾讯云托管 PostgreSQL 时，目标是“换数据库位置，不换业务规则”。

**<span style="font-size:18px;color:#fff">以后要把业务数据从现在自己搭的服务器搬到云服务商托管的存储上。搬的时候数据怎么存、谁能查、规则是什么全都不变，只是换个更稳定的地方放，用户完全感觉不到变化。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">当前数据库是装在轻量服务器上的自建 PostgreSQL。以后迁移到腾讯云托管 PostgreSQL 时，目标是“换数据库位置，不换业务规则”。</span>

### 15A.1 必须保持不变的部分

| 内容 | 要求 |
|---|---|
| 表名和字段名 | 迁移前后保持一致 |
| 主键和外键 | 保持一致，不重新生成业务编号 |
| 枚举和状态 | 保持一致，例如 `active`、`deleted` |
| API 接口 | 前端不需要因为换数据库而改接口 |
| 权限规则 | 不因数据库搬家而改变 |
| 时间和时区 | 统一使用 UTC 存储，展示时转换 |

### 15A.2 必须避免的写法

- 不把业务数据写死在服务器路径中；
- 不依赖某台机器的本地用户名；
- 不使用只在某个环境存在的临时表；
- 不把文件放进数据库二进制字段；
- 不让前端直接连接 PostgreSQL；
- 不把密码、API Key 和数据库连接串提交到 GitHub；
- 不用手工改表代替 Migration；
- 不把 `localhost` 写死在业务代码里，数据库地址必须来自环境变量。

**<span style="font-size:18px;color:#fff">这些"不许做"的规矩：不把路径写死在某台机器上、不依赖某台特定机器、不用只在某个环境才有的临时表、不把大文件塞进业务记录里、不让前端直接连业务存储、不把密钥密码公开写出来、不手动改表代替正规的版本变更流程、不把地址写成本机。一句话，让系统能随时搬到别的地方。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">15A.2 必须避免的写法：不写死服务器路径、不依赖本机用户名、不用临时表、不放二进制文件、不让前端直连、不提交密钥、不用手工改表代替 Migration、不写死 localhost。</span>

### 15A.3 连接配置标准

应用只读取环境变量，不读取开发电脑上的固定配置：

```text
DB_HOST=
DB_PORT=5432
DB_NAME=qingyu
DB_USER=
DB_PASSWORD=
DB_SSL_MODE=
DB_POOL_MIN=
DB_POOL_MAX=
```

目标是保持业务接口不变；实际迁移还要核验版本、网络、TLS 证书、账号权限、扩展、备份和恢复，不能只改地址。

**<span style="font-size:18px;color:#fff">连业务存储的地址、账号、密码不写在代码里，而是放在外部配置里，搬到哪填哪。换了环境光改个地址还不够，还得核对版本对不对、网络通不通、账号权限够不够、备份齐不齐，不能只改个地址就上线。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">应用只读取环境变量。实际迁移还要核验版本、网络、TLS 证书、账号权限、扩展、备份和恢复，不能只改地址。</span>

### 15A.4 迁移步骤

按《迁移与性能验收规范》执行：先恢复演练，再停止所有写入来源、完成最终备份与校验、配置目标库、只读验收，最后开放写入。订单回调、后台任务和 Agent 也必须受停写控制。

**<span style="font-size:18px;color:#fff">迁移顺序固定：先空跑一遍演练会不会出问题，再停掉所有写入、把最后一批数据备份好、搬过去、让大家只读验收一遍，确认没问题再重新开放写入。连后台自动跑的任务也得一起停，不然搬到一半又来新数据。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">按规范执行：先恢复演练，再停止所有写入来源、最终备份与校验、配置目标库、只读验收，最后开放写入。订单回调、后台任务和 Agent 也必须受停写控制。</span>

### 15A.5 回滚方法

目标库尚未收到业务写入时，确认旧库仍是权威数据后可以回切。目标库已经收到写入时，禁止直接切回旧库；必须先停写，保全新库增量并完成经演练的数据回灌和对账，或在新库修复。恢复不了一致性就维持维护状态，不能为了恢复页面而丢订单或作品。

**<span style="font-size:18px;color:#fff">迁移到一半发现新库有问题：要是还没人往新库写数据，直接退回旧库就行。可一旦已经有人在新库里用了，就绝不能直接切回旧库——那样新库这半天的数据就丢了。得先停写、把新库这半天多出来的数据补齐对平，搞不定就挂"系统维护中"，绝不为了让页面赶紧恢复就把订单和作品搞丢。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">目标库未收到写入可回切；已收到写入时禁止直接切回，必须先停写、保全新库增量、回灌对账或在新库修复。恢复不了就维持维护状态，不能为恢复页面而丢订单或作品。</span>

## 15B. PostgreSQL Migration 文件规范

每次表结构变更必须有版本化文件，例如：

```text
database/migrations/
├── 0001_create_users_and_workspaces.sql
├── 0002_create_teams_and_memberships.sql
├── 0003_create_roles_and_permissions.sql
├── 0004_create_billing_and_usage.sql
├── 0005_create_generations_and_assets.sql
└── 0006_create_audit_and_outbox.sql
```

Migration 必须满足：

1. 可以在一台空 PostgreSQL 上从零执行；
2. 同一版本不能重复执行；
3. 失败时能定位是哪一步；
4. 生产环境执行前先在测试库演练；
5. 高风险变更要有回滚或兼容期；
6. 不把真实用户数据写进 Migration 文件。

**<span style="font-size:18px;color:#fff">每回改表都要写一份变更说明，这份说明得满足：①拿到一台全新空环境能从头执行一遍；②同一份说明不能重复执行；③执行到哪一步出问题，一眼能看出是哪步；④正式环境上跑之前，先在测试环境试一遍；⑤大改动要留好回退的后路；⑥说明里不许夹带真实用户的名字和订单。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">Migration 必须满足：可在空库从零执行；同版本不重复执行；失败可定位；生产前先在测试库演练；高风险变更有回滚或兼容期；不写真实用户数据。</span>

这份需求通过后，至少应能回答：

- 每一条数据属于哪个用户、团队和空间；
- 一个用户能否读取这条数据；
- 谁可以创建、修改、分享和删除它；
- 重复请求是否会重复扣额度或重复创建；
- 用户离职、团队删除和账号注销后数据怎么处理；
- PostgreSQL、Appwrite、文件存储各自保存什么；
- 后续升级到 10 万用户时，哪些部分可以扩容，哪些部分需要拆分。

本规范确认前，不创建正式 Migration，不迁移 SQLite 数据，也不修改线上服务连接方式。

### 19.2 画布数据的逻辑层次与适度拆表

项目、节点、连接、文件是不同逻辑对象。初期节点配置可用 canvas_nodes.config JSONB，加 schema_version 和大小限制；只有配置独立查询、权限或更新频率确有需要才拆 canvas_node_configs。允许有版本的项目快照用于恢复，但不能让它与节点表同时成为可写权威。

**<span style="font-size:18px;color:#fff">画布上的"项目、方块、连线、文件"是四样不同的东西，不能揉成一团。一开始每个方块的参数先存在它自己的配置里，等真有必要单独查、单独管了，再拆出去单独建表。可以存个整幅快照方便恢复，但快照只能用来回看，不能和方块表两边同时能改，不然不知道以谁为准。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">项目、节点、连接、文件是不同逻辑对象。初期节点配置可用 canvas_nodes.config JSONB，加 schema_version 和大小限制；确有需要才拆 canvas_node_configs。项目快照用于恢复，但不能与节点表同时成为可写权威。</span>

| 层 | 建议表 | 保存什么 | 不保存什么 |
|---|---|---|---|
| 项目层 | `canvas_projects` | 项目名称、所属空间、创建人、状态、版本 | 不把所有节点都塞成一列大 JSON |
| 节点层 | `canvas_nodes` | 节点类型、坐标、尺寸、标题、业务状态、排序 | 不把文件二进制直接放进节点 |
| 节点配置层 | canvas_nodes.config；canvas_node_configs 为可选拆分 | 各类型节点的参数快照、schema_version | 不让不同节点共用一套互相污染的字段 |
| 关系层 | `canvas_connections` | 起点节点、终点节点、端口、关系类型 | 不用前端数组下标当永久 ID |
| 结果层 | `generation_tasks`、`generation_outputs` | 请求、状态、模型、耗时、错误、结果文件 | 不把“正在生成”的临时状态当最终结果 |
| 会话层 | `canvas_chat_sessions`、`canvas_chat_messages` | 项目内问答历史和引用节点 | 不与全局 Agent 线程混成一张消息表 |
| 展示层 | `canvas_views` 或项目字段 | 视口、背景、显示选项 | 不让展示偏好决定业务归属 |

### 19.3 未来加新功能时的固定接入方式

新增功能必须先归入一个业务模块，再决定它依赖哪一个已有聚合。不能直接在任意表里加几个字段。

**<span style="font-size:18px;color:#fff">加新功能先想清楚它归哪个业务模块、跟哪些已有数据有关，再动手。不许图省事随手在别的表里加几个字段。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">新增功能必须先归入一个业务模块，再决定它依赖哪一个已有聚合。不能直接在任意表里加几个字段。</span>

```text
新功能
├── 先判断归属空间：个人 workspace / 团队 workspace
├── 再判断业务模块：canvas / asset / generation / billing / agent / admin
├── 优先复用既有实体；有独立业务事实时才新增主表
├── 通过外键关联已有主表：例如 workspace_id、user_id、asset_id、task_id
├── 需要跨模块通知时：写 outbox_events，不直接互相改表
├── 需要统计时：用独立分析事件；计费消耗才写 usage_records
└── 需要大文件时：写 file_objects 元数据，文件放对象存储
```

新增表必须回答五个问题：

1. 这条数据的唯一事实来源是哪张表？
2. 它属于哪个 `workspace_id`，个人还是团队？
3. 谁能读、谁能改、谁能删除？
4. 删除后要不要保留审计、账务或合规记录？
5. 查询最常用的条件是什么，是否已经有对应索引？

### 19.4 保持整洁、避免串数据和避免变慢的硬规则

**<span style="font-size:18px;color:#fff">下面这张表是必须遵守的硬规则：数据各归各的模块、每条数据都标上属于哪个空间、查数据必须带空间编号、扣费和记录要么全成功要么全失败、实时状态不存进业务记录、大文件不放进业务记录、列表必须分页、两人同时改不能互相覆盖、模块之间不直接互相调用。守住这些，系统才不会越跑越乱、越跑越慢。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">19.4 硬规则表：模块边界、归属必填、外键唯一约束、查询权限、事务边界、不写实时状态、大字段分离、分页索引、乐观并发、事件解耦、统一命名、禁止隐式 JSON、机密分离、可迁移。</span>

| 规则 | 具体要求 | 解决的问题 |
|---|---|---|
| 模块边界 | 初期采用单数据库、应用模块目录分组；不要求每个模块建立独立服务或 schema。领域包括：`identity`、`workspaces`、`iam`、`canvas`、`generation`、`asset`、`billing`、`agent`、`admin` | 新功能有固定位置，不会随便塞表 |
| 归属必填 | 空间业务表带 workspace_id；用户偏好带 user_id，组织表带 team_id，全局模型目录由平台管理；不能强塞同一字段到所有表 | 防止 A 用户看到 B 用户数据 |
| 外键和唯一约束 | 所有关系用外键；业务幂等键、成员关系、点赞关系、订单号加唯一约束 | 防止重复数据和孤儿数据 |
| 查询权限 | 服务端每次查询先确定当前用户可访问的 workspace 集合，再查询业务记录 | 防止只按 ID 查询造成越权 |
| 事务边界 | 创建订单、扣额度、生成任务、写结果等操作用短事务；大文件上传不占事务 | 防止半成功和锁表太久 |
| 不把实时状态写库 | 并发数、SSE 连接、Agent 在线状态放进程内存/Redis；只定时写汇总 | 防止每个请求都打 PostgreSQL |
| 大字段分离 | 画布快照、原始响应、长文本、文件正文放对象存储或分表；主表保留摘要和引用 | 防止列表查询被大字段拖慢 |
| 分页和索引 | 所有列表接口必须分页；按 `workspace_id + updated_at`、`workspace_id + status` 建索引 | 防止用户一多就全表扫描 |
| 乐观并发 | 记录 `version`；更新时带旧版本条件，不一致就返回冲突 | 防止两个人互相覆盖数据 |
| 事件解耦 | 普通跨模块动作由应用服务同步编排、模块各自写入；需要异步可靠投递时才使用 outbox_events，并实现消费去重 | 防止互相调用导致循环和脏数据 |
| 统一命名 | 表名复数 snake_case，外键统一 `_id`，时间统一 `timestamptz`，状态使用受控值 | 以后看表就知道是什么 |
| 禁止隐式 JSON | JSONB 只用于确实会变化的配置或原始快照；可查询、可关联、可统计的字段必须独立列 | 防止“什么都能放但什么都查不清” |
| 机密分离 | API Key、WebDAV 密码、Agent Token 只保存密文/引用，业务表不返回明文 | 防止后台泄密 |
| 可迁移 | 目标结构不使用 SQLite 专有语法；扩展仅在源库和目标库均验证支持后使用，不依赖云厂商私有业务格式 | 以后迁移到腾讯云托管 PostgreSQL 不重写业务 |

### 19.5 当前实现与目标架构的差距清单

**<span style="font-size:18px;color:#fff">这张表列了现状和目标的差距：现在数据大多存在你自己浏览器里（换手机就没了）、老系统还是临时凑合的、密钥明文存在网页里、实时数据记在内存里重启就丢。右边是以后要改成的样子——数据搬回服务器、密钥由后台保管、业务数据和缓存分开。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">19.5 差距清单：浏览器本地数据、SQLite 临时表、内存态统计、localStorage 密钥等现状与目标架构对比。</span>

| 当前情况 | 风险 | 目标改法 |
|---|---|---|
| 画布、资产和生成日志主要在浏览器本地 | 换设备看不到；清缓存可能丢数据；团队无法共享 | 登录后以 PostgreSQL 为主，浏览器只做缓存和离线草稿 |
| qingyu_server 仍使用 SQLite 用户、画布和 API Key 表 | 当前表结构和身份链路未形成完整多租户约束；不能仅凭 SQLite 名称判断是否安全 | 新接口直接按 PostgreSQL 目标模型实现，不继续扩展 SQLite schema |
| 所查 http.ts 主入口创建单个 CanvasSession；tenant-manager.ts 的 token 前缀逻辑未证明已接入主入口 | 重启、扩容和多实例时状态可能不一致 | 按内部 workspace_id、user_id、thread_id 验权和隔离；持久化任务与审批，实时连接可按规模使用 Redis；禁止 token 前缀充当身份 |
| Appwrite 同时承担身份和团队列表 | 业务团队权限若分散在两处，容易出现权限不一致 | Appwrite 只认身份；团队、岗位、权限以 PostgreSQL 为唯一事实来源 |
| API Key 实时统计在单进程内存 | 多实例统计会分叉，重启会丢 | Redis 做实时计数，PostgreSQL 做按日汇总 |
| 前端 localStorage 保存多种 Token 和 API 配置 | 容易泄露，也无法统一撤销 | 生产环境改成 HttpOnly 会话和服务端密钥引用；本地配置仅用于开发 |
| 远程提示词、插件和 WebDAV 数据可能直接覆盖本地数据 | 同步时会覆盖新数据或产生混合版本 | 使用版本号、内容哈希、同步批次和冲突记录，默认不静默覆盖 |

### 19.7 以“新增一个功能”为例

假设以后增加“团队模板市场”：

1. 模板本身属于 `asset`，建立 `asset_templates`，带 `workspace_id` 和发布状态。
2. 模板引用的图片、视频仍通过 `asset_files` 关联，不复制文件。
3. 购买或额度扣减属于 `billing`，建立订单和额度流水，不在模板表里加余额字段。
4. 购买成功通知属于 `collaboration/governance`，通过 `outbox_events` 发送。
5. 模板市场的搜索统计属于分析数据，不把访问次数不断写回模板主表。

这样增加功能时，每个数据仍然有固定位置，模块之间通过明确的 ID 和事件连接，后续迁移时分别核验 PostgreSQL、文件、Appwrite 身份和 Agent 历史依赖；只换数据库位置不等于搬完全部系统。

**<span style="font-size:18px;color:#fff">比如做"团队模板市场"这个新功能：模板本身归资产模块管、收费的事归计费模块管、通知归消息模块管、点赞数归互动模块管。每样数据都有固定位置，模块之间通过编号和事件联系。以后迁移时，业务存储、文件、登录身份、历史记录得分别核对——只换业务存储不等于把整个系统都搬了。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">新增功能时每个数据仍有固定位置，模块之间通过明确 ID 和事件连接；迁移时分别核验 PostgreSQL、文件、Appwrite 身份和 Agent 历史依赖，只换数据库位置不等于搬完全部系统。</span>

## 20. 本次代码审计后的结论

当前系统不是只有“用户、团队、订阅、资产”四类数据。实际还包含画布结构、生成过程、模型目录、密钥路由、插件、提示词、Agent 工作流、同步、文件、计费流水、运营后台和本地缓存等数据。

数据库设计的核心不是把字段列得越多越好，而是让每条数据只有一个明确的主人：身份归 Appwrite，业务事实归 PostgreSQL，文件归对象存储，实时状态归 Redis，浏览器只保存缓存和草稿。这只是隔离和扩展的设计基础；是否真正防串数据，要以实现后的越权、并发、缓存、文件和消息测试为准。

**<span style="font-size:18px;color:#fff">数据设计的关键不是表建得越多越好，而是每样数据只有一个明确的归属：登录身份由专门管登录的地方负责、业务记录存在我们这边、文件存在专门存文件的地方、实时状态由缓存负责、你浏览器里只存临时草稿。这只是设计稿，真正能不能防止用户之间数据串了，还得靠以后实际测试来验证。</span>**<br><span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">数据库设计核心是让每条数据只有一个明确主人：身份归 Appwrite，业务事实归 PostgreSQL，文件归对象存储，实时状态归 Redis，浏览器只存缓存和草稿。是否真正防串数据以实现后的测试为准。</span>
