## 每次上线后怎么收尾

8. **<span style="font-size:18px;color:#fff">新版本确认能正常使用后，再清理本次上传的临时文件。发布失败时，先保留排查需要的内容并登记，不能一失败就把证据删掉，也不能永久堆着不处理。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">发布收尾依次核对提交/发布标识、实际生效版本、首页及引用资源、相关 API 和服务状态，再对本次任务独占且已无用途的 staging 目录生成清理清单。失败任务登记原因、责任人及复查时间。清理须避开并发上传、构建、迁移与恢复任务；不能按通配符删除所有 qingyu-upload*。现有 .github/workflows/deploy.yml 已包含成功路径下删除 qingyu-upload，不代表历史残留已有治理机制。</span>


9. **<span style="font-size:18px;color:#fff">旧版页面可能还开在用户浏览器里，旧文件不能上线后马上删。先确认哪些文件还需要，再按约定的保留时间处理。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">延续部署流程中的旧哈希资源保留要求：保护当前版本、必要回退版本、仍在支持窗口内的客户端资源及有效缓存引用。仅首页不再引用不等于无人使用；禁止发布前清空正式目录。资源保留时间需结合缓存策略、客户端生命周期和回退窗口确认，未确认前不启用按年龄自动删除。</span>

## 运行记录不能无限增长

12. **<span style="font-size:18px;color:#fff">每个长期运行的软件都要限制运行记录占用，达到上限后按规则替换最旧的记录。保留多久要兼顾排查需要，不能等硬盘快满了才全部清空。</span>**<br>
