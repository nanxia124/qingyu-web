### 这是什么
规定用户花了几次额度、系统扣了多少钱、生图任务有没有成功，保证不出错。

### 用户怎么用
- 点生成先锁住一次额度，防止重复点扣多次
- 图成功出来正式扣额度，失败了锁的额度自动退回
- "我的额度"数字和实际扣的对得上

## 2. 一次生成的完整流程

```text
认证、空间权限与权益检查
    → 幂等校验
    → 短事务：原子预占额度 + 创建任务 + 写 Outbox
    → 提交后返回 task_id
    → Worker 领取任务并记录租约
    → 事务外调用 AI / 上传文件
    → 短事务：写结果 + 记录用量 + 结算或释放预占 + 更新状态
    → 异步通知与统计
```

大白话：先把这次预算留住，再生成；成功后按规则结账，把多留的钱释放。耗时的外部请求不能一直占着数据库事务。

额度预占必须通过数据库条件更新或行锁原子完成：可用余额足够才同时减少 available、增加 reserved。任务、预占流水和 Outbox 同事务提交，任一步失败全部回滚。所有流程按固定账户顺序加锁；遇到死锁或序列化失败，只做有上限且幂等的重试。

幂等键范围为 (workspace_id,created_by,operation,idempotency_key)。相同键和相同请求返回原任务；相同键而请求内容不同返回 409。平台支付回调使用提供商事件编号，不能由浏览器伪造。幂等保留期限必须长于客户端、队列和回调的最大重试窗口。

1. **<span style="font-size:18px;color:#fff">你点生成后，系统按顺序做：先确认你已登录、有没有可用额度，然后记下这次任务，先把要扣的额度冻结，再把请求发给模型，图出来后正式扣额度。等模型生成的那段时间，后台不能一直占着连接。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">流程：认证/空间/权益检查 → 幂等校验 → 短事务（原子预占额度+建任务+写 Outbox）→ 返回 task_id → Worker 领取并记租约 → 事务外调 AI/上传 → 短事务（写结果+记用量+结算或释放+更新状态）→ 异步通知统计。</span>



2. **<span style="font-size:18px;color:#fff">冻结额度这一步必须原子完成：先看你余额够不够，够了就同时把可用的减掉、冻结的加上，一步到位，不能分两步中间被插队。任务、冻结记录、要发的通知必须同时成功，哪步没成功就全部撤销重来。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">预占通过条件更新或行锁原子完成：余额足够才同时减 available、加 reserved；任务/预占流水/Outbox 同事务提交，任一步失败全回滚；按固定账户顺序加锁；死锁/序列化失败只做有上限且幂等的重试。</span>



3. **<span style="font-size:18px;color:#fff">每笔请求都带一个唯一编号，同一个编号再来就把上次的结果原样还给你，不会再扣一遍——就算你手抖连点三次也只扣一次。但要是同一个编号、内容却不一样，直接报错不给办。支付平台发回来的消息只认它自己给的流水号，不能你在网页上自己编一个。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">幂等键范围 (workspace_id,created_by,operation,idempotency_key)；同键同请求返回原任务，同键不同内容返回 409；支付回调使用提供商事件编号，浏览器不可伪造；幂等保留期须长于客户端/队列/回调最大重试窗口。</span>

## 3. 状态与异常处理

| 场景 | 状态与处理 | 不能做什么 |
|---|---|---|
| 还在排队 | queued；允许原子取消并释放预占 | 不能取消后仍被 Worker 领取 |
| 已被领取 | running；有效租约持有者推进状态 | 不能两个 Worker 同时有效结算 |
| 用户请求停止 | cancel_requested；等待外部停止结果 | 不能直接认定未产生上游费用 |
| 成功且文件确认就绪 | succeeded；结算实际额度并释放差额 | 不能文件没落地就显示永久保存成功 |
| 确认失败且无可计费用量 | failed；释放预占 | 不能只改任务状态而遗漏流水 |
| 超时、断网、上游结果不明 | reconciling；查询上游状态，保留待核对额度 | 不能自动当失败再发一次付费请求 |
| 部分结果成功 | 记录每个输出和实际用量；按价格快照结算 | 不能把失败输出算成完整成功 |
| Worker 重启或租约过期 | 恢复查询；新 lease_token 排除旧 Worker 的迟到写入 | 不能只恢复内存状态就算任务可靠 |

当上游支持幂等键时传递稳定请求标识；不支持时不能承诺外部调用“恰好一次”。发生结果不明时进入对账，避免盲目重试。对于流式、无法预知总量的请求，设定最大预算，超预算前追加预占或停止；不能先透支再把余额写成负数。

预占到期需要先核验任务和提供商状态，再释放。未解决的结果不明应进入告警和人工处理时限，不能无限占用用户额度。最终业务期限和付费规则在收费前确认。

1. **<span style="font-size:18px;color:#fff">生图任务有好几种状态：排队中、正在生成、用户要求取消、成功、失败、结果不明。每种状态该怎么办、绝对不能怎么办，都列在表里。比如用户中途要求取消，不能立马当一分钱没花——模型那边可能已经在处理了。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">任务状态机：queued（可原子取消并释放）、running（有效租约持有者推进）、cancel_requested（等外部停止结果，不认定无费用）、succeeded（文件就绪才结算并释放差额）、failed（无费用则释放预占，不遗漏流水）、reconciling（查上游、保留待核对额度，不盲目重发）、部分成功按输出与用量结算；Worker 重启靠新 lease_token 排除迟到写入。</span>



2. **<span style="font-size:18px;color:#fff">如果模型服务本身支持”同一个请求别重复处理”，我们就把请求编号传过去；它不支持的，我们也不敢保证”绝对只做一次”。联系不上模型服务时就进”待核对”，绝不能重新发一次请求——那就变成做两次收两次钱了。遇到边做边出量、不知道总共要花多少的活，先定一个最高预算，快超了就再加冻或者干脆停，绝不能先透支再把余额写成负数。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">上游支持幂等键则传稳定请求标识，不支持时不承诺外部调用恰好一次；结果不明进入对账不盲目重试；流式不可预知总量请求设最大预算，超预算前追加预占或停止，不透支成负余额。</span>



3. **<span style="font-size:18px;color:#fff">冻结的额度不会无限期占着。时间到了先去查清楚这单到底成没成，再决定是结账还是解冻；查不清的要报警给人工处理，不能一直占着你的额度不给你用。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">预占到期先核验任务与提供商状态再释放；未解决的结果不明进入告警和人工处理时限，不无限占用用户额度；最终业务期限与付费规则收费前确认。</span>

## 4. 支付、退款、兑换与对账

目标规则：回调先验签，将通知收件记录与待处理标记同事务可靠保存，再按渠道协议确认接收。处理时校验商户、订单、金额、币种、最终支付状态；每笔真实收款与订单支付状态、待发放任务同事务提交，无法归属的可信实收进入待核账记录。随后将订阅变更、额度流水、发放唯一标记及 Outbox 同事务提交。发放失败保留实收事实并重试，不回滚外部收款，也不要求用户再付款。各阶段使用短事务，远程查单不占数据库锁。客户端跳转到“支付成功”页面不能触发发放；可信的服务端主动查单可作为确认依据。

重复回调返回相同结果；乱序事件不得把已支付订单退回待支付。退款以支付平台确认结果为准，用关联原流水的冲正记录调整，不删除原支付。已经消费的额度怎么抵扣、部分退款规则、取消生成的计费条件均为待确认产品规则，未确定前不能开启对应收费功能。

兑换码需有效期、适用方案、使用次数上限和兑换记录；在事务中原子占用。邀请奖励需唯一的合格事件记录，不能反复注册或重复回调无限领额度。初期不启用未经定义的奖励功能。

| 对账对象 | 必须核对 |
|---|---|
| 额度账户 | 从起始值和所有流水可重建 available/reserved，且余额非负 |
| 预占 | 预占总量 = 已结算 + 已释放 + 未决部分 |
| 任务 | 每个终态有唯一结算决议；无悬空输出和未处理预占 |
| 支付 | 每笔实收均须关联原订单或待核账记录；同订单可有多笔实收，正常购买只触发一次权益计划，各期只发一次；逐笔支付限制退款金额，正常商品退款另受订单政策限制，多收款退款不得误回收正常权益 |
| 供应商成本 | 与用户收费分别记录；上游花费不等于用户扣费 |

1. **<span style="font-size:18px;color:#fff">先检查付款消息是真是假，再保存消息。确认收到钱后，要记清这笔钱和还没办完的会员开通。开通中途失败就继续补办，不能把收过的钱抹掉，也不能让用户再付一次。网页显示付款成功本身不算凭证，还要向付款平台核实。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">统一分阶段事务：Inbox+待处理标记；验证后的 payments+订单支付状态+fulfillment 待办；订阅+额度流水+发放唯一标记+Outbox。阶段间持久重试，发放幂等。验签回调或可信服务端查单确认收款，浏览器回跳不能证明到账。目标方案，当前实现差距见支付规范第 3.1 节。</span>



2. **<span style="font-size:18px;color:#fff">支付平台可能因为没收到我们的确认而重复发消息，重复发就回同一个结果，不能退了又付、付了又退。退款以支付平台说的为准，退了就在原流水上补一笔“冲正”，不把原来那条付款记录删掉。已经花掉的额度怎么退、退多少，这些规矩还没定，没定之前不能开收费。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">重复回调返回相同结果；乱序事件不把已支付退回待支付；退款以支付平台确认结果为准，用关联原流水的冲正记录调整，不删除原支付；已消费额度抵扣、部分退款、取消计费条件未定前不开对应收费。</span>



3. **<span style="font-size:18px;color:#fff">兑换码有有效期、只能用于指定套餐、一张码只能用一次，用一次就作废。邀请好友送额度也一样，得有一笔真实的”谁邀请了谁”的记录，不能反复注册小号、反复回调来刷额度。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">兑换码需有效期、适用方案、使用次数上限和兑换记录，事务中原子占用；邀请奖励需唯一合格事件记录，不能反复注册或重复回调无限领额度；初期不启用未定义奖励。</span>



4. **<span style="font-size:18px;color:#fff">账户上的余额，必须能从起始值加上每一笔进出记录一笔一笔重新算出来，不能对不上。冻结的额度必须等于”已经结算的+已经释放的+还冻着的”，三方加起来不多不少。我们付给模型厂商的钱和我们向用户收的钱是分开记的，不能混为一谈。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">对账：额度账户可从起始值+全部流水重建 available/reserved 且非负；预占总量=已结算+已释放+未决；每终态任务有唯一结算决议，无悬空输出与未处理预占；每笔实收关联订单或待核账记录，允许同单多笔实收，权益计划与每期发放各自去重；逐笔退款不超可退额；供应商成本与用户收费分别记录。</span>

5. **<span style="font-size:18px;color:#fff">付重的钱和正常购买的钱分别退。比如 100 元订单误付了两次，退多收的 100 元不能顺手取消正常会员；另一笔也需要退款时，要单独处理。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">退款区分商品退款与 duplicate_payment；待审批、处理中、成功、未知占用逐笔支付的可退额；驳回/取消须确认未送渠道，失败须为明确终态才释放。与拒付核对避免双计。订单退款状态按正常购买分配判断，不能累计所有退款达到订单金额就认定商品全退。完整规则见支付规范第 10 节，现有订单级退款约束尚待调整。</span>

### 4.1 自动续费的扣款与权益一致性（目标规则）

**<span style="font-size:18px;color:#fff">每一期会员都有自己的账单。反复收到同一期的消息，只能开通一次；下一期必须单独记，不能覆盖上个月的收款。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">唯一账期键为订阅与固定周期/sequence，关联唯一续费订单；扣款尝试可多次，但每笔实收全部登记。每账期只生成一次权益计划，各分期独立去重。价格、授权、优惠、时区、账期边界及权益规则均固化版本。字段与验收以支付规范第 9.2—9.8、13.1 节为准。</span>


**<span style="font-size:18px;color:#fff">平台定时扣款和网站定时扣款只能选一个。扣款卡住了先查清结果，不能因为没收到回应就重新扣钱。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">每订阅 collection_owner 唯一，含失败重试职责；同账期扣款用稳定渠道标识，未知结果仅查询原尝试。明确终态软失败才允许有界重试；每次重试复核授权、取消、金额与提醒条件。手动补缴须控制原自动尝试，不能并行双收。</span>


**<span style="font-size:18px;color:#fff">用户取消后要保留已买的会员，并停止后续扣款。取消时已经开始处理的那笔，要显示正在核对；不能说取消成功后就不管了。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">本地取消与派发通过订阅锁/版本裁决，渠道取消结果独立持久化；取消请求先阻止新本地派发及重试，网络已发送或渠道托管在途款主动核对。provider_cancel_status 确认后才能宣告未来停扣；paid_through_at 独立保留。未知结果不能释放为可重扣状态。</span>


**<span style="font-size:18px;color:#fff">续费退款只处理对应月份；恢复旧记录后，先检查用户是否已经取消，再恢复工作。不能把已取消的自动续费重新打开。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">退款关联原账期/支付/发放批次，退款后的未来续费策略单独版本化。恢复须隔离旧执行者，核对渠道授权与解约、停机期间自动扣款、原账期实收及退款；重放原操作键，不以当前日期重建历史应收或盲补扣。未经同意的价格/周期变化不进入扣款。</span>

提醒提前量、重试次数、宽限期等候选值集中在 [支付接入需求规范](19-支付接入需求规范.md) 第 9.4 节维护；它们是待确认建议，不是当前生产配置。自动续费需 PAY 基础验收和全部 AUTO 专项验收通过后才能开放。

## 5. 投递、验收与上线门槛

Outbox 消费按至少一次投递设计；消费者以 event_id 或业务唯一键去重，处理结果和去重记录原子提交。重试有次数和退避，超过上限进入待处理队列并告警。初期可用 PostgreSQL 持久任务表轮询，不强制部署 Redis 或独立消息队列。

必须验证：余额仅够一次时并发发起十次；同一请求重复发送；同键不同内容；回调重复和乱序；Worker 领取后崩溃；外部成功而本地超时；取消与成功同时到达；部分成功；重复退款；交易处理中断库。允许拒绝或等待核对，不允许重复发权益、余额负数、跨空间结算和无记录丢单。

本规范同时定义当前实现和后续验收要求。额度保护、可恢复任务和重复请求防护已经落地；正式收费前仍必须通过真实支付沙箱、供应商回调、超时核对和供应商成本对账验收。

1. **<span style="font-size:18px;color:#fff">通知这种事（比如”图生成好了”），就算系统发的时候出故障了也不能丢。做法是：业务操作和”待会要发通知”记录在同一条数据里，稍后有定时任务去检查这些记录、把通知补发出去，发多遍也不怕——因为每条通知都有编号，发过就记下来，不会重复发。初期不用上专门的消息队列，让后台定时检查就行。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">Outbox 至少一次投递，消费者按 event_id/业务唯一键去重，处理与去重记录原子提交；重试有次数与退避，超限进待处理队列并告警；初期可用 PostgreSQL 持久任务表轮询，不强制 Redis/MQ。</span>



2. **<span style="font-size:18px;color:#fff">上线前得专门找茬测：余额只够一次时同时点十次、同一请求重复发、编号一样内容不同、支付消息重复和乱序、后台做到一半崩了、外面成功了这边超时、取消和成功同时到、部分成功、重复退款、做到一半后台崩了。这些情况下可以拒绝或者让你等，但绝不能重复送权益、余额变成负数、跨空间结算、或者无声无息丢单。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">必须验证：余额仅够一次时并发十次、重复请求、同键不同内容、回调重复与乱序、Worker 领取后崩溃、外部成功本地超时、取消与成功同时到达、部分成功、重复退款、交易中断库；允许拒绝或等待核对，不允许重复发权益/负余额/跨空间结算/无记录丢单。</span>



3. **<span style="font-size:18px;color:#fff">目前“额度保护、断了能接着做、重复请求不重复扣”这些已经做好了；但真收钱之前，还得拿真支付沙箱、真供应商回调、超时核对、供应商成本对账再过一遍关。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">额度保护、可恢复任务、重复请求防护已落地；正式收费前仍须通过真实支付沙箱、供应商回调、超时核对与供应商成本对账验收。</span>

## 6. 有没有预扣款：有额度预占，没有银行卡预授权

本系统当前实际采用的是预占平台额度，不是从用户银行卡、微信或支付宝自动扣款，也不是支付平台的预授权。目标现金支付规则：单次购买由用户确认订单；自动续费依据明确有效授权与固定账期发起，均以可信回调或服务端查单证明收款。不能把额度预占、自动扣款、银行卡预授权混用。预占链路已在数据库和 API 中实现；真实支付接入仍未完成，自动续费只是本次补齐的需求，不能认为已开启。

| 步骤 | 可用额度 | 冻结额度 | 已结算消耗 | 用户看到的意思 |
|---|---:|---:|---:|---|
| 初始 | 100 | 0 | 0 | 有 100 点可用 |
| 预估最多 20 点，原子预占 | 80 | 20 | 0 | 留出 20 点给当前任务，还没最终扣掉 |
| 实际使用 12 点，结算并释放 8 点 | 88 | 0 | 12 | 最终花了 12 点 |
| 若确认未执行即失败（另一分支） | 100 | 0 | 0 | 20 点全部释放 |

用户界面必须分别展示可用、冻结、已扣额度；每项都能展开到 task_id 和流水。禁止把冻结显示成最终扣费。预占数额由服务端按价格版本和用户确认的输入上限计算，客户端只能提出参数。

1. **<span style="font-size:18px;color:#fff">生成前预留使用额度，不等于从银行卡扣钱。普通购买需要你确认付款；以后开通自动续费，也必须先得到你的明确同意，才按约定的金额和时间扣款。两种付款都要核实真实结果，不能拿预留额度当成收到了钱。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">当前额度预占已实现，与 recurring billing、银行卡预授权不同；目标单次购买经用户确认，续费经有效 mandate 按固定账期执行，两者均验签/主动查单确认实收。真实支付与自动续费尚未完成接入及验收。</span>



2. **<span style="font-size:18px;color:#fff">举个例子：你有100积分，这单预估最多花20，就先圈出20（可用变80、冻结变20）；最后实际只用了12，就结12、把多圈的8退回来（可用变88、冻结0）。要是这单压根没做成，20全部退回来，你还是100。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">数值示例：初始 available=100/reserved=0；预占 20 后 80/20；实付 12 结算并释放 8 后 88/0、已结算 12；失败分支 100/0/0，20 全部释放。</span>



3. **<span style="font-size:18px;color:#fff">界面上“可用”“冻结”“已扣”三笔账要分开显示，每笔都能点进去看到是哪单花的。冻结的钱绝不能显示成“已经扣了”吓你。冻多少由后台按套餐价格和你确认的输入上限算，网页只能提参数，不能自己定。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">UI 须分别展示可用/冻结/已扣，每项可展开到 task_id 与流水；禁止把冻结显示成最终扣费；预占数额由服务端按价格版本与用户确认输入上限计算，客户端只提参数。</span>

### 6.1 预占状态和流水的数学约束

预占状态：active → partially_settled → closed，或 active → closed；状态在行锁内按累计金额计算。reconciling 是核对原因而非“已释放”。对于每条预占：累计预占（含追加）= 已结算 + 已释放 + 尚冻结；三者非负。已结算额度如需返还，另记 refund/compensation 流水，不把原结算数倒改成零。

| 动作 | available_delta | reserved_delta | 约束 |
|---|---:|---:|---|
| 预占 x | -x | +x | 可用足够且来源额度有效 |
| 结算 y | 0 | -y | y 不大于该预占尚冻结额 |
| 释放 z | +z | -z | 仅释放仍可用的来源额度；过期部分按下节处理 |
| 退款/补偿 r | +r | 0 | 引用原结算或批准的补偿事件，累计退款不超过可退额 |

余额和流水必须同事务更新；同一 operation_key 只能生效一次。定期重算并比较账户值，有差异就暂停受影响账户写入并告警，不自动挑一个数字覆盖。

1. **<span style="font-size:18px;color:#fff">冻结的演变路线是：刚冻上 → 结了一部分 → 全部结清，或者刚冻上直接结清。“正在核对”只是个待查原因，不等于已经把钱退给你。每笔冻结都得满足：冻掉的 = 结掉的 + 退掉的 + 还冻着的，三块都不能是负数。要往回退钱，就另写一笔退款记录，不把原来那条结账记录改成零。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">预占状态 active→partially_settled→closed 或 active→closed，行锁内按累计金额计算；reconciling 是核对原因非已释放；累计预占(含追加)=已结算+已释放+尚冻结，三者非负；已结算返还另记 refund/compensation，不倒改原结算为零。</span>



2. **<span style="font-size:18px;color:#fff">改余额和写流水必须同时发生。同一个编号只能生效一次。定期把流水从头加一遍和当前余额对，对不上就先把这个账号锁起来报警，不能自作主张挑一个数字覆盖另一个。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">余额与流水同事务更新；同一 operation_key 只生效一次；定期重算并比对账户值，有差异暂停受影响账户写入并告警，不自动挑一个数字覆盖。</span>

### 6.2 来源、到期、团队预算不能丢

需要增加以下记录；这不是再造一套余额，而是对同一额度流水补充来源分配。

| 记录 | 必要字段 | 防止什么错误 |
|---|---|---|
| quota_grants 额度发放批次 | id、workspace_id、account_id、source_type、source_id、unit、issued_amount、expires_at、policy_version_id | 订阅赠送、购买和奖励混在一起，无法判断到期或退款 |
| quota_allocations 预占来源分配 | id、workspace_id、reservation_id、grant_id、reserved_amount、settled_amount、released_amount | 一次预占跨多个批次后，不知道应该退回哪一批 |
| quota_ledger 补充字段 | grant_id、reservation_id、reverses_entry_id、reason_code、actor_type、actor_user_id | 扣费、过期、释放、退款和人工调整不可追踪 |
| workspace_member_budgets（启用成员预算时） | workspace_id、user_id、period_start、period_end、unit、limit_amount | 单成员耗光团队额度；它是消耗限制，不是独立发放余额 |

建议初期先消耗最早到期的可用批次。预占跨过到期时间后，已经接受任务的冻结部分按提交时规则处理；释放时原批次若已过期，应原子记录释放及过期冲销，不变回可花余额。累计账户余额应等于批次流水汇总。具体有效期、退款去向与补偿期限在收费前确认并版本化。

团队预算和团队总额度必须在同一事务下检查和预占，按固定顺序加锁；预算不是“额外一份钱”。任务创建后不可换 workspace 来逃避额度或成员限制。

1. **<span style="font-size:18px;color:#fff">光记”你有多少额度”还不够，还得记清楚这笔额度是哪来的：是订阅送的、买的、还是活动奖的，哪天到期。不然退钱时都不知道该退到哪一笔上。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">quota_grants 记发放批次（来源/金额/到期）、quota_allocations 记预占跨批次来源、quota_ledger 补 grant_id/reservation_id/reverses_entry_id 等追踪字段、workspace_member_budgets 记成员消耗上限；不是再造一套余额。</span>



2. **<span style="font-size:18px;color:#fff">花的时候先花最早过期的那批。如果一单冻着冻着跨了到期时间，已经接了任务的那部分按接单时的规矩办；退的时候原批次已经过期的，就记一笔”过期冲掉”，不退成你能继续花的钱。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">初期先消耗最早到期批次；预占跨到期时间时已接受任务的冻结部分按提交时规则处理，释放时原批次已过期则原子记释放及过期冲销，不变回可花余额；账户余额应等于批次流水汇总。</span>



3. **<span style="font-size:18px;color:#fff">团队总额度和每个成员的额度上限，得在同一笔操作里一起查、一起冻，按固定顺序来。成员预算不是”额外一份钱”，是从团队总额度里划给他的消费上限。任务一旦建了，不能把任务挪到别的空间来绕开额度限制。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">团队预算与团队总额度同事务检查和预占、固定顺序加锁；成员预算是消耗限制不是独立余额；任务创建后不可换 workspace 逃避额度或成员限制。</span>

### 6.3 预扣风险处理

| 场景 | 处理方案 |
|---|---|
| 双击、刷新、网络重发 | 同一个幂等键返回原预占和任务，不再冻结 |
| 费用可能超出预估 | 先原子追加预占且不得超用户确认预算；失败则停止继续消耗。已不可避免的上游超额进入平台成本差异，不擅自向用户追扣 |
| 取消与回调同时到达 | 按预占行锁、任务版本和操作唯一键裁决，不允许既全退又全扣 |
| 上游成功、归档失败 | 保留成本事实，只重试归档；用户结算按固定计价规则，不能重新生成并再收费 |
| 超时无法确认 | 进入核对，设置 next_reconcile_at、deadline_at、last_error、处理负责人；到期告警，不直接当失败 |
| 长期核对无结果 | 必须有收费前明确的冻结最长时限与释放/补偿策略；若已释放后收到成功回调，进入异常处理，禁止无授权追扣或重新预占 |
| 系统恢复后发现旧预占 | 先查支付/上游状态和独立回调记录，再恢复处理，不批量释放或重试 |

金额真实扣款、订阅生效、用户额度发放是关联的不同事实。支付成功而发放失败需由已持久化支付事件幂等补发；多次真实付款不能靠唯一约束假装第二笔不存在，须记录所有交易并进行退款或人工处理。

1. **<span style="font-size:18px;color:#fff">下面是各种幺蛾子情况怎么收拾：双击刷新→同一单号原样返回不再冻；费用可能超预估→最多加到你确认的预算就停，超出来的部分我们自己认，不偷偷追扣你；取消和回调同时到→按规矩裁决，不能既全退又全扣；外面成功了本地存档失败→只重试存档，不重新生成再收一次钱；一直查不清→挂起待人工，到期报警，绝不先当失败处理。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">风险处理：双击/刷新/重发同键返回原预占不重复冻结；超预估先原子追加且不超用户确认预算，不可避免的上游超额进平台成本差异不追扣；取消与回调同时到按行锁/版本/唯一键裁决；上游成功归档失败只重试归档不重新收费；超时进核对并设 next_reconcile_at/deadline_at；长期无结果须有冻结最长时限与释放/补偿策略；恢复后旧预占先查上游状态不批量释放。</span>



2. **<span style="font-size:18px;color:#fff">真扣钱、订阅生效、额度到账，这是三件互相挂钩但各自独立的事。钱付了但权益没发上，得靠支付消息去补发；真付了两次钱，不能靠“唯一约束”假装第二笔不存在，得把两笔都记下来，然后退款或者人工处理。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">真实扣款、订阅生效、额度发放是关联但不同的事实；支付成功而发放失败由已持久化支付事件幂等补发；多次真实付款不能靠唯一约束假装第二笔不存在，须记录所有交易并退款或人工处理。</span>

### 6.4 前端生成入口

所有面向用户的生图入口都必须进入统一的服务端计费生命周期；前端可以按页面和任务类型使用不同请求函数或异步任务接口，不要求全部共用同一个 `requestGeneration` 或 `requestEdit`。任何入口都不能绕过服务端登录、报价、余额检查、积分预留、幂等、生成结果核验及结算。请求参数至少包含会影响报价的模型、提示词、数量、画质和尺寸；接口返回的图片数据必须作为结果引用展示。接口失败时保持失败状态并显示错误，不能插入空图片或把失败当作成功。

1. **<span style="font-size:18px;color:#fff">所有你能点的生图按钮，都必须经过同一套登录、报价、余额检查、预留和结算规矩。不同页面可以有不同请求方式，但不能绕开扣积分流程，也不能用延时假装“图好了”。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">前端入口按页面/任务类型使用适合的 API，但全部进入同一 server-side billing lifecycle：身份校验→报价验证→原子预留→幂等创建→生成与结果核验→结算/释放/核对→刷新余额。参数覆盖会影响计价的模型/提示词/数量/画质/尺寸；接口返回结果作为资产展示，失败明确报错。</span>

### 6.5 渠道代理的"成功"要验真

**<span style="font-size:18px;color:#fff">渠道代理转发图片请求时，不能光看对方回了个"200 好的"就算成功。要拆开它回的内容看一眼，里面真的带了图片数据才算成功；如果 200 但里面是空的、或者是个错误提示，就记成失败，不能算一次有效调用。聊天、文字这种流式接口不受影响，还是原样转发。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">proxyRequest 对 targetPath 含 /images/ 的请求先缓冲整个响应体，JSON.parse 后检查 data 数组是否有 b64_json、url 或 task_id；有则 committed，空 data 或解析失败记 failed 并写 phase=empty_image/bad_json。chat/responses 等流式路径保持 pipe 转发不变。避免上游 200 包错导致渠道调用数虚高。</span>
