# 迁移与性能验收规范

版本：0.3。状态：执行与验收要求，尚未做压测、恢复或迁移演练。返回 [总览](01-数据库与多租户总览.md)。

### 这是什么
以后把数据库从自己服务器搬到腾讯云托管数据库时，怎么搬不出事。

### 用户怎么用
用户不直接接触，效果是搬家过程中数据不丢、搬完后东西一样、网站不变慢。

### 现在长什么样
搬什么不搬什么已列清楚，还没真搬，压测也没做。

## 1. 迁移目标与边界

目标是自建 PostgreSQL 到腾讯云托管 PostgreSQL 时保持业务编号、数据归属和接口语义一致。不能在未演练的情况下承诺“零停机、零丢失、完美迁移”。初期优先选择可控制的停写迁移，实际停机时长由恢复演练决定。

| 对象 | 处理方式 | 不可遗漏 |
|---|---|---|
| PostgreSQL 业务数据 | 逻辑备份与恢复；版本兼容性先验证 | 表、约束、索引、视图、序列、函数、触发器、RLS、权限与迁移版本 |
| Appwrite 身份 | 原服务保留或独立迁移 | 普通 PostgreSQL 业务备份不包含登录身份、密码、Appwrite 自身依赖 |
| 文件存储 | 可原地保留；如迁移则复制对象并核验 | 路径映射、对象版本、大小、校验和、访问策略、未完成上传 |
| Agent 状态 | 持久数据随对应表或文件迁移，运行中任务先排空或登记恢复 | 历史、附件、技能、审批、供应商任务编号 |
| 缓存、搜索 | 从权威数据重建，切换后使用新版本命名空间 | 不把旧权限缓存带到新环境 |
| 密钥与配置 | 受控迁移，验证目标环境可解密 | 数据库账号、TLS 根证书、密钥版本、第三方回调和网络规则 |

迁移前检查轻量服务器到托管数据库的实际私网连通路径、目标地域、证书校验和最小访问规则。不能仅因为在同一地域就假定可以连接，也不能靠公开数据库端口解决。

扩展不是一律禁止，但必须在目标产品版本和权限范围验证可用。数据库角色和超级用户能力通常不能原样照搬，须在目标端按应用最小权限重建。版本支持和腾讯云具体限制在实际购买与迁移时重新核实。

1. **<span style="font-size:18px;color:#fff">迁移的目标是把后台数据从自己服务器搬到腾讯云托管库，表名、编号、数据归属、点按钮后系统怎么回应，统统不变。但没演习过就不能保证”全程不停机、一个数不丢、完美搬完”。初期选可控的停写迁移，真停多久得先演习一遍才知道。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">目标：自建 PostgreSQL 到腾讯云托管 PostgreSQL 保持业务编号、数据归属、接口语义一致；未演练前不承诺零停机/零丢失/完美迁移；初期优先可控停写迁移，停机时长由恢复演练决定。</span>



2. **<span style="font-size:18px;color:#fff">迁移的时候不是只搬业务数据这一样。登录账号、存的图片视频文件、正在跑的AI任务、缓存、访问密钥，各有各的搬法，漏一样都出问题。下面这张表列了每样东西怎么搬、哪些细节不能漏——比如普通业务数据备份里是不包含登录密码的，得单独搬。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">迁移对象：PostgreSQL 业务数据（逻辑备份恢复，含表/约束/索引/视图/序列/函数/触发器/RLS/权限/迁移版本）；Appwrite 身份独立保留或迁移；文件存储原地保留或复制核验；Agent 持久数据随表迁移、运行中任务先排空；缓存搜索从权威数据重建；密钥配置受控迁移并验证可解密。</span>



3. **<span style="font-size:18px;color:#fff">搬之前先实测两条服务器之间的网络通不通，不能想当然觉得”同一个地区肯定能连”，也不能图省事把后台端口直接暴露在公网上。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">迁移前检查私网连通路径、目标地域、证书校验、最小访问规则；不因同地域假定可连，不靠公开端口解决。</span>



4. **<span style="font-size:18px;color:#fff">后台数据里有些特殊功能（扩展插件）不是不能用，但得先确认目标环境那个版本支持、权限也够。原来那个”超级管理员”权限不能原样搬过去，目标环境要按”够用就行”的最小权限重新开账号。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">扩展须在目标版本与权限范围验证可用；数据库角色与超级用户能力不照搬，目标端按应用最小权限重建；版本支持与腾讯云限制实际购买迁移时重新核实。</span>

## 2. 停写迁移步骤和通过条件

| 阶段 | 动作 | 通过条件 / 失败处理 |
|---|---|---|
| 预演 | 在隔离目标恢复测试备份；核对权限、关键业务与性能 | 记录备份大小、耗时、错误和恢复步骤；失败则修复后重演，不进入正式切换 |
| 冻结变更 | 固定应用与数据库脚本版本，暂停结构变更 | 记录版本和校验值；禁止迁移中顺带升级业务 |
| 控制所有写入 | 停止用户写接口、Worker、计划任务、Agent 写入、同步和管理员写入 | 确认没有旧连接继续写入；回调选择经验证的提供商重试或独立持久收件箱，未持久接收不得返回成功 |
| 排空任务 | 完成或登记在途任务、支付与未决额度 | 每个未完成工作有唯一编号、恢复方案和负责人 |
| 最终备份 | 记录时间点，保存备份校验和并恢复到目标 | 只有预演备份不算最终数据；恢复报错立即停止 |
| 数据核验 | 核对行数、主外键、抽样内容校验、关键账务总额、序列、文件引用和身份映射 | 无无法解释的差异，额度/支付逐笔可对账 |
| 配置切换 | 停写状态下更新连接配置，关闭旧池，验证 TLS、权限与所有实例指向 | 新旧不能双写；包括后台进程而不只是网页服务 |
| 只读验收 | 验证身份、空间隔离、历史、资产读取和文件访问 | 检查通过才允许写；此阶段失败可按下表回切 |
| 开放写入 | 标记第一个业务写入时点；受控恢复入口、Worker 和回调 | 运行可追溯的业务冒烟验证、检查错误率和对账 |
| 观察退出 | 旧库保持只读，备份隔离保留，监控目标库 | 观察期建议至少覆盖一次结算周期和一次备份恢复检查；具体时长在执行单确认 |

停写方案追求切换范围内所有已确认写入零遗漏。它不代表突发宕机也天然零数据损失，灾备目标需单独规定。

1. **<span style="font-size:18px;color:#fff">迁移的流程按顺序做：先在测试环境演习一遍→确认好版本→停止写入→把正在进行的任务做完或登记好→最后备份盘点→逐项核对→切换到新环境→只读模式验收→重新开放写入→旧环境保留观察一段时间。每一步都写了”什么情况算过关、出问题怎么办”。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">停写迁移十阶段：预演→冻结变更→控制所有写入（含用户接口/Worker/计划任务/Agent/同步/管理员/回调）→排空任务→最终备份并恢复到目标→数据核验（行数/主外键/抽样/账务总额/序列/文件引用/身份映射）→配置切换（不双写）→只读验收→开放写入→观察退出（旧库只读、备份隔离保留）。</span>



2. **<span style="font-size:18px;color:#fff">这套”停写迁移”是保证这次迁移过程中已经确认的数据一条不丢。但它不等于突发宕机也不丢数据——那是另一回事（灾备），得单独规定。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">停写方案追求切换范围内已确认写入零遗漏；不代表突发宕机天然零数据损失，灾备目标需单独规定。</span>

## 3. 回滚决策

| 目标库情况 | 允许的操作 | 必须确认 |
|---|---|---|
| 未接受任何业务写入 | 停止所有目标连接，重新连接旧库再开放服务 | 旧库完整且为权威；回调和任务仍在可恢复状态 |
| 已接受业务写入 | 优先在新库修复；需回切时先全量停写，保全增量并执行已演练回灌 | 新订单、额度流水、作品、审批等全部核对，旧库在回灌完成前不得开放 |
| 增量无法可靠合并 | 继续维护状态，保全两边数据，人工核对并修复 | 不允许丢弃新库写入以“快速恢复” |

禁止未经演练的双向复制或手工挑几张表回灌。使用增量逻辑复制时要额外处理结构变更、序列、复制延迟、故障恢复和发布权限；不能以“复制已连上”代替完整核对。[PostgreSQL 逻辑复制限制](https://www.postgresql.org/docs/16/logical-replication-restrictions.html)

1. **<span style="font-size:18px;color:#fff">迁移过去发现不对劲怎么办？看情况：如果新库还没开始接收新数据，那简单，全部切回旧库就行；如果新库已经收了新数据，就不能直接切回——得先停止写入，把新库这几天新增的数据一笔笔抄回旧库，核对无误再切；要是两边数据合不拢，就维持”只接收不写入”的状态人工核对，绝不能为了快点恢复把新库的新数据扔了。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">回滚：目标库未收业务写入可停目标连接、回切旧库；已收写入优先在新库修复，需回切时全量停写、保全增量、执行已演练回灌并核对新订单/额度流水/作品/审批；增量无法可靠合并则维持维护状态人工核对，禁止丢弃新库写入换取快速恢复。</span>



2. **<span style="font-size:18px;color:#fff">不许没演习过就搞两边同时复制、或者手工挑几张表往回倒。光说“复制连上了”不算数，得真对数。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">禁止未经演练的双向复制或手工挑表回灌；增量逻辑复制需额外处理结构变更/序列/复制延迟/故障恢复/发布权限；不以“复制已连上”代替完整核对。</span>

## 4. 备份与结构升级

操作方案见 [备份回滚恢复执行规范](09-备份回滚恢复.md)，包括基础备份与 WAL 的区别、误删旁路恢复、外部支付对账、日志链验证与演练。以下目标是候选值，不代表当前已启用。

自动异机备份、失败告警和一次完整恢复演练是 P0 上线门槛。备份不与原数据库只放在同一块盘上；加密、访问控制和保留策略必须覆盖数据库、文件与解密依赖。

建议初期评估基线：每日全备、保留 14 天、恢复时间不超过 4 小时。仅每日备份意味着最坏可能损失接近一天数据，不能声称零丢失。收费业务建议启用持续日志归档，将可接受损失时间目标收紧至 5 分钟以内；这些是待成本与演练确认的目标，不是当前保障。达不到就调整方案或明确缩小上线范围。

可接受损失时间称为 RPO，恢复所需时间称为 RTO。实际值必须通过中断与恢复演练记录。基本备份不能等到“10 万用户”再做。

Migration 应有执行历史、校验和和互斥锁。已应用脚本不得修改，失败不吞异常。结构升级优先增加兼容字段、后台分批回填、校验后切换读取，最后再删除旧字段；回滚不等于直接运行破坏性删表。评估锁等待、执行时间、磁盘余量与长事务，避免发布把线上请求堵死。

1. **<span style="font-size:18px;color:#fff">每天自动备份到另一台机器、备份失败要报警、完整恢复演习一次——这三条是上线硬门槛。备份盘不能和系统后台放在同一块硬盘上，不然硬盘一坏俩都完。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">自动异机备份、失败告警、一次完整恢复演练是 P0 上线门槛；备份不与原 DB 同盘；加密/访问控制/保留策略覆盖 DB、文件与解密依赖。</span>



2. **<span style="font-size:18px;color:#fff">初期目标：每天全量备份一次、留14天、数据能在4小时内恢复。但要知道：只靠每天备份，最坏情况可能丢接近一天的数据，不能吹“零丢失”。真收钱的业务建议开持续日志备份，把“最多丢多久”压到5分钟以内。这些都是要花钱和演习才能定的目标，不是现在就做到了。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">基线候选：每日全备、保留14天、RTO≤4小时；仅每日备份最坏损失接近一天，不称零丢失；收费业务建议持续日志归档将 RPO 收紧至5分钟以内；均为待成本与演练确认的目标。</span>



3. **<span style="font-size:18px;color:#fff">最多能接受丢多久数据叫 RPO，恢复要花多久叫 RTO。这两个数必须靠真的模拟一次宕机、真恢复一遍才能写下来，不能拍脑袋。备份这事不能等“10万用户了”才做。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">RPO=可接受损失时间，RTO=恢复所需时间，实际值须经中断与恢复演练记录；基本备份不能等到10万用户再做。</span>



4. **<span style="font-size:18px;color:#fff">改表结构按顺序做：先加兼容的新字段→后台慢慢把老数据迁过来→确认新字段好用了→再删老字段。不能上来就把老字段删了。改的时候得盯着别把正在处理的请求堵死。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">Migration 需执行历史、校验和、互斥锁；已应用脚本不改、失败不吞异常；结构升级优先加兼容字段→后台分批回填→校验后切读→最后删旧字段；回滚不等于直接跑破坏性删表；评估锁等待/执行时间/磁盘余量/长事务，避免堵死线上请求。</span>

## 5. 性能：以实测为准，不按注册人数猜配置

10 万注册用户不是 10 万同时在线。先用小配置跑当前负载，再根据监控扩容。以下是规划用的候选验收档位，尚未实测，不能当作当前服务器承载承诺。

| 档位 | 测试数据 | 并发与吞吐 | 目的 |
|---|---|---|---|
| 初期 | 1 万用户、10 万任务、10 万资产；混入大团队和长历史 | 50 个活跃会话，普通接口 20 请求/秒 | 找明显慢查询、泄漏和单机瓶颈 |
| 增长 | 10 万用户、100 万任务、100 万资产，包含单个大租户 | 200 个活跃会话，普通接口 100 请求/秒 | 验证索引与隔离在数据增长后仍可用 |
| 外部生成 | 模拟图片/视频长耗时、重试、失败与回调；默认不消耗真实付费 API | 初期总并发候选值 5，空间并发候选值 2；以供应商限额和资源验证为准 | 检查背压和恢复，不把 AI 推理耗时算成数据库慢 |

负载脚本需声明读写比例、热点租户占比、请求体大小、页大小、缓存冷热、部署配置、网络位置；预热 10 分钟，持续负载至少 30 分钟，再测试突发流量和故障恢复。测试数据用合成内容，不复制真实用户机密。

| 指标 | 候选通过门槛 | 不通过时 |
|---|---|---|
| 普通列表/详情 API | 同地域测试下 p95 ≤ 500ms、p99 ≤ 1500ms；不含文件下载和外部 AI | 检查慢 SQL、连接池、权限查询、响应体和网络 |
| 创建任务接口 | 持久化并返回 task_id 的 p95 ≤ 1000ms，不等待生成完成 | 检查事务长度、锁等待和预占热点 |
| 意外服务错误 | 稳定负载下 5xx < 0.1%；业务拒绝和主动限流独立统计 | 排查资源耗尽与超时，不能删除样本美化结果 |
| 数据正确性 | 跨租户泄露、重复结算、负余额、已确认任务丢失均为 0 | 阻止上线，修复后重跑相关验收 |
| 稳定性 | 无持续增长的连接/内存、无 OOM；队列积压可在恢复后消退 | 限流、限制并发、优化，再评估扩容 |

p95 表示 95% 的请求不超过该时间。到不了目标不代表只能买大服务器，先查调用次数、索引、返回内容和锁；完成复测后再记录可承载范围。

1. **<span style="font-size:18px;color:#fff">10万注册用户不等于10万人同时在线。先按小配置跑着，看监控哪儿不行再扩容。下面这些是”将来要测到的档位”，不是现在服务器就扛得住。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">10万注册≠10万并发；先用小配置跑当前负载再按监控扩容；下表为候选验收档位，未实测，不代表当前服务器承载承诺。</span>



2. **<span style="font-size:18px;color:#fff">压测要讲清楚：多少读多少写、哪个大客户占多少流量、页面多大、缓存是热是冷、机器在哪。先预热10分钟、正经跑30分钟，再突然加流量、故意搞故障看能不能恢复。测试用假数据，不能拿真用户的密码来压。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">负载脚本声明读写比例/热点租户占比/请求体大小/页大小/缓存冷热/部署配置/网络位置；预热10分钟、持续负载≥30分钟，再测突发流量与故障恢复；测试数据用合成内容，不复制真实用户机密。</span>



3. **<span style="font-size:18px;color:#fff">p95 的意思是：95% 的请求都快于这个时间。到不了目标不代表只能砸钱买更大的机器——先查查是不是某个查询太慢、快速查找标记没加、一次返回了太多东西。查完再测，测完再写”我们能扛多少”。跨空间串数据、重复扣钱、负余额、已完成的任务丢了，这几样必须是零，出一个就别想上线。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">p95=95%请求不超过该时间；不达标先查慢SQL/连接池/权限查询/响应体/锁与预占热点，复测后再记录承载范围；数据正确性红线（跨租户泄露/重复结算/负余额/已确认任务丢失）必须为0，否则阻止上线。</span>

## 6. 具体查询与运行约束

列表默认 20 条、最大 100 条；用稳定游标，例如 (created_at,id)，对应 (workspace_id,created_at,id) 索引。一次批量查询关联数据，避免每条记录再访问数据库。列表不返回原图、全部节点、完整对话和原始响应。可编辑时间排序须定义翻页变化行为，不能承诺并发更新时天然无重漏。

连接池预算按全部 API 实例、Worker 和运维预留计算，不能每加一个进程都开满数据库连接。禁止外部 AI 调用占用数据库事务；设置语句、锁和请求超时以及有界重试。请求进入队列前检查空间和平台限流；队列满时明确拒绝或排队，不能无限占内存。

常用查询以实际 SQL 执行计划和冷/热缓存数据验证。按查询选择索引，不给每个字段都加索引。统计和文件处理离开前台关键路径；权限撤销不能等待很久的统计或缓存刷新。只有瓶颈证据充分时才引入分区、读副本或独立服务。

1. **<span style="font-size:18px;color:#fff">列表一屏默认20条、最多100条，用稳定的翻页标记。一次把一页要的数据都查回来，别每条都单独跑一趟后台。列表里不要塞原图、全部节点、完整对话这些大件。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">列表默认20条、最大100条，用稳定游标 (created_at,id)，对应 (workspace_id,created_at,id) 索引；批量查关联数据避免每条再访问 DB；列表不返原图/全部节点/完整对话/原始响应；可编辑排序须定义翻页变化行为。</span>



2. **<span style="font-size:18px;color:#fff">后台连接数要提前算好，不能每开一个程序就占满连接。等AI回复的那段时间不许占着后台连接不撒手。队列满了就明说“请排队”或“现在忙”，不能无限往内存里塞请求。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">连接池预算按全部 API 实例/Worker/运维预留计算；禁止外部 AI 调用占用 DB 事务；设语句/锁/请求超时与有界重试；入队前检查空间与平台限流，队列满明确拒绝或排队，不无限占内存。</span>



3. **<span style="font-size:18px;color:#fff">加不加快速查找标记、加在哪，得看实际跑出来的查询计划，不能每个字段都加快速查找标记（标记多了反而拖慢写）。统计和文件处理别挡在前台请求的路上。只有真测出瓶颈了，才搞分区、读副本、拆服务。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">常用查询以实际执行计划和冷/热缓存验证，按查询选索引、不给每字段加索引；统计与文件处理离开前台关键路径；权限撤销不等待长统计或缓存刷新；瓶颈证据充分才引入分区/读副本/独立服务。</span>
