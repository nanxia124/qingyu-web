# 支付接入需求规范

版本：0.5。编写及修订日期：2026-09-25。状态：已补充自动续费完整需求及专项验收；支付通知重试、重复实收留痕和逐笔退款限制已完成本地实现及专项测试；订单幂等与重复提交通过本地模拟测试；真实支付渠道、真实退款、自动续费代码和业务验收尚未完成，未开启真实扣款。

## 1. 这份文档管什么

**<span style="font-size:18px;color:#fff">规定用户怎样付款、什么时候开通会员、付重了怎么办、怎样退款，以及工作人员怎样核对收到的钱。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">范围：渠道接入、订单、支付尝试、订阅、权益、退款、对账、安全、恢复与验收。本文不记录经营主体或个人资料。仅编写规范，不代表执行代码修改、商户申请或生产部署。</span>


**<span style="font-size:18px;color:#fff">本次主要解决中国大陆用户付款；海外付款保留扩展位置。先把一种付款方式完整做好，再增加其他方式。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">需求范围同时包含单次购买与自动续费完整闭环；实施先完成单渠道基础，再验证续费授权与账期扣款，按渠道能力分别开放。第二渠道、跨境支付和升级补差价独立排期，不承诺上线日期。初期不建设现金充值钱包，包括不可提现钱包；平台使用额度与现金分别管理。</span>

## 2. 总体分类

| 第一层 | 第二层 | 用户或工作人员看到什么 |
|---|---|---|
| 付款前 | 套餐、价格、优惠、付款方式 | 买什么、多少钱、有效多久、给谁使用 |
| 付款中 | 创建订单、打开收银台、确认结果 | 待付款、确认中、付款成功、失败原因 |
| 付款后 | 会员、额度、购买记录 | 已开通的权益和对应订单 |
| 售后 | 退款、取消续费、争议 | 退款进度、停止续费时间、处理结果 |
| 运营 | 收款核对、退款核对、到账核对 | 哪笔金额对不上、谁处理、怎么处理 |
| 安全与维护 | 权限、凭证、告警、备份恢复 | 谁能操作、异常是否已处理、恢复后金额是否一致 |

## 4. 支付渠道与开通前提

**<span style="font-size:18px;color:#fff">网页能显示某个付款按钮，不代表已经能收款。只有申请通过、真实付款和退款都验证成功，才向用户开放。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">渠道能力由服务端配置和平台审核决定。技术支持、商户准入、产品权限、结算能力分别确认；不能把任意付款方式视为已开通。</span>

| 渠道 | 拟用场景 | 必须核实 | 当前决策 |
|---|---|---|---|
| 微信支付 | 电脑扫码；微信内付款；手机浏览器付款 | Native、JSAPI、H5 分别核实产品权限、应用绑定、域名及备案要求 | 国内候选；不能用一个产品权限代替全部场景 |
| 支付宝 | 电脑网站或手机网站付款 | 对应支付产品、业务类目、网站与域名要求、退款权限 | 国内候选；准入条件待专项核实 |
| Antom | 统一收银台，支持已签约的钱包或银行卡 | 付款人地区、签约产品、币种、结算、退款、续费权限 | 候选；截图和品牌标志不能证明本项目可用 |
| PayPal | 海外付款 | 商业收款权限、目标地区、结算、订阅能力 | 跨境候选，不能默认替代国内收款 |
| Stripe | 海外银行卡、已开通的钱包及订阅 | 支持地区、账户资格、产品与结算权限 | 仅作为候选；参考代码存在不代表可开通 |
| Creem / Waffo | 托管收银台及订阅 | 产品准入、收款与结算地区、支持方式、退款及争议规则 | 参考代码可研究；资格未确认 |

**<span style="font-size:18px;color:#fff">服务器放在新加坡，只说明程序运行在哪里；能开通哪些付款方式，要另看支付平台的要求。不要为了显示按钮而跳过审核。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">部署地域与支付准入分开评估。检查公网 HTTPS 可达性、TLS、回调防火墙、跨境延迟、域名与产品要求；不承诺境外部署可以免除支付产品要求。</span>

## 5. 用户付款的完整流程

**<span style="font-size:18px;color:#fff">用户先看清购买内容，再付款；钱是否到账由后台向付款平台确认，不能靠用户点“我已付款”就开会员。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">支付流程以渠道验签通知或服务端主动查单为依据。浏览器回跳、截图、前端参数不能作为到账凭证。</span>

| 顺序 | 用户看到什么 | 后台必须做什么 | 完成条件 |
|---|---|---|---|
| 1. 确认购买 | 套餐、总价、币种、有效期、购买空间 | 校验登录与购买权限，从可信价格版本计算金额 | 金额和权益明确 |
| 2. 创建订单 | 唯一订单号 | 固定购买空间、付款人、金额、价格及权益快照 | 重试返回同一订单 |
| 3. 打开付款页 | 二维码或平台收银台 | 创建或复用该订单付款尝试，保存渠道编号和过期时间 | 获得可信付款链接 |
| 4. 等待付款 | 待付款或确认中 | 接收通知、主动查单；限频查询 | 不重复创建交易 |
| 5. 确认到账 | 已付款，权益开通中 | 核对渠道账户、交易号、订单号、金额、币种与状态；可靠保存实收和待发放任务 | 付款可信且可追查，通知收到不等于已开通 |
| 6. 发放权益 | 会员和额度更新 | 在一次完整保存中提交订阅、额度流水、发放完成标记和后续通知 | 发放一次且归属正确；失败保留已付款事实并补发 |
| 7. 结果不明 | “正在确认，请勿重复付款” | 继续查询原交易，重试失败进入异常队列 | 查清前不要求再次支付 |

**<span style="font-size:18px;color:#fff">先记住付款平台的消息，再记清收到的钱，最后开通权益。开通失败只能补开，不能把已经收到的钱说成没收到。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">统一处理边界：①验签后 Inbox 与待处理标记同事务持久化，按渠道协议确认接收；②验证收款事实后 payments、订单支付状态和 fulfillment 待办同事务提交；无法归属的可信实收进入独立待核账记录，不猜测关联；③订阅、额度、发放唯一标记与 Outbox 同事务提交。任何阶段失败均由持久任务恢复，远程调用不放在持锁事务内。重复事件复用已有处理任务，不新增权益。付款与发放状态分别展示。</span>

## 6. 防止重复付款与错发权益

**<span style="font-size:18px;color:#fff">第一次已付款，第二次再点应显示原订单结果。两个窗口同时付款时，也不能给用户重复开两份会员。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">采用幂等控制，即重复提交只产生一次业务效果；不能仅靠按钮禁用。外部渠道无法跨系统保证绝对只扣一次，必须同时设计重复实收检测与退款补偿。</span>

| 场景 | 必须处理 | 不允许 |
|---|---|---|
| 快速连点 | 按钮进入处理中；服务端复用购买意图和订单 | 每次点击创建新付款 |
| 刷新、关闭后重开 | 订单中心可恢复原订单并查询 | 丢掉原单要求重新购买 |
| 两标签页使用不同请求编号 | 服务端识别同空间、同商品、同购买周期的未完成意图；明确区分新购买 | 仅凭客户端随机编号声称彻底防重 |
| 第一次付款成功，第二个旧弹窗仍开着 | 再次发起前查单；页面获知成功后关闭旧付款入口 | 把旧二维码当成仍可支付 |
| 切换支付渠道 | 先查旧交易并确认关闭；不支持关单时限制切换或进入人工处理 | 同时放出多个不受控的可付款交易 |
| 下单请求超时 | 使用原渠道订单号查询；支持渠道幂等键时原键重试 | 直接换新编号再次扣款 |
| 支付通知重复或乱序 | 按事件号和交易号去重；成功状态不可退回待付款 | 每次通知重复赠送权益 |
| 两渠道确实各收到一笔钱 | 保留两笔真实流水；权益只给一次；多收款进入退款与告警流程 | 隐藏第二笔实收或只忽略通知 |

### 6.1 怎样区分重复点击和确实想再买

**<span style="font-size:18px;color:#fff">刷新页面和再次点原来的付款按钮，继续处理原订单。用户明确选择“再次购买”时，要重新展示购买内容并确认，不能偷偷合并或偷偷多收一笔。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">引入服务端 purchase_intent_id；购买快照含 workspace、商品版本、数量、币种、优惠结果、目标权益周期及操作类型。幂等键在用户/空间/操作范围校验 request_hash；相同键不同内容拒绝。并发建单以数据库唯一约束/锁裁决，不仅依赖浏览器。</span>

| 操作 | 规则 |
|---|---|
| 同一次结账的双击、刷新、恢复页面 | 使用同一购买意图及订单；按钮禁用只辅助显示 |
| 两窗口各产生了新编号 | 查找该空间相同购买快照的未完成意图；有查看权限者恢复原单，无权限者只提示已有采购待处理，不泄露详情 |
| 订单已经付款 | 原页面仅显示结果；明确选择再次购买且确认新周期后，才创建新意图 |
| 更换套餐、数量、优惠或空间 | 重新确认报价；原单不直接修改；旧付款尚未查清时不得盲目创建冲突的可付款交易 |
| 原订单过期或关闭 | 先核实渠道已关闭或付款结果，再允许新单；旧单晚到实收仍须登记处理 |

购买意图的有效期、同商品并发采购范围在上线前配置并验收，不用无限期的“同空间同商品只能有一单”限制正常续买。

## 7. 数据怎么分类、怎么连接用户

**<span style="font-size:18px;color:#fff">付款人和使用权益的人要分清。个人购买给个人空间，团队购买给选定团队，付款后不能因为切换了页面就发到另一个团队。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">订单固定 purchaser_user_id、workspace_id 与权限快照；后续关联按订单确定，不能信任回调或前端任意传入的用户编号。团队采购权限单独定义，成员离职不转移团队权益。</span>

下表为目标逻辑字段，不是对当前库字段齐全程度的声明。实际增量设计需与 [字段字典](12-数据库字段字典.md) 核对，避免另建重复账本。

| 分类与拟关联对象 | 关键字段（技术补充） | 大白话与约束 |
|---|---|---|
| 套餐版本 `plan_versions` | `id, plan_id, currency, price_minor, entitlement_snapshot` | 记录买的时候多少钱、送什么，改新价格不能改旧单 |
| 订单 `orders` | `id, order_no, workspace_id, purchaser_user_id, plan_version_id, amount_minor, currency, status, idempotency_key, request_hash, expires_at` | 一次购买的总记录；同编号不同购买内容拒绝 |
| 付款尝试（拟补充） | `id, order_id, provider, provider_account_id, environment, merchant_order_no, provider_payment_id, status, expires_at` | 记录每次与收款平台联系；结果未知仍要能追查 |

| 权益流水 `quota_ledger` | `workspace_id, account_id, order_id, operation_key, entry_type, amount` | 记录发放、使用与回收；历史流水不直接改写 |
| 退款 `refunds` | `order_id, payment_id, workspace_id, amount_minor, currency, status, idempotency_key, provider_refund_id` | 每笔退款明确退哪一次收款 |
| 争议与对账差异（拟补充） | `payment_id, provider_case_id, reason, amount_minor, currency, status, assigned_to` | 记录拒付、少收、多收及处理人员 |
| 操作与通知 | `actor_id, action, resource_id, reason, request_id, occurred_at` | 谁改了什么、为何处理、用户有没有收到结果 |
| 购买意图（拟补充） | `id, workspace_id, purchaser_user_id, request_hash, order_id, status, expires_at` | 保存本次确认的购买内容，用于恢复和防重复 |
| 权益发放计划（拟补充） | `order_id, subscription_id, installment_no, period_start, period_end, due_at, policy_version, status` | 年付按月赠送时，每一期可追查且只发一次 |
| 权益执行记录（拟补充） | `operation_key, order_id, payment_id, status, attempts, next_retry_at, completed_at` | 收钱后开通失败也能继续处理 |
| 退款分类 `refunds` | `refund_kind, payment_id` | 已实现正常退款与重复收款退款分类，并绑定对应实收；真实渠道退款及退款后的权益调整仍未接通 |
| 发票关联（已有基础，待完善） | `invoice_requests, invoice_request_orders, currency, refunded_amount, correction_reference` | 关联实收、退款和开票调整，避免同一金额重复开票 |

**<span style="font-size:18px;color:#fff">人民币、美元和使用次数分别记，不能混加。银行卡完整号码和安全码不放进网站保存。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">金额采用最小货币单位整数与 ISO 币种，按币种精度显示，不统一假设两位小数。外部编号唯一范围含 provider、account、environment；事务、外键与唯一约束共同防错。使用托管收银台或官方安全组件，不保存 PAN/CVV。</span>

## 8. 付款、退款和会员分别记录状态

**<span style="font-size:18px;color:#fff">“付了钱”“退了钱”“会员能不能用”是三件事，必须分别看。请求卡住，只能说还没查清，不能直接说付款失败。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">目标状态机与现有 enum/check 约束需后续映射；本文不直接改变现有状态值。金额事实与权益有效性分开保存。</span>

| 对象 | 目标状态 | 关键规则 |
|---|---|---|
| 订单 | 待付款、已付款、关闭、部分退款、全额退款 | 关闭后收到真实成功通知仍需核实并补发或退款，不能丢弃 |
| 付款尝试 | 创建中、待付款、确认中、成功、失败、关闭 | 超时进入确认中；成功不能被旧失败消息覆盖 |
| 退款 | 待审批、处理中、成功、失败、结果未知、驳回、取消 | 请求已受理不代表资金已退回；取消仅限尚未送渠道且确认无外部退款的申请 |
| 订阅 | 生效、到期、待续费、停止续费、暂停 | 取消自动续费不等于立即失去已购买时间 |
| 权益 | 待发放、已发放、待调整、已调整 | 已收到钱但发放失败，补发原订单，不能让用户再付 |

## 9. 订阅、团队和预扣款

**<span style="font-size:18px;color:#fff">买一个月会员和授权每月自动扣钱不同。两种购买方式都要设计完整；自动续费只有在用户明确同意、付款渠道支持并完成测试后才能使用。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">默认 prepaid 单次购买。Recurring billing 需渠道权限、授权记录与独立续费账期幂等键；展示金额、周期、下一扣款时间和取消入口。按约定日历周期或明确天数计算，不混用“自然月”和固定 30 天。</span>

| 规则 | 用户看到的结果 | 技术约束 |
|---|---|---|
| 续买同档套餐 | 明确从原到期日延长还是立即生效 | 上线前固定规则并保存订单快照，不能以当前套餐配置覆盖旧单 |
| 升级、降级 | 清楚展示何时生效、补多少钱、剩余额度如何处理 | 首期不开放未定义的补差价；后续新增独立规则 |
| 团队购买 | 确认页醒目标明团队名称 | 后台校验采购权限；团队权益不跟随付款人离职转移 |
| 自动续费失败 | 提醒用户处理，显示会员截止时间 | 重试次数和宽限期预先定义，不能无限尝试扣款 |
| 生图前预留额度 | 任务成功扣额度，确认失败释放额度 | 复用现有额度预占体系，不代表冻结银行卡资金 |
| 银行卡预授权 | 如将来需要，单独说明冻结金额和释放时间 | 首期不启用；需设计授权、扣款、撤销、到期释放全链路 |

### 9.1 年付、按月赠送和剩余会员时间

**<span style="font-size:18px;color:#fff">买一年会员不等于自动续费，也不代表一次送完一年的额度。付款前必须说清楚何时送、每次送多少、没用完能不能留到下个月。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">付款周期与 entitlement schedule 分离，订单固化发放政策。一次发全年与逐月发放为互斥配置；逐月按 (order_id, entitlement_type, installment_no) 唯一，不能重放年付成功事件来模拟每月到账。</span>

| 事项 | 必须确定与实现 |
|---|---|
| 发放节奏 | 明确一次发全年或分期发；分期需要保存每期时间、数量和完成状态 |
| 月末与闰年 | 明确使用时区、自然月或固定天数、月底日期规则；保存绝对时间及政策版本 |
| 重启与漏发 | 扫描已到期未发记录；补发原期，不创建新的期号；已过有效期的额度按购买时政策处理 |
| 已有会员再次购买 | 续买策略必须明确；推荐保留已购时间，从原到期日衔接，但需产品确认后启用 |
| 同时续买 | 锁定订阅记录后按已接受的订单顺序计算，保留逐订单贡献时段，不让后单覆盖前单 |
| 退款与发放同时发生 | 串行裁决该订单发放/停发；退款按原单发放批次调整，不回收后来另买的额度 |
| 取消自动续费 | 停止未来扣款；已经付清年度订单的剩余赠送不因取消续费而停止，除非另有退款或终止处理 |

上述商业政策尚待确认；未选择并实现发放方案前，不上架承诺对应权益的年付套餐。

### 9.2 开通授权与用户页面

**<span style="font-size:18px;color:#fff">用户必须主动选择自动续费，才能按期扣钱。页面要清楚显示每次多少钱、多久扣一次、下次何时扣，以及去哪里取消。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">自动续费 opt-in 不预勾选、不与基础服务同意捆绑。记录授权文本版本、确认时间、授权人、目标 workspace、支付渠道/账户/环境与 provider_mandate_id。渠道验签通知或服务端查询确认协议生效后才能设 active；授权成功不代表首次支付成功。</span>

| 环节 | 必须展示或检查 | 处理结果 |
|---|---|---|
| 选择自动续费 | 套餐、币种、本期实付、后续价格、频率、首次与下次扣款时间、取消入口、退款政策 | 单次购买仍可单独选择；不把点击购买当成同意续费 |
| 优惠或试用 | 首期优惠、优惠结束时间、之后金额；免费试用结束是否收费 | 未实现明确试用规则前，不开放到期自动转付费 |
| 完成渠道授权 | 校验渠道协议、授权范围和目标空间 | 返回网站不算授权成功；处理中展示真实状态 |
| 续费管理页 | 开关状态、付款方式脱敏信息、下期日期与金额、已付有效期、每期记录 | 用户可查看失败原因、更新付款方式或取消 |
| 团队授权 | 核实采购权限和付款授权，不把团队管理权限当银行卡扣款授权 | 保存授权人；成员离职不改权益归属，须核验或暂停未来扣款授权 |
| 重新开启 | 重新确认价格、日期及有效授权，必要时重新签约 | 不补扣暂停期间账单，不自动恢复已撤销协议 |

### 9.3 每期怎样扣款和发权益

**<span style="font-size:18px;color:#fff">每期续费都单独留一张账单。付款平台已经在扣这期的钱时，我们不能再扣一遍；钱收到后才增加这期对应的会员时间和额度。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">每份订阅固定 collection_owner：provider_managed（渠道调度）或 merchant_managed（本系统调度），严禁双重调度及双重失败重试。账期唯一键基于 subscription_id、固定账期边界/sequence、operation；同账期重试关联原订单，不因重启、切渠道或更新付款方式生成另一张应收账单。</span>

| 顺序 | 规则 |
|---|---|
| 创建账期 | 固定账期起止、计费时区、价格版本、币种、优惠、付款授权和权益计划；已确定账期不能因执行晚了而滚动改时间 |
| 提前通知 | 保存提醒内容、发送时间及投递结果；站内展示加已验证联系方式提醒；失败重试与告警 |
| 扣款前复核 | 检查授权仍有效、未取消、未付、未有结果未知尝试、价格符合已确认范围及提醒要求 |
| 发起扣款 | 同账期只允许一个有效执行者；使用稳定渠道请求标识并记录尝试。无法判断渠道是否受理时转查单，禁止盲重发 |
| 确认到账 | 复用第 5 节分阶段处理；核对渠道账期编号与原订单，不仅凭付款邮箱匹配 |
| 发权益 | 按该账期快照延长会员并生成对应额度发放计划；重复通知只返回原结果 |
| 结束账期 | 已付、明确失败或关闭分别记录；长期未决告警。不能跳过未决期静默多扣未来期 |

渠道自行调度时，系统仍需在可控时间内生成/同步账期与提醒，核对渠道计划。若渠道无法落实约定的提醒、取消或停扣条件，不开放该自动续费产品，不以本地开关代替渠道停扣。

### 9.4 扣款失败、补缴与建议参数

**<span style="font-size:18px;color:#fff">余额不足可以按约定再试；还没查清有没有扣成功，就只能查原记录。用户取消了，不能继续追着扣。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">区分可重试软失败、需用户验证的 action_required、授权失效/禁止重试的硬失败、结果未知。重试前每次重新校验授权与取消状态；查询次数不计为扣款次数。以下是产品建议值，不是平台通用规则或法律结论；须核对渠道要求并经确认后生效。</span>

| 参数或情形 | 建议或必须行为 | 状态 |
|---|---|---|
| 扣款前提醒 | 建议提前 7 天及 1 天各提醒；短周期产品另设政策，不套用此值 | 建议值，待确认；渠道/适用要求更严格时从严配置 |
| 首次明确软失败后的重试 | 建议最多额外 2 次，分别在失败后 24、72 小时；按原账期处理 | 建议值，待确认；不得叠加渠道自带重试 |
| 结果未知 | 建议 1、5、15 分钟查单，之后每小时核对；持续 24 小时告警升级人工 | 建议值，待确认；不能到 24 小时就假定失败并重新扣款 |
| 需用户验证或授权失效 | 提示用户去官方页面处理；停止无意义的自动重试 | 必须遵守 |
| 宽限期 | 建议 3 天仅保留查看/导出历史内容，不新增付费生成额度；原已购权益按自身期限处理 | 建议值，待确认；宽限不等于免费续上会员 |
| 提醒未能送达 | 留存失败并重试；无法完成产品约定的提醒条件时暂停该次自动扣款，通知人工处理 | 必须落实到实际扣款执行方 |
| 用户主动补缴 | 查原账期与所有未决尝试；停止该期自动重试并确认渠道状态，再复用原账期付款 | 同期不能人工与自动两路同时收款 |
| 迟到付款成功 | 按原周期/补缴政策开通或退款，记录已过期时间如何处理 | 政策待确认，不默认从到账时间任意延长 |

### 9.5 取消续费与正在扣款的冲突

**<span style="font-size:18px;color:#fff">取消后，已经买到的会员继续用。若取消时平台已经开始扣这一笔，要告诉用户正在核对，不能显示“已取消”却继续悄悄扣钱。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">分开保存 cancel_requested_at、local_collection_blocked_at、provider_cancel_status、cancel_effective_at、paid_through_at。取消请求与本地扣款派发使用订阅锁/版本裁决；网络提交存在不确定窗口，不以进程锁宣称可原子撤销外部扣款。</span>

| 时机 | 必须动作 | 用户看到 |
|---|---|---|
| 尚未发出扣款 | 立即禁止本地新派发及重试，撤销排队任务；请求渠道停扣并核实 | 取消处理中，展示现有会员截止时间 |
| 已发送或渠道自行发起 | 查询在途交易及渠道订阅；能撤销则撤销，不能撤销则记录结果 | 明确提示本次正在处理、可能已有扣款 |
| 渠道确认停止后续扣款 | 保存确认依据和生效时间，禁止后续调度 | 自动续费已取消；不影响已付有效期 |
| 渠道取消超时 | 保持本地停扣，持续查协议状态、告警；不提前宣称彻底取消 | 取消处理中，可追踪处理进度 |
| 确认取消后仍有新扣款 | 登记实收，区分取消前已受理与取消后违规发起；后者进入退款补偿与告警 | 展示异常收款及退款处理，不静默开新周期 |
| 本期已付后取消 | 只停止未来续费；本期退款走独立申请规则 | 已付会员及年度分期赠送按约定继续 |
| 用户在付款平台解约 | 验签接收或查单同步撤销状态，终止本地调度 | 各端一致显示取消，不自动重新签约 |

退订后不默认追扣取消前明确失败的账期；确需补缴由用户主动确认。允许用户在账号内完成取消，不把联系人工作为唯一正常取消入口。

### 9.6 价格、付款方式、退款与权限变化

**<span style="font-size:18px;color:#fff">自动续费不是同意以后任意涨价。价格、周期或付款方式变了，需要按新内容确认；退款也不能误改其他月份的会员。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">重大授权条件变化产生新的授权/价格政策版本，不覆盖历史快照。退款关联 billing_cycle_id 与 payment_id，权益调整定位该期及其发放批次。升级补差规则未定义前不开放自动中途变更。</span>

| 变化 | 要求 |
|---|---|
| 涨价、币种、周期变化 | 提前展示新条款并明确确认；未确认时不得按新条件扣款，按已公布安排保留旧价或停续 |
| 首期优惠结束 | 首次授权清楚列出后续标准价，扣款提醒再展示；超出原授权条件须重新确认 |
| 升级、降级、席位变化 | 显示生效账期、金额与权益；不以成员数量实时变化偷偷增加已确认扣款 |
| 更换付款方式 | 经渠道验证后绑定；旧交易未决先查清，不能新旧方式各扣一次 |
| 更换支付渠道 | 核实旧渠道停续，确认新授权与首次账期，衔接已付期限；旧记录仍可查和退 |
| 本期退款或拒付 | 单独记录未来续费是否暂停/取消；建议先暂停未来扣款，重新开启需明确确认；最终政策待确认 |
| 退款不影响其他期 | 根据本期时段与批次调整；保留其他已付周期，不直接把整个订阅删掉 |
| 账号注销或团队解散 | 立即提出停续并阻止新派发，确认渠道结果；未决交易进入售后清单 |
| 团队授权人离职或权限被撤销 | 立即暂停新的本地派发并请求渠道停续；既有权益留在团队，新负责人须重新取得付款授权 |

### 9.7 数据、状态与恢复

**<span style="font-size:18px;color:#fff">要能查清楚：谁同意续费、哪一期该付多少钱、试了几次、有没有取消、会员有没有到账。恢复旧记录后，也不能把已取消的续费重新打开。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">下表为逻辑增量方案，复用现有 subscriptions/orders/payments/事件/权益体系；实施前核对字段字典，不另建平行账本。时间存 UTC 并保留计费时区及账期锚点，渠道托管账期以核验后的渠道周期映射到本地。</span>

| 对象 | 目标字段 | 作用与约束 |
|---|---|---|
| 续费授权 | `id, subscription_id, workspace_id, authorized_by, provider, account_id, environment, provider_mandate_id, terms_version, authorized_at, revoked_at, status` | 记录待授权、有效、撤销中、已撤销、过期、失败；平台凭证只保存受保护引用 |
| 订阅续费设置 | `collection_owner, billing_timezone, anchor, policy_version, cancel_requested_at, provider_cancel_status, cancel_effective_at, paid_through_at` | 授权、扣款开关与已付会员期限独立 |
| 续费账期 | `id, subscription_id, sequence, period_start, period_end, due_at, amount_minor, currency, plan_version_id, order_id, provider_cycle_id, status` | 账期唯一且金额固化；计划中、待提醒、可扣款、处理中、需用户操作、待核对、已付、关闭分别记录 |
| 扣款尝试 | `cycle_id, attempt_no, provider_request_id, mandate_id, scheduled_at, sent_at, failure_class, status, next_retry_at` | 与第 7 节付款尝试合并；重试不新建账期，不把失败次数抹掉 |
| 续费提醒 | `cycle_id, reminder_type, channel, destination_ref, scheduled_at, sent_at, delivery_status, template_version, content_hash` | 保存通知内容与投递证据，提醒失败可恢复处理 |
| 每期权益 | `cycle_id, order_id, installment_no, operation_key, policy_version, status` | 接入既有发放计划，账期发放与每月分期分别去重 |

恢复时先隔离旧执行者，再与渠道核对有效授权、取消结果、账期付款及退款；支付平台可能在网站停机时继续续费，不能只检查本地定时任务。任何恢复出的 active 授权须核实未在备份后撤销，才允许继续派发。以原账期和交易号重放，缺少归属进入待核账，不按当前日期批量补扣历史月份。渠道托管与本地调度迁换需先停旧执行方并查清在途款，确认无双重调度后再放行。

### 9.8 自动续费开放门槛

**<span style="font-size:18px;color:#fff">规则写好不等于可以扣钱。只有用户授权、扣款、取消、退款和出故障后的处理都跑通，才给用户显示自动续费入口。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">门槛：渠道 recurring 能力获批；授权与提醒政策已确认；执行方唯一；取消实际生效可验证；失败/未知结果闭环；逐账期权益与退款正确；AUTO 验收通过。新签约与现存订阅停扣分开控制，隐藏按钮不能替代取消渠道订阅。灰度、真实小额测试与部署另行授权。</span>

## 10. 退款、拒付与对账

**<span style="font-size:18px;color:#fff">退款必须既查钱有没有退回，也处理对应会员和剩余额度。用户已经用掉多少权益，要按购买前公开的退款规则处理。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">退款与权益调整分离但关联。退款成功是渠道事实，权益回收失败进入补偿队列，不能把退款事实改成失败；不凭手工退款单号直接宣告渠道退款成功。</span>

| 事项 | 处理要求 |
|---|---|
| 提交退款 | 校验申请权限、退款政策、原支付币种及剩余可退金额 |
| 并发退款 | 待审批、处理中、成功和结果未知均占用原支付的可退金额；加锁防止超退 |
| 退款超时 | 持原退款编号查询，查清前不得另建退款重复退钱 |
| 原路退回 | 优先通过原支付交易退款；不自动转到任意第三方账户 |
| 权益回收 | 关联原订单发放记录；明确已消费额度和正在执行任务如何处理；不误扣其他订单赠送额度 |
| 拒付与争议 | 保存渠道案件编号、期限、证据和处理结果；按规则暂停相关权益，保留申诉记录 |
| 每日对账 | 分渠道、币种、账期核对订单、实收、退款、手续费、净结算与到账 |
| 对不上金额 | 建立差异任务、告警、责任人和处理期限；禁止为了对平直接修改历史金额 |
| 人工处理 | 必填原因和外部证据，关键动作二次确认，保留操作记录 |

### 10.1 按实际收款分别算能退多少

**<span style="font-size:18px;color:#fff">一张 100 元订单误收了两次，要分别记录两个 100 元。先退多收的 100 元，不应取消正常会员；正常购买也要退款时，再处理另一笔。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">逐 payment_id、币种计算可退金额：确认实收－成功退款－待审批/处理中/未知退款占用－已确认不可再退的拒付金额；重叠争议与退款需对账消除双计。争议期间限制退款并查询渠道可退状态。正常商品退款另受订单政策上限约束；`duplicate_collection` 退回独立处理，不重复调整权益。</span>

| 情况 | 规则 |
|---|---|
| 审批驳回或用户取消 | 仅在未提交渠道且确认无外部副作用时释放占用，保留审批记录 |
| 渠道明确失败 | 核实失败属于终态才释放；超时、连接断开不能当失败 |
| 同一退款重复提交 | 同键同金额和原支付返回原申请；同键不同内容拒绝 |
| 多笔收款都退款 | 每笔不超过各自剩余可退额；订单不能只用“总退款达到订单金额”判断正常商品已全退 |
| 多收款退回成功 | 只减少对应异常实收的待处理金额，不回收合法购买的会员与额度 |
| 退款已成功但权益调整失败 | 保存真实退款，建立待调整任务；重复执行只调整一次 |

### 10.2 发票与退款联动

**<span style="font-size:18px;color:#fff">开票和退款要一起核对。已经退掉的钱不能继续当成正常购买金额开票；已经开过票的订单退款后，也要留下对应处理记录。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">复用 invoice_requests / invoice_request_orders，扩展净可开票金额、币种与更正记录；具体发票调整操作按开票渠道及财务确认规则执行，本文不声明已实现自动开票或税务处理。</span>

| 情况 | 处理要求 |
|---|---|
| 申请开票 | 核对成功购买的净金额、已有开票占用和退款；异常重复收款不作额外商品收入开票 |
| 合并开票 | 限同一有权限的空间与同币种；不同币种不直接相加 |
| 开票处理中发生退款 | 原子登记冲突并暂停或转人工核对，避免双方各按旧金额完成 |
| 已开票后退款 | 不删除原票；关联退款与必要的更正/冲红处理进度，不把发票处理失败写成退款失败 |
| 开票驳回后重申 | 保留旧申请，确认未实际开出后释放占用；不能因旧关联永久阻止重申 |

## 11. 接口、安全与页面要求

**<span style="font-size:18px;color:#fff">网站只展示付款结果，真正的收款确认交给后台。工作人员能看订单，不代表能随意退款或修改密钥。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">以下为目标契约。复用 `/api/billing/orders`、退款和通知入口时必须兼容现有调用；未实现的查单、关闭付款尝试、渠道能力接口另行设计并版本化。</span>

| 范围 | 必须满足 |
|---|---|
| 创建与查询 | 服务端定价；按用户与空间授权；返回订单号、状态、下一操作，不回传支付私钥 |
| 渠道适配 | 各渠道实现下单、查单、关单、退款、查退款、验签和状态转换；不支持的能力明确返回 |
| 通知认证 | 严格使用各渠道官方签名、证书及解密规则；核对环境与收款账户；支持密钥轮换 |
| 通知重试 | 先可靠落库；按渠道响应协议确认接收；业务失败由持久化任务重试、超限告警；不能只返回成功就丢失处理 |
| 密钥 | 仅服务端保管，配置页面脱敏；不进 Git、不进浏览器、不进日志；读配置与改配置权限分开 |
| 网络 | HTTPS、请求体大小限制、超时、限流、回调地址固定；不允许用户指定任意服务端跳转或请求目标 |
| 页面反馈 | 提交、取消、退款等操作成功失败均用统一 antd `App.useApp().message` 提示，并保留可恢复的订单状态 |
| 确认弹窗 | 取消订单、关闭渠道、退款等关键动作确认；展示金额、币种、对象和后果 |
| 查询频率 | 页面按需轮询并退避，隐藏时降低频率；后台合并同订单查单，不对每次页面刷新调用渠道 |
| 审计 | 保存操作者、对象、原因和结果；客服、财务、管理员分权；人工发权益也有独立记录 |

### 11.1 停用渠道、注销与历史记录

**<span style="font-size:18px;color:#fff">不再接受新付款，不代表旧订单可以不管。用户注销或团队解散后，未完成退款仍要处理，工作人员仍需能核对原收款。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">拆分新下单、历史查单、通知接收、退款能力开关。软停用渠道保留必要凭证版本与路由；凭证泄露则立即撤销并启用安全替代，不为历史兼容继续使用泄露密钥。财务保留与账号删除独立，个人信息按最小化原则及确认后的保留政策处理。</span>

| 操作 | 保留什么 | 阻止什么 |
|---|---|---|
| 关闭新收款 | 历史通知、查单、对账、退款与待办 | 新建可支付交易 |
| 注销账号 | 审核未决订单，保留必要账务编号和受控售后途径 | 删除账本或把退款转到任意新账户 |
| 团队解散 | 确定退款处理责任人，保留原空间归属和审计 | 把团队历史交易改成个人交易 |
| 历史清理 | 按统一保留策略处理明细、通知原文和脱敏数据 | 只按备份保留天数删除财务原始记录 |

### 11.2 性能和异常积压

**<span style="font-size:18px;color:#fff">付款人数增加时，查看订单不能拖垮网站。处理不过来的付款消息必须排队保留，并提醒工作人员，不能丢掉。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">生产启用前确定并记录峰值下单 QPS、并发查单、回调突发量、P95/P99 响应时间、最大积压年龄、恢复追平时间和渠道限额。注册用户总数不能代替并发负载。使用索引、分页、短事务、有限连接池与有界 Worker；重试退避加抖动。</span>

压测必须同时包含正常查询与重复通知，核对测试前后账务记录数量。报告写清环境、数据量、输入负载、实测延迟、错误率及积压恢复时间；任何已接收消息丢失、重复发放或跨空间读取均不通过。数值门槛待上线前确认，未填写或未测不得宣称通过。

## 12. 备份、恢复与以后更换服务

**<span style="font-size:18px;color:#fff">把网站记录恢复到昨天，不会把今天收的钱退回。恢复后必须重新核对付款平台的记录，补上漏单，再恢复正常购买。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">数据库回滚不能回滚外部金融交易。结合 [备份回滚恢复](09-备份回滚恢复.md) 执行恢复演练，并对恢复点至当前的渠道账单、支付、退款、续费、权益进行重放与对账。</span>

| 情况 | 操作顺序 | 验证结果 |
|---|---|---|
| 付款服务故障 | 暂停新付款入口，保留原订单查询；告警 | 用户不会被引导重复支付 |
| 数据恢复 | 暂停扣款、自动退款、续费和权益任务；保存或安全重试回调；恢复备份 | 记录恢复时间点与丢失窗口 |
| 恢复后核账 | 先补渠道实收与退款事实，再按原操作编号重放权益 | 不重复收款、不重复发放、无漏单 |
| 更换数据库托管 | 保留订单号、渠道号、唯一约束、流水和任务进度 | 切换前后同笔付款仍只产生一次权益 |
| 切换支付平台 | 新订单使用新渠道；旧订单仍走原渠道查单和退款 | 原付款与原渠道关系不丢失 |
| 版本回退 | 保持新旧接口兼容，单独评估数据库变更 | 不通过恢复旧库来“撤销”真实收款 |

**<span style="font-size:18px;color:#fff">恢复不能只补一条收款金额，还要查出这笔钱原来是谁买的、买给哪个团队、买了什么。查不清就留给人工核对，不能猜着发会员。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">恢复材料须覆盖订单快照、workspace/purchaser 关联、价格与权益政策版本、渠道订单映射和去重标记。恢复点之后的新订单若已丢失，优先从受保护的独立订单记录、日志链或可信渠道映射重建；渠道仅返回金额不足以重建归属。无法关联的实收进入待核账清单，不自动创建任意用户订单。</span>

| 恢复检查 | 放行条件 |
|---|---|
| 原进程与新进程隔离 | 停止旧实例写入，废除旧任务领取资格，确认只有恢复后的服务能推进付款和权益 |
| 通知与实收覆盖 | 核对恢复点前仍未决交易，以及恢复点至当前的全部实收/退款；不能只查新建交易 |
| 订单重建 | 每笔款项有可信订单映射，或进入有责任人的待核账记录；不随意猜测用户 |
| 密钥与权限 | 注入当前有效密钥，重放注销、撤权和删除记录，不复活旧权限 |
| 放行报告 | 无未解释的金额差；孤立实收与未决退款有清单和处理限制；记录哪些功能仍未放行 |

恢复目标和备份保留期统一引用 [备份回滚恢复](09-备份回滚恢复.md) 的相应阶段与后续修订，不在这里另建一套数值。该文正式付费阶段列有候选 RPO ≤ 5 分钟、RTO ≤ 4 小时，均须演练确认，不能据此声称当前已达标。告警响应和财务记录保留期另行确认，不能用备份保留期代替财务保留期；不承诺零停机或零数据丢失。

## 13. 验收清单

**<span style="font-size:18px;color:#fff">能付成功一次还不够。必须试过卡顿、重复点击、重复通知、退款失败和恢复记录，才开放真实收款。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">以下是完整目标验收清单。部分底层情况已在本地隔离 PostgreSQL 测试中覆盖，覆盖范围见本节后面的“本次本地验证”；其他项目仍未验收。正式渠道开通后另安排经授权的小额真实付款与退款，保存脱敏证据。</span>

| 编号 | 测试场景 | 必须看到的结果 |
|---|---|---|
| PAY-01 | 正常购买 | 付款、订单、订阅与额度一致 |

### 13.2 自动续费专项验收

**<span style="font-size:18px;color:#fff">自动续费要单独测试，尤其要试“取消和扣款碰到一起”“网站停机时平台仍在扣款”“手动补缴和自动重试碰到一起”。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">以下 AUTO 项全部待执行；与 PAY 基础验收共同作为开放门槛，不以模拟时钟或模拟回调单独替代渠道端验证。</span>

| 编号 | 场景 | 必须看到的结果 |
|---|---|---|
| AUTO-01 | 未主动选择、授权失败、仅浏览器返回成功 | 不开启自动扣款；授权成功但首款失败也不发已付权益 |
| AUTO-02 | 同期两个任务或两方调度 | 唯一执行方；本地及渠道不会分别主动扣一次 |
| AUTO-03 | 提醒重复执行、投递失败 | 提醒去重，有失败记录；未满足约定提醒条件时实际执行方暂停扣款 |
| AUTO-04 | 明确软失败、需用户验证、授权撤销 | 分别按已确认次数重试、等待用户、立即停续；不无限重试 |
| AUTO-05 | 发起后超时、渠道已收款、通知丢失 | 查原交易，不能新扣；到账补发原期权益一次 |
| AUTO-06 | 取消先于派发、取消与网络提交竞争 | 前者不派发；后者显示待核对并查在途交易，不虚报全部取消 |
| AUTO-07 | 渠道取消超时、确认停续后新扣款 | 本地保持停扣；异常实收进入可追踪退款补偿 |
| AUTO-08 | 平台侧解约、网站侧重新开启 | 解约同步停止调度；重新开启明确确认且不补扣停用月份 |
| AUTO-09 | 涨价、优惠到期、升级、降级、改席位 | 按授权和政策版本处理；未经确认不得越过授权扣款范围 |
| AUTO-10 | 手动补缴与自动重试、更换付款方式 | 同账期复用订单；查清并控制原尝试后付款，不产生不受控双收 |
| AUTO-11 | 扣款成功但权益失败、重复回调 | 实收保留，同期权益补发一次，不新增下一期扣款 |
| AUTO-12 | 取消续费后本年度仍有分期赠送 | 保留已付期权益和赠送；未来未付期不再扣款 |
| AUTO-13 | 本期退款/拒付，与下一期扣款竞争 | 按锁与确认后的政策裁决停续、查单；不回收其他已付期权益 |
| AUTO-14 | 注销、团队解散、授权人离职 | 禁止新派发并核实渠道停续；售后可追踪，团队权益不转给个人 |
| AUTO-15 | 跨月末、闰年、夏令时、延迟扣款 | 固定账期边界不重复、不漏期；迟到款按确认政策处理 |
| AUTO-16 | 恢复旧库、停机期间渠道续扣、旧任务再运行 | 旧执行者失效；先核授权和账单，已撤销授权不复活，不批量补扣 |
| AUTO-17 | 跨渠道/执行方切换、关闭续费功能 | 核实旧调度停用与在途款，已付时间衔接，历史查询退款继续可用 |
| AUTO-18 | 宽限到期、重试耗尽、长期结果未知 | 按确认政策限权且保留原已购权益；未知交易持续追踪，不当作失败再扣 |

## 14. 实施顺序与待确定事项

**<span style="font-size:18px;color:#fff">先确定第一种付款方式和退款规则，再开发一条完整流程。没有确定的规则先保留为待定，不能由代码偷偷替你决定。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">实施顺序：准入与政策确认 → 字段差异审查 → 单渠道适配 → 幂等与权益事务 → 退款/查单/对账 → 故障恢复 → 验收 → 开放渠道。各阶段修改文件前另行提供清单并取得开工授权。</span>
