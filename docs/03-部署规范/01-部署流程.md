# 自动部署规范

本仓库通过 GitHub Actions 构建前端，并部署到腾讯云轻量服务器。

**<span style="font-size:18px;color:#fff">上线后怎样整理临时文件、旧软件、备份和运行记录，按服务器维护规范执行。先保护网站正常使用和恢复能力，再清理确认无用的内容。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">参见 <a href="02-服务器整洁与安全维护.md">服务器整洁与安全维护规范</a>。该文包含只读检查记录、治理规则及待实施项，不表示已清理生产文件或启用自动维护；继续遵守本文件的旧哈希资源保留要求。</span>

1. **<span style="font-size:18px;color:#fff">前端代码你一提交，系统自动构建并部署到服务器；但后端服务得你手动把文件传上去、再重启才生效。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">前端 git push origin main 后 GitHub Actions 自动构建部署；后端 scripts/deploy/api-server.mjs 需手动 scp 上传到 ubuntu@43.160.249.6:~/qingyu-api/ 并重启 node 进程</span>


2. **<span style="font-size:18px;color:#fff">登录服务器用 ubuntu 账号，不要用 root。账号填错会直接报"认证失败"。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">SSH 登录账户使用 ubuntu，公钥在该账户 ~/.ssh/authorized_keys；不能填 root，否则 unable to authenticate</span>


3. **<span style="font-size:18px;color:#fff">登录用的私钥只保存在加密配置中，不能提交到代码仓库，也不能写进日志。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">私钥只保存在 GitHub Actions 的 SSH_PRIVATE_KEY 加密配置中，不得提交到仓库或写入日志</span>


4. **<span style="font-size:18px;color:#fff">文件先传到 ubuntu 账号能写的目录，再通过管理员权限复制到网站目录——因为 ubuntu 账号没有直接写网站目录的权限。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">先上传到 ubuntu 可写的 /home/ubuntu/qingyu-upload，再通过 sudo 复制到 /var/www/qingyu-web</span>


5. **<span style="font-size:18px;color:#fff">上传时要去掉 dist 这一层目录，让 index.html 直接在网站根目录下；不然多套一层目录会导致页面打不开。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">上传 dist/* 必须设置 strip_components:1，让 index.html 直接位于上传目录下，避免网站根目录多套一层 dist 导致 403</span>


6. **<span style="font-size:18px;color:#fff">部署新版本时不要立刻删除旧文件，正在访问的用户还在用旧文件；等流量切到新版本后再清理。也不要在发布前清空网站目录。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">覆盖文件时保留旧的带哈希资源，避免正在打开页面的用户遇到资源丢失；不在发布前清空网站目录</span>


7. **<span style="font-size:18px;color:#fff">这次自动部署只更新前端，后端服务和其他服务需要单独部署，不在自动流程里。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">当前工作流只发布前端，API 后台和 Agent 服务需要独立部署</span>


8. **<span style="font-size:18px;color:#fff">推送前先在本地构建一遍，确认没有错误再发布。页面上需要弹登录框的地方，要在同一个组件里读取登录状态，不然生产构建会因为引用未定义而失败。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">推送前先运行 npm run build；页面组件新增登录保护操作时，要在同一组件读取 useAuthStore 的 openAuthModal，避免生产构建因未定义引用失败</span>


9. **<span style="font-size:18px;color:#fff">出问题别乱查：先看是哪一步失败的，再看那一步的日志。连不上服务器就核对账号和密钥对不对；上传成功但页面打不开，就检查文件路径和网站服务状态。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">排查顺序：先定位失败步骤，再查看具体日志。SSH 认证失败核对登录账户和公钥指纹并查服务器 SSH 日志；上传成功但页面异常时检查网站根目录及 HTTP 状态</span>


- SSH 登录账户使用 `ubuntu`，对应公钥位于该账户的 `~/.ssh/authorized_keys`。不能将账户误填为 `root`，否则会出现 `unable to authenticate`。
- 私钥只保存在 GitHub Actions 的 `SSH_PRIVATE_KEY` 加密配置中，不得提交到仓库或写入日志。
- 先上传到 `ubuntu` 可写的 `/home/ubuntu/qingyu-upload`，再通过 `sudo` 复制到 `/var/www/qingyu-web`。
- 上传 `dist/*` 时必须设置 `strip_components: 1`，确保 `index.html` 直接位于上传目录下，避免网站根目录多套一层 `dist` 导致 403。
- 发布前检查上传的 `index.html`；远程脚本遇错即停。发布后检查 Nginx 配置与首页 HTTP 响应，不以文件上传成功作为完整验收。
- 覆盖文件时保留旧的带哈希资源，避免正在打开页面的用户遇到资源丢失；不在发布前清空网站目录。
- 当前工作流只发布前端，API 后台和 Agent 服务需要独立部署。
- 推送前先运行 `npm run build`；页面组件新增登录保护操作时，要在同一组件读取 `useAuthStore` 的 `openAuthModal`，避免生产构建因未定义引用失败。

排查顺序：先定位失败步骤，再查看具体日志。SSH 认证失败时核对登录账户和公钥指纹，并查看服务器的 SSH 日志；上传成功但页面异常时检查网站根目录及 HTTP 状态。

## 详细部署规则

## HTTPS 反代与 Appwrite OAuth

10. **<span style="font-size:18px;color:#fff">用户通过 HTTPS 访问时，要告诉后端这个请求是加密来的；不然后端会以为请求不安全，不断重定向，用户就卡在循环报错里。所有域名统一用正式域名，不要用 IP 地址。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">若域名经 Cloudflare 代理，源站 Nginx 收到的可能仍是 HTTP；转发到 /v1/ 的请求必须把 X-Forwarded-Proto 固定为 https，否则 OAuth 重定向死循环 ERR_TOO_MANY_REDIRECTS；_APP_DOMAIN、_APP_CONSOLE_DOMAIN、Google OAuth 站点域名统一用 litzone.art，不用服务器 IP</span>


11. **<span style="font-size:18px;color:#fff">如果后端还是识别不出请求是加密的，只改转发设置没用；需要给后端开一个专门的端口，让请求直接走这个端口，并在请求里标明是加密协议。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">若 Appwrite 自带 Traefik 仍把转发协议识别为 HTTP，给 appwrite 容器增加主机端口（如 8081:80），Nginx 直接代理到该端口并保留 X-Forwarded-Proto: https，再确认 OAuth redirect_uri 必须以 https:// 开头</span>


如果域名通过 Cloudflare 等代理访问，源站 Nginx 收到的可能仍是 HTTP。转发到 Appwrite 的 `/v1/` 请求必须把 `X-Forwarded-Proto` 固定传为 `https`，否则 OAuth 地址会不断重定向到自身，浏览器会报 `ERR_TOO_MANY_REDIRECTS`。Appwrite 的 `_APP_DOMAIN`、`_APP_CONSOLE_DOMAIN` 和 Google OAuth 使用的站点域名也必须统一，例如 `litzone.art`，不要继续使用服务器 IP。

如果 Appwrite 自带 Traefik 仍然把转发协议识别为 HTTP，单纯修改 Nginx 请求头不会生效。此时给 `appwrite` 容器增加主机端口（例如 `8081:80`），让 Nginx 直接代理到该端口，并保留 `X-Forwarded-Proto: https`，再检查 OAuth 的 `redirect_uri` 必须以 `https://` 开头。

## 模型资源与发布验收

12. **<span style="font-size:18px;color:#fff">语音识别需要的大文件要用专门的大文件存储方式保存。上线时必须取回完整文件，不能只上传一个记录文件位置的小文件。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">当前 .gitattributes 对 public/models/**/*.data、public/models/**/*.wasm、public/models/*.zip 配置 Git LFS；.github/workflows/deploy.yml 的 actions/checkout 使用 lfs: true。发布后检查模型 URL 的状态、Content-Type 和 Content-Length，避免将 LFS 指针或前端回退 HTML 当作模型内容。</span>


13. **<span style="font-size:18px;color:#fff">把代码传上去不等于已经上线。先确认这次发布的每一步都成功，再打开正式网站，检查页面需要的文件和后台服务能否访问。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">推送前执行 npm run build；后端文件有改动时执行 node --check scripts/deploy/api-server.mjs。推送后按本次 commit SHA 查 GitHub Actions，确认 conclusion=success；再检查正式域名首页、首页引用的脚本与样式、/api/config/public 及模型资源。HTTP 可访问只证明发布基础检查通过，不代替登录、语音识别、生成和计费等业务验收。失败时先定位工作流步骤或具体资源，再处理。</span>


14. **<span style="font-size:18px;color:#fff">发布后台前先核对线上文件是否已经更新。文件内容相同、服务正常时，不需要重复上传和重启；内容不同时，仍要单独发布后台。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">比对本地与生产 api-server.mjs 的 SHA-256，并核查 qingyu-api 服务及公开配置接口。仅文件相同不能证明运行进程已加载最新版本；不能确认时需补查进程启动时间与文件更新时间，或按部署流程重启后复验。前端工作流成功不能作为后端已发布的证据；其他后端文件有变更时也要分别核对。</span>


15. **<span style="font-size:18px;color:#fff">检查构建前先记下已有修改，检查后再看哪些文件发生了变化。只有确认是这次检查生成的临时变化，才可以恢复，不能覆盖你原来正在改的内容。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">构建前后分别检查 git status 与 git diff。仓库历史上仍跟踪少量 dist 文件，npm run build 可能改写或删除它们；不要因 .gitignore 包含 dist/ 就假设其不会出现在差异中。只对已确认由本次构建产生、且构建前无用户改动的具体路径恢复，不执行全工作区恢复。线上产物由 GitHub Actions 重新构建。</span>
