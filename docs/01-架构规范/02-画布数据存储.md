# 画布数据存在哪

## 1. 这是什么

**<span style="font-size:18px;color:#fff">你在画布上摆的节点、连的线、跟 AI 聊的天，这些内容的正主是云端服务器，不是你自己的浏览器。你打开画布是从服务器拉下来看，改完了是写回服务器；浏览器只是个临时看的地方，不能拿"我本地存了"当成已经保存好。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">画布结构化数据（项目元信息、节点、连线、聊天会话与消息）的权威存储为 PostgreSQL；浏览器 localForage/localStorage 仅作为运行时缓存与临时编辑状态，不作为持久化草稿来源。本文件规定画布结构化数据的存储位置、加载与保存流程、失败提示口径；文件本体（图片、视频、音频、长文本）的存储规则见《01-生成图对象存储》，多设备同步与冲突规则见《04-需求规范/10-多设备会话与同步》。</span>


## 2. 画布数据存哪

**<span style="font-size:18px;color:#fff">一张画布拆成几部分存：画布叫什么名字、长什么样、你缩放到哪了，记在一张表里；每个节点是什么类型、摆在哪、多大，记在另一张表里；节点之间怎么连的，又是一张表；你跟 AI 聊的天和每句话，各自一张表。所有表都归在你自己的个人空间下面，别人看不见。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">PostgreSQL schema app 下分表存储：canvas_projects（项目元信息：external_key、title、background_mode、show_image_info、viewport、version、status）、canvas_nodes（节点：node_key、node_type、position、width、height、metadata）、canvas_connections（连线：connection_key、from_node_id、to_node_id）、canvas_chat_sessions 与 canvas_chat_messages（聊天）、canvas_project_assets 与 canvas_node_asset_uses（素材关联与固定版本）。所有表带 workspace_id 隔离，个人空间为 type='personal'。</span>


**<span style="font-size:18px;color:#fff">节点里的图片、视频、音频和大段文字，不塞在画布记录里。这些文件先传到腾讯云，画布记录里只写一个文件编号，用到哪个素材就引用哪个编号。这样画布本身的记录很轻，打开快；大文件单独存，省空间也好管理。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">saveCanvasSnapshot 校验拒绝在 nodes.metadata、messages.text、references 中携带 content/dataUrl/blob/https 等内联大内容；文本与媒体正文必须先经 uploadMediaFile 写入 COS，画布快照只接受 textStorageKey/textChecksum 或 asset_id。素材引用通过 canvas_project_assets 与 canvas_node_asset_uses 固定 asset_version_id 与 file_id，不随素材最新版本漂移。</span>


## 3. 打开画布时怎么加载

**<span style="font-size:18px;color:#fff">你打开画布页面，第一件事是问服务器要"我有哪些画布、每张画布里有什么"。服务器返回的那一份才是真的；浏览器里上次留的东西只是临时缓存，不能拿来当数据用。如果服务器没连上，就告诉你"现在打不开"，不能拿本地旧数据冒充云端数据。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">进入画布页后调用 GET /api/canvas/projects（credentials: include），按 workspace 权限返回 active 项目及其 nodes、connections、chatSessions、messages；前端以服务端返回结果作为初始状态。本地 localForage 中的旧数据仅在服务端不可用且产品明确允许离线阅读时作降级展示，且必须显著标记"离线模式，数据可能不是最新"；不得在服务端可达时优先使用本地数据。</span>


**<span style="font-size:18px;color:#fff">你换了电脑、换了浏览器，打开还是那些画布，因为正主在云端。不是说你在自己电脑上摆了半天，换个电脑就没了。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">画布数据按 appwrite_user_id 解析到个人 workspace，与浏览器、设备无关；同一账号在任意设备登录后 GET /api/canvas/projects 都能拿到同一批 active 项目。删除项目通过 status='deleted' 标记，不物理删除，见备份与恢复规范。</span>


## 4. 改完怎么保存

**<span style="font-size:18px;color:#fff">你拖一个节点、改一句聊天，过一小会儿就自动存回服务器。存的时候会带上"我这是基于服务器第几版改的"，服务器看版本对得上才让写；对不上（说明另一边先改了）就告诉你"有冲突"，不会偷偷盖掉别人刚改的。只有服务器真写进去了，才算"已保存"。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">前端对变更做 400ms 防抖后 POST /api/canvas/projects/snapshot，body 中每个 project 携带 serverVersion（来自上一次保存成功返回的 versions 或首次 GET 返回的 version）。后端在事务内按 version 做乐观锁 UPDATE：where version = expectedVersion；版本不匹配返回 409 + code=VERSION_CONFLICT + conflicts[]。成功后后端返回新的 serverVersion，前端更新本地版本标记。</span>


**<span style="font-size:18px;color:#fff">保存是一张画布一张画布地确认，不是"整个页面保存成功"。哪张存上了、哪张没存上，要分得清。你一次改了三张画布，其中一张网络抽风没存上，就只提醒那一张，不能三张都报成功，也不能三张都报错。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">saveCanvasSnapshot 逐 project 处理，任一 project 校验或写入失败即整体回滚事务并抛出；返回成功时 versions 数组列出本次实际写入的 external_key 与新 serverVersion。前端应按 projectId 分别跟踪保存状态（idle/saving/saved/error），错误提示按 projectId 维度，不做"全有或全无"的笼统提示。</span>


**<span style="font-size:18px;color:#fff">生成中的内容先不往云端存。你点了"生成图片"，图还在转圈的时候，这张画布先不往服务器发；等图真出来、真传好，再一起存。不然存上去的是一个"还在生成中"的半成品，换个设备打开就看到半截东西。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">hasGeneratingCanvasContent() 检测任一 node.metadata.status==='loading' 或 texts/images 中存在 loading 项时，跳过云端 snapshot，仅写 localForage 草稿；生成结束后恢复正常防抖保存。该规则是过渡保护，最终目标是生成任务状态独立持久化（见多设备同步规范第 7 节），不依赖"整个画布不发"来保护半成品。</span>


## 5. 保存失败怎么提示

**<span style="font-size:18px;color:#fff">存云端失败了，就明说"云端保存失败"。不要说"本机画布已保存"——那会让你以为没事了，其实换个电脑就看不到刚改的东西。失败就是失败，按钮可以再点一次，但不能假装成功。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">禁止出现"本机画布已保存，但云端同步失败"这类把 localForage 当作成功兜底的文案。前端错误口径：网络/5xx 类失败显示"云端保存失败，请检查网络后重试"；409 版本冲突显示"这张画布在别处已有新版本，你的修改还没存上"；401/登录态过期显示"登录已失效，请重新登录后再保存"。保存状态指示器需对应三态：保存中 / 已保存（服务器确认）/ 保存失败（可重试）。</span>


**<span style="font-size:18px;color:#fff">同一张画布连续保存失败好几次，不要每次都弹一个红框盖满屏幕。失败一次提醒一次就够了，反复失败就把状态挂在那个小角落，你有空再去看；不要一边干活一边被连续弹出四五个一模一样的错误。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">同一 projectId 的 SYNC_FAILED 在指定时间窗口（如 30 秒）内只弹一次 toast，后续失败更新角落状态指示器计数；VERSION_CONFLICT 需用户显式处理，不合并。acknowledgeCanvasSyncIssue 后若再次失败，发布新 issue 时使用递增 attempt 计数，不重复触发 toast。</span>


**<span style="font-size:18px;color:#fff">版本冲突时，你在这台机器上改的东西不能直接丢。要告诉你"服务器那边已经有新版本了"，让你自己决定：是放弃这边的改动，还是把这边的改动另存成一张新画布。不能服务器说有冲突，就把你刚画的盖掉。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">收到 409 VERSION_CONFLICT 时，前端保留当前内存中的未提交修改，弹窗展示冲突说明，提供"放弃本机修改并刷新"与"另存为新画布"两个选项；另存为新画布走 createProject 流程，不带 expectedVersion 插入新 external_key，不复活已删除项目。草稿在用户做出选择前不清空。</span>


## 6. 跟其他规范怎么衔接

**<span style="font-size:18px;color:#fff">画布上放的图片、视频、音频和长文本，存到哪、怎么传、权限怎么查，听《对象存储》那本规范的；画布跟多设备同时登录、版本号、断线重连怎么处理，听《多设备会话与同步》那本规范的。这本只管画布本身的结构数据怎么放。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">跨规范边界：文件本体路径、COS 目录结构、上传/下载/签名 URL、素材版本固定 → 《01-架构规范/01-生成图对象存储》；会话上限、设备管理、outbox 事件、实时推送游标、恢复代次、安全威胁矩阵 → 《04-需求规范/10-多设备会话与同步》。画布结构化数据的表结构、乐观锁、快照写入流程在本文件定义。</span>


**<span style="font-size:18px;color:#fff">画布关联的素材，版本是钉死的。你在画布上放了一张图，后来那张图在素材库里被改了、出了新版本，画布上这张还是原来那张。你要换新版，得自己手动在画布上换，不会自动跟着变。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">canvas_project_assets 与 canvas_node_asset_uses 固定 asset_version_id 与 file_id；保存时校验该版本属于当前 workspace 且 file_objects.status='ready'，否则整体回滚。后续要切换素材版本必须经用户显式操作，见对象存储规范 14.4 节。</span>


## 7. 现在长什么样（当前实现）

**<span style="font-size:18px;color:#fff">现在后端已经有一套正经的数据库表了：画布项目、节点、连线、聊天、素材关联都分表存，带版本号，冲突会拒绝。但是前端还在用浏览器本地当"主仓库"——先把整个画布塞进浏览器本地数据库，再隔几百毫秒往云端同步一次。同步失败就跟你说"本机已保存"，这跟你现在要的"云端才是正主"是反着的。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">后端已实现：app.canvas_projects/nodes/connections/chat_sessions/chat_messages/project_assets/node_asset_uses 全套表，saveCanvasSnapshot 事务写入 + 乐观锁版本号 + 409 VERSION_CONFLICT + outbox 事件；listCanvasSnapshots 按 workspace 拉取。前端现状：useCanvasStore 使用 zustand persist + localForageStorage，将 projects/deletedProjects 整体持久化到浏览器；setItem 400ms 防抖后先写 localForage 再 syncCanvasState POST snapshot；失败时 publishCanvasSyncIssue(SYNC_FAILED) 弹"本机画布已保存，但云端同步失败"。这是待改造的旧模式。</span>


**<span style="font-size:18px;color:#fff">前端的问题不止是文案。现在的保存是"整包上传"：你改了一个节点的位置，它会把整张画布所有节点、连线、聊天记录整个打包发给服务器，服务器那边是先全删再全插。画布上节点多了之后，哪怕只动了一个字，传的数据也很大，慢，也更容易冲突。后面要改成只发改了什么，而不是每次都重发整张画布。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">当前 snapshot 写入流程：对每个 project 先 DELETE canvas_nodes/connections/chat_sessions，再重新 INSERT 全量节点、连线、消息。这是粗粒度整项目覆盖，不是增量操作。后续目标：按节点/连线/消息粒度做 PATCH，携带 expected_version，减少冲突面与传输量；与多设备同步规范第 9 节"改不同节点以可独立节点为粒度"对齐。</span>


**<span style="font-size:18px;color:#fff">生成中的内容先不存云端这个保护现在是有的，靠前端检测"有没有节点还在转圈"。等后面改成真正的增量保存和任务独立持久化，这个保护就能撤掉，不用整包不发了。</span>**<br>
<span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">hasGeneratingCanvasContent() 跳过 snapshot 仅写 localForage 是过渡方案；长期目标是 generation_tasks 独立记录任务状态与输出，画布只引用 task_id，不再用"整张画布不保存"来保护半成品。</span>
