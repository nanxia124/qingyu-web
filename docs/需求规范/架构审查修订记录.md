## 3. 仍需完成的设计与验证

当前交付为需求总览和重点约束，不是全量物理数据字典。实际建表前，按上线功能逐表补齐字段、类型、空值、默认值、约束、索引、权限策略、保留期和接口，并生成经审查的 Migration。

产品仍需确定：团队数量限制、邀请与席位规则、谁能购买团队订阅、资产共享可见范围、公开链接期限、内容保留期、退款和取消计费、文件存储方案。未确定的高影响功能维持关闭，不替用户假定收费规则。

性能数值、备份保留和恢复指标是候选目标，需在资源预算和业务上线范围确定后演练。将来十万注册用户不意味着目前必须购买十万人并发配置。

## 4. 以后必须复用的检查规则

1. 新表先写“事实归属”，后写字段；已经有权威表时，不新增第二个可写副本。
2. 文件存在、接口定义、路由挂载、写入成功和线上验收是五种不同证据，不能混用。
3. 每个空间关联同时审查归属与记录编号；跨空间只能走明确授权关系。
4. 任何外部收费操作都考虑超时结果不明、重复执行、取消和迟到回调。
5. 迁移预案必须回答“目标已产生新数据之后怎么办”，不能只写换回连接地址。
6. 所有完成声明要写验证层级；格式检查通过不能表述成代码、性能或迁移通过。
7. 新功能同步更新总览、所属模块和受影响的横向规范，避免只在最后不断追加另一套互相矛盾的规则。
