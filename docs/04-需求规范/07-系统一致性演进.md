# 系统一致性、演进与运营审查

版本：0.4。日期：2026-09-23。状态：设计约束和现状审查，尚未完成实现与演练。返回 [数据库总览](01-数据库与多租户总览.md)。

### 这是什么
规定系统里时间怎么算、编号怎么排、数据怎么统一。

### 用户怎么用
用户不直接看，效果是手机生的图电脑能按时间看到、刷新列表不重复不漏。

### 现在长什么样
时间统一用 UTC、编号统一用 UUID，老代码里随机 ID 正在清理。
## 1. 时间、编号和排序必须先统一

当前源码同时出现 SQLite Unix 秒、JavaScript `Date.now()` 毫秒、ISO 字符串和 Appwrite 时间字符串；旧表使用整数自增 ID，前端还有 `Date.now() + Math.random()` 和 `nanoid()` 生成编号。它们都能在本地工作，但不能直接作为跨设备、跨服务和迁移后的统一主键。

1. **<span style="font-size:18px;color:#fff">现在各处记时间的方式不统一：有的按秒、有的按毫秒、有的写"昨天下午"，时间一乱就对不上。所以系统规定：时间统一按世界标准时间记，每条数据发一个全球不重复的编号，这样你手机上生的图，电脑登录后也能按正确顺序排出来，刷新列表不会重复、不会漏。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">现状同时存在 SQLite Unix 秒、JS Date.now() 毫秒、ISO 字符串、Appwrite 时间字符串；旧表整数自增 ID，前端用 Date.now()+Math.random()、nanoid() 生成编号。目标：跨设备、跨服务、迁移后统一主键。</span>

<br>

目标规则：

| 对象 | 统一规则 | 原因 |
|---|---|---|
| 数据库时间 | `timestamptz`，服务端以 UTC 写入 | 不受服务器时区和夏令时影响 |
| API 时间 | RFC 3339 UTC 字符串，例如 `2026-09-23T08:00:00Z` | 客户端不会猜秒还是毫秒 |
| 内部主键 | 初期由服务端生成标准 UUIDv4，并用主键约束兜底；客户端离线编号单独映射 | 不依赖数据库扩展或客户端时钟；UUIDv7 如需采用需另做兼容性评估 |
| 外部旧 ID | 单独保存 legacy source、legacy_id 和 mapping 表 | 迁移不改变原记录且能追溯 |
| 排序 | 时间相同用 id 作为第二排序键；分页使用稳定游标 | 不漏记录、不重复记录 |
| 业务编号 | 订单号、任务号可单独生成，不能拿展示编号当外键 | 业务编号可隐藏时间和分片信息 |

2. **<span style="font-size:18px;color:#fff">具体规矩：时间一律按世界标准时间存，不管服务器在北京还是纽约都不会乱；对外给的时间带个"Z"后缀，一看就知道是秒还是毫秒；每条数据发一个全球不重复的编号，不靠你电脑自己生成；老系统过来的旧编号单独存档，能查得到对应关系；两条数据时间一模一样时，再按编号排，翻页时不会漏一条也不会重复一条。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">数据库时间 timestamptz 服务端 UTC 写入；API 时间 RFC3339 UTC 字符串（如 2026-09-23T08:00:00Z）；内部主键初期服务端生成 UUIDv4 并用主键约束兜底，客户端离线编号单独映射，UUIDv7 需另做兼容评估；外部旧 ID 单独存 legacy source/legacy_id/mapping 表；排序时间相同用 id 作第二键，分页用稳定游标；订单号/任务号单独生成，不能拿展示编号当外键。</span>

<br>

用户已明确不需要迁移旧测试业务数据：首次 PostgreSQL 上线以空库初始化，不建设 SQLite 数据迁移工程，也不擅自删除旧库。已有 Appwrite 身份是否保留与业务库初始化分开处理；保留身份时，经验证的首次登录幂等创建内部用户与个人空间，不迁入旧业务历史。

3. **<span style="font-size:18px;color:#fff">以前测试时攒的那些假数据，这次不迁过来，新系统从零开始。你以前的登录账号可以保留，但旧账号里的那些测试图、测试记录不一起迁过来，也不随便把你的旧账号删了。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">用户已明确不迁移旧测试业务数据：首次 PostgreSQL 上线以空库初始化，不建 SQLite 迁移工程，不擅自删旧库；已有 Appwrite 身份是否保留与业务库初始化分开处理，保留时经验证的首次登录幂等创建内部用户与个人空间，不迁入旧业务历史。</span>

<br>

以后如明确需要导入项目文件，必须声明旧时间单位、格式版本和 ID 映射，不能按字段名猜测或直接覆盖同名记录。未来 PostgreSQL 搬到托管数据库保持原主键，不重新编号。时间相同加 ID 能稳定排序，但并发编辑中的翻页仍可能变化；导出要求一致视图时使用有期限的快照任务。

4. **<span style="font-size:18px;color:#fff">以后万一要从老地方导东西进来，必须说清楚旧时间是按秒还是毫秒、旧编号怎么对应，不能凭着字段名字就瞎猜、直接盖掉同名记录。以后换后台存数据的地方，也不给数据重新发编号，还是原来那套。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">未来导入项目文件必须声明旧时间单位、格式版本和 ID 映射，不能按字段名猜测或直接覆盖同名记录；PostgreSQL 搬到托管数据库保持原主键不重新编号；时间相同加 ID 可稳定排序，但并发编辑中翻页仍可能变化，导出要求一致视图时用有期限快照任务。</span>


## 2. 外部结果不是永久数据

上游返回的图片、视频或音频 URL 可能过期、需要鉴权、被删除或无法在未来迁移。`generation_outputs` 不能只保存 URL。正确生命周期是：

5. **<span style="font-size:18px;color:#fff">AI 生成完图，给的是一个临时链接，过段时间可能失效、要登录才能看、甚至被删。所以系统不能只把这个临时链接记下来，得趁链接还有效时把图真的下载存到自己服务器上，才算永远是你的。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">上游返回的图片/视频/音频 URL 可能过期、需鉴权、被删除或无法迁移；generation_outputs 不能只保存 URL。</span>

<br>

```text
上游响应
  → 保存 provider_request_id 和原始响应摘要
  → 下载/复制到受控 file_objects
  → 校验 checksum、mime、大小、尺寸和时长
  → file_object = ready 后才挂到 asset_versions
  → 对外返回短期下载地址
```

如果上游只返回外链，结果状态只能是 `external_pending` 或 `external_unarchived`，不能显示为永久保存成功。下载失败要进入可重试任务；超过保留期限仍没有归档，向用户明确提示“链接可能失效”。数据库备份和文件备份分开校验，不能只备份 URL。

6. **<span style="font-size:18px;color:#fff">具体动作是：先记下这张图是向谁要的、长什么样 → 趁链接有效赶紧下载存到自己服务器 → 核对文件大小、格式、尺寸对不对 → 确认存好了，才把它挂到你的作品里 → 平时给你看的还是个临时预览地址。如果对方只给了个外链、还没下载成功，作品会标着"待归档"，不会骗你说"已永久保存"。备份时图片文件和业务记录要分开备份，光备份链接没用。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">生命周期：保存 provider_request_id 和原始响应摘要→下载/复制到受控 file_objects→校验 checksum/mime/大小/尺寸/时长→file_object=ready 后才挂 asset_versions→对外返回短期下载地址。只返回外链时状态只能是 external_pending 或 external_unarchived，不能显示永久保存成功；下载失败进可重试任务；超期未归档向用户提示"链接可能失效"；数据库备份和文件备份分开校验，不能只备份 URL。</span>


## 3. 状态机必须分清业务维度

每个可恢复对象都要写状态迁移规则，不允许页面自行拼接状态。

7. **<span style="font-size:18px;color:#fff">每样东西都有它自己的一套状态，比如一个生图任务会从排队、生成中走到成功或失败，不能由网页随便拼一个状态出来。下面这张表规定了每样东西从开始到结束，状态只能怎么变，乱变会被系统拒绝。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">每个可恢复对象都要写状态迁移规则，不允许页面自行拼接状态。</span>

<br>

| 对象 | 建议状态 | 终态 | 终态后规则 |
|---|---|---|---|
| 生成任务 | queued → running / cancel_requested / reconciling → succeeded / failed / cancelled | succeeded、failed、cancelled | reconciling 是等待核对的中间态；终态由授权执行器按 version 和租约条件提交 |
| 生成尝试 | pending → dispatched → provider_succeeded / provider_failed / unknown | provider_succeeded、provider_failed | unknown 非终态，等待查询；不能因未知就重新付费调用 |
| 文件 | pending → ready / failed；failed → pending 重试；经引用核验后进入 deleting → deleted | deleted | ready 仅代表持久化完整，使用还需检查与授权；传输状态归 upload_sessions；历史外键可指向 deleted 墓碑 |
| 上传会话 | initiated → uploading → completing → completed；取消经 aborting → aborted；异常可 failed | completed、aborted、failed | 重试创建新尝试并保留原文件身份，completed 不等于文件 ready；迟到云端请求仍需核查 |
| 订阅 | pending → active / past_due → cancelled / expired | 单次订阅周期结束，不代表订阅槽永久失效 | subscriptions 是空间订阅槽，可进入新周期；周期变更记事件，取消续订与立即停权分开 |
| 订单与资金 | 订单付款状态 pending → paid / cancelled；payment 尝试另记成功失败，refund/dispute 独立记录 | 以各子对象契约定义 | paid 以后可以退款或争议；不能把已支付历史改写成从未支付 |
| 成员 | invited → active ↔ suspended；active/suspended → left；left 可重新邀请加入 | 无永久业务终态 | 复用成员关系，变化追加 membership_events；重入不得自动恢复旧权限 |
| 分享授权 | pending → active → revoked / expired | revoked、expired | 过期后不再签发新文件地址 |
| Outbox | pending → processing → delivered / retrying / dead_letter | delivered；dead_letter 为待处置 | dead_letter 可受控重放，保留原 event_id 以便消费者去重 |

每次迁移记录 actor、request_id、旧状态、新状态、原因、时间和版本。数据库约束或状态服务拒绝非法跃迁。页面的 `pending/success/failed` 只是展示映射，不能成为数据库事实。

8. **<span style="font-size:18px;color:#fff">举几个你天天见的：你的图正在生成时是"排队/生成中"，最后变成"成功/失败/已取消"；如果网络卡住不知道出没出来，会停在"核对中"，这时候系统不会因为不知道就再花钱重生成一遍。一笔订单付了就是付了，以后退款可以另记一笔，但不能把"已付款"偷偷改回"没付款"。成员离职是"离开"，以后再邀请回来是新的记录，不会自动把他以前的权限又恢复。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">生成任务 queued→running/cancel_requested/reconciling→succeeded/failed/cancelled；生成尝试 pending→dispatched→provider_succeeded/provider_failed/unknown（unknown 非终态，不能因未知就重新付费调用）；文件 pending→ready/failed，核验引用后 deleting→deleted；上传进度由 upload_sessions 管理；订阅 pending→active/past_due→cancelled/expired，订阅槽可进新周期；订单 pending→paid/cancelled，refund/dispute 独立记录，paid 后可退款不能改写历史；成员 invited→active↔suspended→left，left 可重新邀请，重入不自动恢复旧权限；分享授权 pending→active→revoked/expired；Outbox pending→processing→delivered/retrying/dead_letter。每次迁移记录 actor/request_id/旧状态/新状态/原因/时间/版本，非法跃迁被拒绝；页面 pending/success/failed 只是展示映射，不是数据库事实。</span>

<br>

生成任务的 status 表示产品任务进度；attempt.status 表示供应商执行结果；输出清单与 file_objects.status 派生的只读 persistenceStatus 表示归档；quota_reservations 表示额度处理。上游成功但归档失败时，保留上游成功事实，任务进入 reconciling 并仅重试下载，不重新生成。这些维度通过同一 task_id 及固定输出槽位关联，不能互相覆盖；用户何时扣费按明确的产品计价规则决定。

9. **<span style="font-size:18px;color:#fff">注意："任务进度""对方有没有生成成功""文件存没存好""额度扣没扣"是四件分开记录的事，不能互相盖掉。比如图对方其实生成出来了，只是咱们这边还没下载归档好——那就只重试下载，绝不再花钱让对方重新生成一遍。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">生成任务 status=产品任务进度，attempt.status=供应商执行结果，输出清单与 file_objects.status 派生 persistenceStatus=归档，quota_reservations=额度处理；上游成功但归档失败时保留上游成功事实，任务进 reconciling 仅重试下载，不重新生成；这些维度通过同一 task_id 及固定输出槽位关联，不能互相覆盖；用户何时扣费按明确产品计价规则决定。</span>


## 4. API 契约与兼容策略

当前前端、qingyu_server 和 canvas-agent 由不同代码目录维护，不能依赖“大家记得改”。每个公共接口必须登记：方法、路径、认证、workspace 范围、请求 schema、响应 schema、错误码、幂等规则、超时、分页、版本和审计动作。

10. **<span style="font-size:18px;color:#fff">网页、后台、AI助手这三块是不同人写的，不能靠"大家记着改"。它们之间每一条数据通道都要有一份写死的约定：数据叫什么、谁能取、长什么样、出错算谁的、超时多久算失败。没有这份约定的通道，不许上线。</span>**<br>
    <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">前端、qingyu_server、canvas-agent 分目录维护，不能靠"大家记得改"；每个公共接口必须登记方法、路径、认证、workspace 范围、请求 schema、响应 schema、错误码、幂等规则、超时、分页、版本、审计动作。</span>

<br>

规则：

1. 新接口先定义服务端 schema；未知字段默认拒绝或明确忽略，不能把任意 JSON 直接落库。
2. 破坏性变化新增 `/v2` 或经过兼容窗口；旧字段保留到客户端迁移完成。
3. 同一语义只能有一个正式路由；旧 `/api/users`、billing token 和 Appwrite 入口要登记兼容期限。
4. 状态码和错误结构统一；失败不能返回 200 再让前端猜。
5. 客户端超时、重复提交和断线重连都按幂等请求处理。
6. 公开接口、内部接口、管理员接口、Agent 本地高权限接口分开认证和审计。

接口契约文件和 Migration 同步评审；没有契约、权限和回滚说明的接口不进入生产。

11. **<span style="font-size:18px;color:#fff">几条硬规矩：网页多传了莫名其妙的字段，不许偷偷存进去；要改老通道就另开一个新版本，老的留一段时间等大家适应；同一个功能只能有一个正式入口，旧入口要登记"什么时候关"；失败就是失败，不许假装成功再让网页猜；你网络抖了一下重复点、断线重连，都不能重复扣你钱。</span>**<br>
    <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">规则：①新接口先定服务端 schema，未知字段默认拒绝或明确忽略，不能任意 JSON 直接落库；②破坏性变化新增 /v2 或经过兼容窗口，旧字段保留到客户端迁移完成；③同一语义只有一个正式路由，旧 /api/users、billing token、Appwrite 入口登记兼容期限；④状态码和错误结构统一，失败不返回 200 让前端猜；⑤客户端超时、重复提交、断线重连都按幂等请求处理；⑥公开/内部/管理员/Agent 本地高权限接口分开认证和审计。接口契约与 Migration 同步评审，无契约、权限和回滚说明的接口不进生产。</span>


## 5. 数据生命周期、导出和删除

用户能看到的“删除”必须拆成几个事实：隐藏、回收站、永久删除、匿名化和账务保留。订单、支付、额度流水、审计和安全事件各自定义保留依据与期限，不因为注销就级联删除，也不能一律永久保留。必要身份字段是否保留需按实际业务和适用要求确认，不能笼统承诺全部匿名化或“天然合规”。

12. **<span style="font-size:18px;color:#fff">你点的"删除"其实分好几层：先在你眼前藏起来 → 放进回收站还能恢复 → 真删了 → 把你的身份抹掉 → 但付款和订单记录还得留着（这是法律要求）。不能你一注销账号，订单和付款记录就凭空消失，也不能啥都永远留着。</span>**<br>
    <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">用户"删除"拆成：隐藏、回收站、永久删除、匿名化、账务保留；订单/支付/额度流水/审计/安全事件各自定义保留依据与期限，不因注销级联删除，也不一律永久保留；必要身份字段是否保留按业务和适用要求确认，不能笼统承诺全部匿名化或"天然合规"。</span>

<br>

## 6. 配置、插件和供应链

## 7. 成本与资源边界

“十万用户”首先是成本和资源问题，不只是数据库容量。每个 workspace 至少有存储、生成次数、Token、并发、外部 API 成本和导出任务限制。平台还要有供应商级每日预算、单请求最大输入、最大文件尺寸、最大保留期和异常流量熔断。

18. **<span style="font-size:18px;color:#fff">将来真有十万人用，最先顶不住的不是存储空间，而是钱和资源。所以每个空间都要限：存多少、生几次、同时跑几个、导出占多少。整个平台还要设"今天最多给 AI 供应商花多少钱"，流量不对劲就自动熔断，不能让人无限花钱。</span>**<br>

## 8. 最小运营闭环

上线前必须有以下可操作入口，而不是只有表：

- 任务管理：查看 queued/running/reconciling/dead_letter，暂停、重试、人工确认和审计。
- 额度和账务对账：按空间、订单、任务、供应商和时间段重算并导出差异。
- 密钥轮换：新增版本、灰度验证、撤销旧版本，不在日志显示明文。
- 数据删除/导出：查看进度、失败原因、重试和完成证明。
- 配置发布：草稿、校验、发布、回滚、影响范围和操作人。
- 事故处理：request_id/task_id 查询链路，限流、关闭供应商、只读模式和维护页。

20. **<span style="font-size:18px;color:#fff">真上线前，后台得有一套能点的管理界面，不能只有一张张空表：能看出各个部分健不健康；能看到哪些任务卡住了，能暂停、重试、人工放行；能按空间和时间把额度和订单重新核对一遍，找出对不上的地方；能换新密钥而不泄露；能看删除和导出跑到哪一步、为什么失败；出大事时能一键限流、关掉某个 AI 供应商、切到"只看不改"模式和维护页。</span>**<br>
