# 计费与任务一致性规范

版本：0.3。状态：设计约束，尚未实现、对账或并发验证。返回 [总览](数据库与多租户需求规范.md)。

## 1. 数据分组与关键字段

| 表 | 关键字段 | 大白话与限制 |
|---|---|---|
| plan_versions | id、plan_id、price_minor、currency、effective_at、status | 一版套餐一份价格和权益，已售版本不覆盖 |
| subscriptions | id、workspace_id、plan_version_id、status、period_start、period_end | 每空间一个基础订阅槽；免费权益也走统一规则 |
| orders | id、workspace_id、created_by、plan_version_id、amount_minor、currency、status、idempotency_key | 订单保存购买时的金额和权益快照，前端不能决定应付金额 |
| payments | id、workspace_id、order_id、provider、provider_payment_id、status、paid_at | 第三方交易号在提供商范围内唯一，可有多次付款尝试 |
| payment_events | id、provider、provider_event_id、payload_hash、status、received_at | 回调验签后记录；事件号唯一，避免反复赠送额度 |
| refunds | id、workspace_id、payment_id、amount_minor、status、idempotency_key | 退款也有独立状态，申请不等于退款成功 |
| quota_accounts | id、workspace_id、unit、available、reserved、version | 一空间一额度单位一账户；两类余额非负 |
| quota_ledger | id、workspace_id、account_id、operation_key、kind、available_delta、reserved_delta、task_id、created_at | 只追加的额度流水；operation_key 在账户内唯一 |
| quota_reservations | id、workspace_id、account_id、task_id、amount、settled_amount、released_amount、status、expires_at | 先锁住本次最多可花的额度，再结算，不能超扣 |
| usage_records | id、workspace_id、task_id、attempt_id、metric、quantity、source_event_id | 事实用量，如 Token、图片张数，不能直接等同于钱包金额 |
| generation_tasks | id、workspace_id、created_by、model_id、status、version、idempotency_key、request_hash、pricing_version_id | 用户一次意图对应一任务；价格版本必须固定 |
| generation_attempts | id、workspace_id、task_id、provider_request_id、attempt_no、status、lease_until、lease_token | 一次任务可有多次执行尝试；记录上游请求和领取租约 |
| outbox_events | id、workspace_id、event_type、aggregate_id、payload_version、status、attempts、next_attempt_at | 事务内记录要做的后续工作；失败不丢任务 |

money 使用最小货币单位整数并带币种，不用浮点数。额度用明确单位的整数或固定精度 numeric，不能把“元”“Token”“次数”相加。初期不建设现金充值钱包；如以后开放充值，wallet_accounts/wallet_ledger 另行定义，不能与 quota_ledger 混用。

## 2. 一次生成的完整流程

```text
认证、空间权限与权益检查
    → 幂等校验
    → 短事务：原子预占额度 + 创建任务 + 写 Outbox
    → 提交后返回 task_id
    → Worker 领取任务并记录租约
    → 事务外调用 AI / 上传文件
    → 短事务：写结果 + 记录用量 + 结算或释放预占 + 更新状态
    → 异步通知与统计
```

大白话：先把这次预算留住，再生成；成功后按规则结账，把多留的钱释放。耗时的外部请求不能一直占着数据库事务。

额度预占必须通过数据库条件更新或行锁原子完成：可用余额足够才同时减少 available、增加 reserved。任务、预占流水和 Outbox 同事务提交，任一步失败全部回滚。所有流程按固定账户顺序加锁；遇到死锁或序列化失败，只做有上限且幂等的重试。

幂等键范围为 (workspace_id,created_by,operation,idempotency_key)。相同键和相同请求返回原任务；相同键而请求内容不同返回 409。平台支付回调使用提供商事件编号，不能由浏览器伪造。幂等保留期限必须长于客户端、队列和回调的最大重试窗口。

## 3. 状态与异常处理

| 场景 | 状态与处理 | 不能做什么 |
|---|---|---|
| 还在排队 | queued；允许原子取消并释放预占 | 不能取消后仍被 Worker 领取 |
| 已被领取 | running；有效租约持有者推进状态 | 不能两个 Worker 同时有效结算 |
| 用户请求停止 | cancel_requested；等待外部停止结果 | 不能直接认定未产生上游费用 |
| 成功且文件确认就绪 | succeeded；结算实际额度并释放差额 | 不能文件没落地就显示永久保存成功 |
| 确认失败且无可计费用量 | failed；释放预占 | 不能只改任务状态而遗漏流水 |
| 超时、断网、上游结果不明 | reconciling；查询上游状态，保留待核对额度 | 不能自动当失败再发一次付费请求 |
| 部分结果成功 | 记录每个输出和实际用量；按价格快照结算 | 不能把失败输出算成完整成功 |
| Worker 重启或租约过期 | 恢复查询；新 lease_token 排除旧 Worker 的迟到写入 | 不能只恢复内存状态就算任务可靠 |

当上游支持幂等键时传递稳定请求标识；不支持时不能承诺外部调用“恰好一次”。发生结果不明时进入对账，避免盲目重试。对于流式、无法预知总量的请求，设定最大预算，超预算前追加预占或停止；不能先透支再把余额写成负数。

预占到期需要先核验任务和提供商状态，再释放。未解决的结果不明应进入告警和人工处理时限，不能无限占用用户额度。最终业务期限和付费规则在收费前确认。

## 4. 支付、退款、兑换与对账

回调先验签，再校验商户、订单、金额、币种、最终支付状态。支付事件入库、订单状态变化、权益发放必须在同一短事务内完成。客户端跳转到“支付成功”页面不能触发发放。

重复回调返回相同结果；乱序事件不得把已支付订单退回待支付。退款以支付平台确认结果为准，用关联原流水的冲正记录调整，不删除原支付。已经消费的额度怎么抵扣、部分退款规则、取消生成的计费条件均为待确认产品规则，未确定前不能开启对应收费功能。

兑换码需有效期、适用方案、使用次数上限和兑换记录；在事务中原子占用。邀请奖励需唯一的合格事件记录，不能反复注册或重复回调无限领额度。初期不启用未经定义的奖励功能。

| 对账对象 | 必须核对 |
|---|---|
| 额度账户 | 从起始值和所有流水可重建 available/reserved，且余额非负 |
| 预占 | 预占总量 = 已结算 + 已释放 + 未决部分 |
| 任务 | 每个终态有唯一结算决议；无悬空输出和未处理预占 |
| 支付 | 平台已确认交易与订单、发放流水一一对应；退款额不超可退额 |
| 供应商成本 | 与用户收费分别记录；上游花费不等于用户扣费 |

## 5. 投递、验收与上线门槛

Outbox 消费按至少一次投递设计；消费者以 event_id 或业务唯一键去重，处理结果和去重记录原子提交。重试有次数和退避，超过上限进入待处理队列并告警。初期可用 PostgreSQL 持久任务表轮询，不强制部署 Redis 或独立消息队列。

必须验证：余额仅够一次时并发发起十次；同一请求重复发送；同键不同内容；回调重复和乱序；Worker 领取后崩溃；外部成功而本地超时；取消与成功同时到达；部分成功；重复退款；交易处理中断库。允许拒绝或等待核对，不允许重复发权益、余额负数、跨空间结算和无记录丢单。

本规范定义的是验收要求，不是这些测试已经通过。P0 接入任何消耗平台成本的调用前落实额度保护和可恢复任务；正式收费前再通过真实支付沙箱和对账验收。
