## 1. 从第一性原理定义系统必须守住的事实

第一性原理就是先不看页面和表名，只问“系统必须保证什么”。轻域至少必须守住以下不变量（Invariant，任何状态下都不能被破坏）：

1. **<span style="font-size:18px;color:#fff">这份文件规定了系统必须守住的 9 条安全底线，任何时候都不能破，哪怕页面打不开、用户急着催图也不能跳过。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">第一性原理：不看页面和表名，只问"系统必须保证什么"。以下 Invariant（不变量）任何状态下都不能被破坏。</span>

<br>

| 不变量 | 大白话 | 破坏后的后果 |
|---|---|---|
| 身份唯一 | 一个请求只能对应一个已验证的内部 user_id | A 用户可以冒充 B 用户 |
| 空间唯一 | 每条个人或团队业务数据只有一个明确 workspace_id | 数据串租户、团队互相看见 |
| 权限不可绕过 | 页面、接口、后台任务、文件、SSE、Agent 都走同一权限判定 | 关掉页面按钮仍能直接调用接口 |
| 密钥不外泄 | 平台 API Key、用户 Key、数据库密码不进入浏览器长期存储、日志和普通响应 | 任意脚本或访客盗用密钥，产生费用 |
| 钱和额度守恒 | 订单、支付、额度预占、结算、退款可以从流水重算 | 重复扣费、超发额度、账对不上 |
| 外部副作用可追踪 | 每次可能收费的上游调用有唯一请求号和最终状态 | 超时后重试造成重复生成和重复扣费 |
| 已确认数据不丢 | 数据库、任务、文件和事件都有恢复路径 | 重启后任务消失、结果丢失 |
| 读写边界清楚 | 业务事实只由一个模块写入，其他模块读或通过事件协作 | 两处同时修改，最后写入覆盖正确值 |
| 失败可见 | 失败返回失败，不能显示成功；异常进入告警或待处理 | 用户以为已保存，运营却找不到数据 |

2. **<span style="font-size:18px;color:#fff">记住，"页面能打开""图能生成"都不算数。这 9 条底线比这些都重要——破任意一条，要么有人能冒充你、要么钱算错、要么你的图凭空消失。</span>**<br>
   <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">这些不变量优先于"接口能返回""页面能打开"和"暂时能生成"。</span>

## 3. 统一请求生命周期

所有业务请求按下面的固定顺序执行，不能由各路由自行发挥：

13. **<span style="font-size:18px;color:#fff">每个请求都必须按固定顺序处理：先限流 → 确认你登录了、认出你是谁 → 查你属于哪个空间、有没有权限 → 检查是不是重复请求 → 先把任务或订单记下来 → 这才去调外部 AI → 最后把成功或失败记下来，给你一个查询编号。每一步顺序不能乱，更不能先扣钱再查你是谁。</span>**<br>
    <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">所有业务请求按固定顺序执行，各路由不得自行发挥：限流→验 Appwrite 会话并映射内部 user_id→解析 workspace_id 并验成员/角色/资源/订阅→校验幂等键与版本→短事务写任务/订单/预占/Outbox→事务提交后才调外部服务→持久化成功/失败/重试/结果不明→返回 request_id/task_id 和明确状态。</span>

<br>

```text
请求进入
  → 限制来源、大小、超时和速率
  → 验证 Appwrite 会话并映射内部 user_id
  → 解析 workspace_id，并验证成员、角色、资源和订阅
  → 校验幂等键与请求版本
  → 在短事务中写入任务/订单/预占/Outbox
  → 事务提交后才调用外部服务或发异步任务
  → 持久化成功、失败、重试或结果不明
  → 返回稳定 request_id/task_id 和明确状态
```

读取接口也要走身份和空间校验；只有健康检查、公开模型目录等明确的公共接口才允许例外，并单独设置速率限制和返回字段。

14. **<span style="font-size:18px;color:#fff">就连"只看一眼"的查询，也得先查你是谁、有没有资格看这个空间的数据。只有像"健康检查""公开模型列表"这种人人能看的才例外放行，而且也要限速、只给必要信息。</span>**<br>
    <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">读取接口也要走身份和空间校验；仅健康检查、公开模型目录等明确公共接口允许例外，单独设置速率限制和返回字段。</span>


## 4. 统一失败原则

| 状态 | 用户看到什么 | 数据动作 |
|---|---|---|
| 未登录 | 登录提示或 401 | 不创建业务记录 |
| 无权限 | 403，或为防止泄露返回 404 | 不改变任何数据 |
| 重复请求 | 原任务/订单结果或 409 | 不重复扣费、不重复创建 |
| 外部超时但结果不明 | “核对中”，不是“失败” | 保留任务和预占，后台查询或人工对账 |
| 数据库提交失败 | 失败和 request_id | 事务回滚，不能显示成功 |
| 文件上传失败 | 失败或处理中 | 业务记录不能引用未 ready 文件 |
| 通知失败 | 主业务成功，通知待重试 | Outbox 保留并告警 |

15. **<span style="font-size:18px;color:#fff">系统报错怎么告诉你，也有死规矩，核心就一条：没办成就是没办成，不许骗你说"成功了"。订单没真受理就不能显示"已下单"。比如网络卡了、不知道图出没出来，界面会告诉你"核对中"，而不是瞎说"失败"或"成功"。</span>**<br>
    <span style="display:inline-block;font-size:12px;color:#666;transform:scale(0.35);transform-origin:left top;line-height:1">失败原则表：未登录→登录提示/401 不建记录；无权限→403 或 404 不改数据；重复请求→原结果或 409 不重复扣费/创建；外部超时结果不明→"核对中"，保留任务和预占待对账；提交失败→失败+request_id 回滚；上传失败→业务记录不引用未 ready 文件；通知失败→主业务成功，Outbox 保留并重试告警。</span>

<br>

前端不能根据“请求发出”或“页面跳转回来”判断业务成功。成功必须由服务端返回已提交的事实。

16. **<span style="font-size:18px;color:#fff">所以判断成没成功，不是看你有没有跳回页面、按钮转没转完圈，而是服务器那边真的把数据存下来了，才算数。</span>**<br>

## 7. 第一性原理验收清单

1. 两个 Appwrite 用户、两个个人空间、两个团队互相访问和批量查询，不能越权。
2. 任意篡改 URL 中的 workspace、task、asset、file、thread 编号，必须拒绝或返回不泄露存在性的 404。
3. 同一生成请求、支付回调、兑换码、邀请奖励并发重复提交，结果只能产生一次业务事实。
4. Worker、数据库连接、Agent、文件上传、供应商回调在任意一步重启后，任务和额度可恢复或进入待核对，不静默消失。
5. 目标数据库已写入数据后模拟迁移失败，不能丢订单、额度、作品、权限变更和 Agent 历史。
6. 清理浏览器缓存、换设备、退出登录和撤销成员权限后，不能继续读取私有数据。
7. 限制供应商 Key、单空间并发和每日成本，确认异常流量不会无限消耗费用。
8. 每一项通过证据记录提交号、环境、数据规模、脚本、结果和未解决风险。
