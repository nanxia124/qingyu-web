# 数据库交付记录

## 这次到底做了什么

当前系统还没有正式用户，所以本次没有搬运旧用户数据，也没有删除 Appwrite 的身份数据。做的是建立一套新的业务数据库结构，并把安全边界和关键数据规则写进去。

数据库更新文件里的“迁移”指的是更新空数据库的表、字段、索引、约束和函数。它不是把用户从一个数据库搬到另一个数据库。将来如果真的更换托管 PostgreSQL，才需要另做数据备份、导入、校验和切换。

## 现在的数据安全规则

API 服务现在使用独立的非超级账号 `qingyu_api` 连接 PostgreSQL；它不能创建数据库、创建角色或修改数据库结构，密码只保存在服务器环境文件中。`qingyu_app` 继续保留为受限数据库角色，用于权限测试和受控函数。由于现有服务代码仍有一部分直接查询业务表，`qingyu_api` 当前临时启用了 `BYPASSRLS`，空间归属由后端每个查询的用户条件和业务权限校验保证；后续把全部写入收敛到受控函数后，再关闭 `BYPASSRLS`，恢复纯数据库行级安全。

身份、团队成员、角色权限、支付、额度账户、供应商密钥、审计和迁移记录不能由普通账号直接增删改。以后这些动作要通过后端受控事务完成，避免“把 A 的成员改到 B 的团队”或直接把额度改大。

额度不会只靠一个 `balance` 数字覆盖写入。每次预占、成功结算、失败释放都会留一笔流水；重复请求使用幂等键返回同一结果。账户更新使用行锁，防止两个并发请求同时花掉同一份额度。

- 生成结果：图片生成成功后会在同一事务内写入生成任务、生成输出、文件对象、资产版本和 outbox 事件；前端上传生成结果时会携带来源 `task_id`，后端再次校验任务属于当前用户、当前空间且状态为 succeeded，避免出现“有图片但没有计费事实”的孤立资产。收藏操作复用资产收藏表。保存失败不会阻断当前页面展示，但数据库不会留下半条生成记录。资产文件读取接口会再次校验工作空间权限，并防止对象键跳出对象目录。
- 跨设备资产读取：资产列表中的图片会带登录凭证调用受保护的文件接口，再通过对象 URL 显示；凭证不会放进文件地址，也不会把私有文件变成公开链接。
- 生成元数据：生成结果资产版本会保存提示词、模型、质量和尺寸等元数据，文件和生成过程信息可以一起追溯。
- 生图历史恢复：生图工作台刷新或换设备后从受保护的 PostgreSQL 资产接口恢复最近结果，并通过受保护文件接口读取图片；首屏只读取最近 24 张缩略图，避免一次刷新产生大量文件请求。
- 管理端计费数据：正式环境的统计、用户列表、额度调整和订单列表统一读取 PostgreSQL；额度调整会追加 `adjustment` 流水，并在可用额度不足时拒绝，不再修改旧 JSON 账本。
- 管理后台 API 渠道：供应商地址、模型、启用状态和密钥统一保存在 `platform_api_keys`；密钥使用服务端 AES-256-GCM 加密，数据库不再保留明文。管理列表只返回脱敏值，完整密钥只在管理员授权的模型拉取操作中解密读取。旧 `keys.json` 仅用于首次迁入，迁入后 PostgreSQL 是正式来源。
- API 密钥明文防回写：线上已确认明文字段数量为 0、密文数量为 2；0041 迁移已加入数据库检查约束，任何明文写入都会被 PostgreSQL 拒绝。空库重放、线上明文拒绝测试和备份恢复均已通过。
- 代理身份边界：服务器 AI 代理必须携带业务 JWT；服务器会检查业务会话是否仍为当前在线会话，离线设备不能继续消耗供应商资源。业务登录接口不再相信浏览器单独提交的 `userId`，前端先用 Appwrite 当前会话生成短期 JWT，服务器向 Appwrite 反查并核对用户 ID 后才签发业务 JWT。线上冒用 ID 和未登录代理请求均已实测返回 401。
- AI 调用事实：服务器代理每次调用都会复用 `usage_records` 写入调用人、工作空间、供应商、模型、请求编号和结果状态；开始时为 `reserved`，上游正常返回改为 `committed`，明确失败记为 `failed`，超时或连接中断记为 `unknown`。目前数量单位是 request 次数，不把供应商 Token 或费用猜成用户扣费；真实用量需要以后按供应商回执补录。
- AI 调用额度一致性：付费订阅用户的每次代理请求会用同一个幂等键预占 `monthly` 额度；免费用户按用户、工作空间、日期和功能预占每日 20 次额度。成功响应结算，明确失败释放，超时或断链保持预占并标记 `unknown`，等待补偿核对。重复请求复用原调用记录和原预占，不会重复扣除。
- 未知调用核对：管理员只能对 `unknown` 调用提交明确结论、处理理由和供应商凭据；成功会结算额度，失败会释放额度，处理记录不可修改或删除，重复提交只能返回原结论，相反结论会被拒绝。
- 未知调用接口：`GET /api/admin/billing/usage/unknown` 查看待核对记录；`POST /api/admin/billing/usage/:id/reconcile` 必须带 `confirm=true`、结论、理由和供应商凭据。接口只允许管理员调用，普通请求实测返回 403。
- 额度一致性审计：管理员可调用 `GET /api/admin/billing/quota/audit`，把额度账户当前数字和不可变 `quota_ledger` 重算结果逐账户对比；发现差异只返回差异，不会擅自覆盖余额，避免用错误数字掩盖流水问题。
- 发票数据：用户只能选择自己已支付的订单；一笔订单只能关联一张发票申请。发票申请、订单关联和管理员处理状态放在同一 PostgreSQL 事务边界内，并且发票申请必须绑定工作空间，数据库触发器会拒绝跨工作空间订单。未支付订单、重复申请和跨用户订单都会被拒绝。
- 订单幂等：同一个幂等键只有在套餐和工作空间都一致时才复用原订单；并发创建由 PostgreSQL 唯一约束收敛为一笔，同键换套餐会返回冲突，不会把用户误导到错误套餐。
- 退款数据：退款申请单独记录，不覆盖原支付记录；申请金额不能超过已支付且未退款金额。管理员确认供应商成功后，订单进入 `partially_refunded` 或 `refunded`；供应商失败、处理中和未知状态均保留独立事实，重复退款申请使用幂等键复用。
- 支付回调接收与入账：`POST /api/payment/webhooks/:provider` 只有配置 `PAYMENT_WEBHOOK_SECRET` 并通过 `x-payment-signature` HMAC 校验才接收；供应商事件编号在数据库唯一。成功事件还会在同一幂等处理链中核对订单、金额、币种和交易号，再推进支付记录、订单、订阅和额度；重复回调只返回已处理结果，金额不符或交易号串单会拒绝发放权益。真实供应商密钥和各平台字段映射仍需上线前配置。

## 还没有假装完成的部分

除计费核心链路、团队生命周期、组织架构接口、设备会话、同步事件和基础资产上传链路外，业务前端还没有全面切换到这套表。部门管理页面、邀请邮件发送、真实供应商支付密钥和字段映射、供应商真实 Token 计费、超时调用的自动补偿、真正跨故障域的 COS 备份和告警、字段数据字典仍需继续实现。服务器本地定期备份、挂载镜像副本、临时库恢复验收和空库迁移重放已经启用或验证，但它们不能代替真正异机副本和上线前的完整验收。表数量不能代替这些验收。

SSH 服务器端已把未登录等待从 420 秒降到 60 秒，并提高握手余量、开启连接保活；配置先通过语法检查再平滑 reload。偶发的“TCP 已连接但 banner 超时”仍可能来自外部网络链路，部署脚本应使用 10 秒超时和重试，不能把一次连接失败当成数据库失败。

## 新增数据关联的维护规则

- 涉及空间的关联应同时校验对象编号和空间编号，不能只检查对象存在。
- 拒绝测试必须核对具体约束；不能把重复编号导致的失败当作空间隔离通过。
- 本轮额度分配测试覆盖同空间成功、跨空间使用记录拒绝、跨空间额度批次拒绝；测试数据均回滚。
- 备份恢复成功只证明这份备份能恢复和基础结构存在，不能代替全部业务流程验收。
