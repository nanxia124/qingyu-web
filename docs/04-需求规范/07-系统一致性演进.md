# 系统一致性、演进与运营审查

版本：0.4。日期：2026-09-23。状态：设计约束和现状审查，尚未完成实现与演练。返回 [数据库总览](01-数据库与多租户总览.md)。

### 这是什么
规定系统里时间怎么算、编号怎么排、数据怎么统一。

### 用户怎么用
用户不直接看，效果是手机生的图电脑能按时间看到、刷新列表不重复不漏。

### 现在长什么样
时间统一用 UTC、编号统一用 UUID，老代码里随机 ID 正在清理。
## 1. 时间、编号和排序必须先统一

当前源码同时出现 SQLite Unix 秒、JavaScript `Date.now()` 毫秒、ISO 字符串和 Appwrite 时间字符串；旧表使用整数自增 ID，前端还有 `Date.now() + Math.random()` 和 `nanoid()` 生成编号。它们都能在本地工作，但不能直接作为跨设备、跨服务和迁移后的统一主键。

目标规则：

| 对象 | 统一规则 | 原因 |
|---|---|---|
| 数据库时间 | `timestamptz`，服务端以 UTC 写入 | 不受服务器时区和夏令时影响 |
| API 时间 | RFC 3339 UTC 字符串，例如 `2026-09-23T08:00:00Z` | 客户端不会猜秒还是毫秒 |
| 内部主键 | 初期由服务端生成标准 UUIDv4，并用主键约束兜底；客户端离线编号单独映射 | 不依赖数据库扩展或客户端时钟；UUIDv7 如需采用需另做兼容性评估 |
| 外部旧 ID | 单独保存 legacy source、legacy_id 和 mapping 表 | 迁移不改变原记录且能追溯 |
| 排序 | 时间相同用 id 作为第二排序键；分页使用稳定游标 | 不漏记录、不重复记录 |
| 业务编号 | 订单号、任务号可单独生成，不能拿展示编号当外键 | 业务编号可隐藏时间和分片信息 |

用户已明确不需要迁移旧测试业务数据：首次 PostgreSQL 上线以空库初始化，不建设 SQLite 数据迁移工程，也不擅自删除旧库。已有 Appwrite 身份是否保留与业务库初始化分开处理；保留身份时，经验证的首次登录幂等创建内部用户与个人空间，不迁入旧业务历史。

以后如明确需要导入项目文件，必须声明旧时间单位、格式版本和 ID 映射，不能按字段名猜测或直接覆盖同名记录。未来 PostgreSQL 搬到托管数据库保持原主键，不重新编号。时间相同加 ID 能稳定排序，但并发编辑中的翻页仍可能变化；导出要求一致视图时使用有期限的快照任务。

## 2. 外部结果不是永久数据

上游返回的图片、视频或音频 URL 可能过期、需要鉴权、被删除或无法在未来迁移。`generation_outputs` 不能只保存 URL。正确生命周期是：

```text
上游响应
  → 保存 provider_request_id 和原始响应摘要
  → 下载/复制到受控 file_objects
  → 校验 checksum、mime、大小、尺寸和时长
  → file_object = ready 后才挂到 asset_versions
  → 对外返回短期下载地址
```

如果上游只返回外链，结果状态只能是 `external_pending` 或 `external_unarchived`，不能显示为永久保存成功。下载失败要进入可重试任务；超过保留期限仍没有归档，向用户明确提示“链接可能失效”。数据库备份和文件备份分开校验，不能只备份 URL。

## 3. 状态机必须分清业务维度

每个可恢复对象都要写状态迁移规则，不允许页面自行拼接状态。

| 对象 | 建议状态 | 终态 | 终态后规则 |
|---|---|---|---|
| 生成任务 | queued → running / cancel_requested / reconciling → succeeded / failed / cancelled | succeeded、failed、cancelled | reconciling 是等待核对的中间态；终态由授权执行器按 version 和租约条件提交 |
| 生成尝试 | pending → dispatched → provider_succeeded / provider_failed / unknown | provider_succeeded、provider_failed | unknown 非终态，等待查询；不能因未知就重新付费调用 |
| 文件 | pending → uploading → ready / failed；ready → deleting → deleted；failed 可受控重试或清理 | deleted | ready 是可引用状态，不是不可变终态；归档失败不等于生成失败 |
| 订阅 | pending → active / past_due → cancelled / expired | 单次订阅周期结束，不代表订阅槽永久失效 | subscriptions 是空间订阅槽，可进入新周期；周期变更记事件，取消续订与立即停权分开 |
| 订单与资金 | 订单付款状态 pending → paid / cancelled；payment 尝试另记成功失败，refund/dispute 独立记录 | 以各子对象契约定义 | paid 以后可以退款或争议；不能把已支付历史改写成从未支付 |
| 成员 | invited → active ↔ suspended；active/suspended → left；left 可重新邀请加入 | 无永久业务终态 | 复用成员关系，变化追加 membership_events；重入不得自动恢复旧权限 |
| 分享授权 | pending → active → revoked / expired | revoked、expired | 过期后不再签发新文件地址 |
| Outbox | pending → processing → delivered / retrying / dead_letter | delivered；dead_letter 为待处置 | dead_letter 可受控重放，保留原 event_id 以便消费者去重 |

每次迁移记录 actor、request_id、旧状态、新状态、原因、时间和版本。数据库约束或状态服务拒绝非法跃迁。页面的 `pending/success/failed` 只是展示映射，不能成为数据库事实。

生成任务的 status 表示产品任务进度；attempt.status 表示供应商执行结果；output.archive_status 表示归档；quota_reservations 表示额度处理。上游成功但归档失败时，保留上游成功事实，任务进入 reconciling 并仅重试下载，不重新生成。四者通过同一 task_id 关联，不能互相覆盖；用户何时扣费按明确的产品计价规则决定。

## 4. API 契约与兼容策略

当前前端、qingyu_server 和 canvas-agent 由不同代码目录维护，不能依赖“大家记得改”。每个公共接口必须登记：方法、路径、认证、workspace 范围、请求 schema、响应 schema、错误码、幂等规则、超时、分页、版本和审计动作。

规则：

1. 新接口先定义服务端 schema；未知字段默认拒绝或明确忽略，不能把任意 JSON 直接落库。
2. 破坏性变化新增 `/v2` 或经过兼容窗口；旧字段保留到客户端迁移完成。
3. 同一语义只能有一个正式路由；旧 `/api/users`、billing token 和 Appwrite 入口要登记兼容期限。
4. 状态码和错误结构统一；失败不能返回 200 再让前端猜。
5. 客户端超时、重复提交和断线重连都按幂等请求处理。
6. 公开接口、内部接口、管理员接口、Agent 本地高权限接口分开认证和审计。

接口契约文件和 Migration 同步评审；没有契约、权限和回滚说明的接口不进入生产。

## 5. 数据生命周期、导出和删除

用户能看到的“删除”必须拆成几个事实：隐藏、回收站、永久删除、匿名化和账务保留。订单、支付、额度流水、审计和安全事件各自定义保留依据与期限，不因为注销就级联删除，也不能一律永久保留。必要身份字段是否保留需按实际业务和适用要求确认，不能笼统承诺全部匿名化或“天然合规”。

用户必须能请求数据导出：个人资料、项目、资产元数据、任务历史、账务凭证和分享授权；大文件用受限的临时导出包，不把密钥、内部日志和其他成员数据导出。导出任务本身要验权、限速、过期、审计和可撤销。

删除任务采用“标记 → 阻止新引用 → 生成文件清理任务 → 删除/匿名化 → 校验 → 记录完成”的流程。对象存储删除失败不能把数据库记录假装成已清理。软删除保留窗口、永久删除期限、备份中的延迟消失和法律保留需作为产品规则确认。

恢复旧备份、离线同步和导入均要防止已删除内容复活。删除操作保留最小必要墓碑（对象 ID、空间、删除版本与时间），备份恢复后先重放删除和权限撤销记录，再开放读写；超过墓碑保留期限的旧同步客户端必须重新全量同步。导出开始和下载时都重新验权，成员离职后取消其未完成导出和下载授权。

## 6. 配置、插件和供应链

模型脚本、插件源、提示词源和 WebDAV 都是外部输入，不是天然可信数据。插件必须有来源、版本、checksum、权限清单、启用范围、回滚版本和禁用开关。远程内容先下载到隔离区，校验后再启用；更新失败保留旧版本，不覆盖可运行版本。

平台配置、团队配置和用户偏好分三层：平台设置决定允许范围，团队设置决定团队默认值，用户设置只能在允许范围内覆盖。读取配置时返回“最终生效值”和来源，不能把三层 JSON 互相覆盖造成不可解释的结果。配置更新要有版本、审计和缓存失效事件。

## 7. 成本与资源边界

“十万用户”首先是成本和资源问题，不只是数据库容量。每个 workspace 至少有存储、生成次数、Token、并发、外部 API 成本和导出任务限制。平台还要有供应商级每日预算、单请求最大输入、最大文件尺寸、最大保留期和异常流量熔断。

额度和供应商成本分开记录：用户扣额度不等于平台向供应商支付的钱。失败重试、下载归档、缩略图、日志和备份也会产生资源消耗，不能只统计成功生成次数。

## 8. 最小运营闭环

上线前必须有以下可操作入口，而不是只有表：

- 健康检查和依赖 readiness：数据库、对象存储、Agent、任务执行器和配置服务分别可判断。
- 任务管理：查看 queued/running/reconciling/dead_letter，暂停、重试、人工确认和审计。
- 额度和账务对账：按空间、订单、任务、供应商和时间段重算并导出差异。
- 密钥轮换：新增版本、灰度验证、撤销旧版本，不在日志显示明文。
- 数据删除/导出：查看进度、失败原因、重试和完成证明。
- 配置发布：草稿、校验、发布、回滚、影响范围和操作人。
- 事故处理：request_id/task_id 查询链路，限流、关闭供应商、只读模式和维护页。

## 9. 本轮审查的通过标准

本轮不是说上述能力已经实现。只有完成以下证据，才能把目标写成“已支持”：时间和 ID 迁移样本无误；外部结果有可验证文件副本；非法状态迁移被拒绝；接口契约测试通过；导出、删除和恢复演练通过；插件/密钥轮换可回滚；成本限额和 readiness 在演练中生效。
