# 第一性原理与安全边界审查

版本：0.4。日期：2026-09-23。状态：审查结论与上线门槛，不代表问题已修复。返回 [数据库总览](01-数据库与多租户总览.md)。

### 这是什么
一份红线清单：哪些事绝对不能做错，比如不能冒充别人、钱不能算错、密钥不能泄露。

### 用户怎么用
用户不直接看，但它决定账号不会被盗、数据不会被偷看、钱不会被乱扣。

### 现在长什么样
已列出 9 条红线，P0 的洞还没补完，补完才能正式收费。
## 1. 从第一性原理定义系统必须守住的事实

第一性原理就是先不看页面和表名，只问“系统必须保证什么”。轻域至少必须守住以下不变量（Invariant，任何状态下都不能被破坏）：

| 不变量 | 大白话 | 破坏后的后果 |
|---|---|---|
| 身份唯一 | 一个请求只能对应一个已验证的内部 user_id | A 用户可以冒充 B 用户 |
| 空间唯一 | 每条个人或团队业务数据只有一个明确 workspace_id | 数据串租户、团队互相看见 |
| 权限不可绕过 | 页面、接口、后台任务、文件、SSE、Agent 都走同一权限判定 | 关掉页面按钮仍能直接调用接口 |
| 密钥不外泄 | 平台 API Key、用户 Key、数据库密码不进入浏览器长期存储、日志和普通响应 | 任意脚本或访客盗用密钥，产生费用 |
| 钱和额度守恒 | 订单、支付、额度预占、结算、退款可以从流水重算 | 重复扣费、超发额度、账对不上 |
| 外部副作用可追踪 | 每次可能收费的上游调用有唯一请求号和最终状态 | 超时后重试造成重复生成和重复扣费 |
| 已确认数据不丢 | 数据库、任务、文件和事件都有恢复路径 | 重启后任务消失、结果丢失 |
| 读写边界清楚 | 业务事实只由一个模块写入，其他模块读或通过事件协作 | 两处同时修改，最后写入覆盖正确值 |
| 失败可见 | 失败返回失败，不能显示成功；异常进入告警或待处理 | 用户以为已保存，运营却找不到数据 |

这些不变量优先于“接口能返回”“页面能打开”和“暂时能生成”。

## 3. 统一请求生命周期

所有业务请求按下面的固定顺序执行，不能由各路由自行发挥：

```text
请求进入
  → 限制来源、大小、超时和速率
  → 验证 Appwrite 会话并映射内部 user_id
  → 解析 workspace_id，并验证成员、角色、资源和订阅
  → 校验幂等键与请求版本
  → 在短事务中写入任务/订单/预占/Outbox
  → 事务提交后才调用外部服务或发异步任务
  → 持久化成功、失败、重试或结果不明
  → 返回稳定 request_id/task_id 和明确状态
```

读取接口也要走身份和空间校验；只有健康检查、公开模型目录等明确的公共接口才允许例外，并单独设置速率限制和返回字段。

## 4. 统一失败原则

| 状态 | 用户看到什么 | 数据动作 |
|---|---|---|
| 未登录 | 登录提示或 401 | 不创建业务记录 |
| 无权限 | 403，或为防止泄露返回 404 | 不改变任何数据 |
| 重复请求 | 原任务/订单结果或 409 | 不重复扣费、不重复创建 |
| 外部超时但结果不明 | “核对中”，不是“失败” | 保留任务和预占，后台查询或人工对账 |
| 数据库提交失败 | 失败和 request_id | 事务回滚，不能显示成功 |
| 文件上传失败 | 失败或处理中 | 业务记录不能引用未 ready 文件 |
| 通知失败 | 主业务成功，通知待重试 | Outbox 保留并告警 |

前端不能根据“请求发出”或“页面跳转回来”判断业务成功。成功必须由服务端返回已提交的事实。

## 5. 扩容前后的最小架构

初期使用模块化单体：一个 API 服务、一个 PostgreSQL、一个对象存储、可选的任务轮询 Worker。所有实例共享数据库和文件存储，不能依赖进程内 Map 保存业务状态。

当出现真实瓶颈时再增加 Redis、队列、读副本或独立服务。拆分前必须先定义：数据所有者、接口契约、事件、重试、权限、超时、回滚和观测指标。把服务拆开但仍共用无边界表，只会把脏数据分散到更多地方。

外部 AI 调用要受三层限制：单用户/空间额度、单空间并发、平台供应商并发和成本预算。队列满时明确返回排队或拒绝，不能让请求无限等待。

## 6. 必须建立的运行观测

每个请求、任务、支付、额度和外部调用至少带 `request_id`；任务和上游调用再带 `task_id`、`attempt_id`、`provider_request_id`。日志不记录密码、完整 Token、API Key、提示词中的敏感内容或文件正文。

必须能按以下维度查询：成功率、P50/P95/P99 延迟、4xx/5xx、限流数、队列积压、数据库连接/锁/慢查询、任务恢复、额度差异、支付对账、文件孤儿、跨空间拒绝和密钥读取审计。监控数据是派生数据，不能代替业务流水。

## 7. 第一性原理验收清单

1. 两个 Appwrite 用户、两个个人空间、两个团队互相访问和批量查询，不能越权。
2. 任意篡改 URL 中的 workspace、task、asset、file、thread 编号，必须拒绝或返回不泄露存在性的 404。
3. 同一生成请求、支付回调、兑换码、邀请奖励并发重复提交，结果只能产生一次业务事实。
4. Worker、数据库连接、Agent、文件上传、供应商回调在任意一步重启后，任务和额度可恢复或进入待核对，不静默消失。
5. 目标数据库已写入数据后模拟迁移失败，不能丢订单、额度、作品、权限变更和 Agent 历史。
6. 清理浏览器缓存、换设备、退出登录和撤销成员权限后，不能继续读取私有数据。
7. 限制供应商 Key、单空间并发和每日成本，确认异常流量不会无限消耗费用。
8. 每一项通过证据记录提交号、环境、数据规模、脚本、结果和未解决风险。

上述检查未运行前，只能说“已定义验收标准”，不能说“系统已经安全、可扩展或支持十万用户”。
