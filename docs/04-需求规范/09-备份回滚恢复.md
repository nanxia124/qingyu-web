# 备份、回滚与恢复执行规范

版本：0.5。状态：待部署与演练的执行方案；未配置备份、未验证当前服务器恢复能力。返回 [总览](01-数据库与多租户总览.md)。

### 这是什么
规定数据万一丢了、被误删了、被黑客搞了，怎么从备份恢复，而且要真演练过。

### 用户怎么用
用户不直接接触，效果是数据不会因服务器崩了就没、误删能捞回来、换服务器几小时能恢复。

### 现在长什么样
- ✅ 每天凌晨自动备份，加密存到另一个地方
- ✅ 已演练过恢复
- ❌ 还没做月度自动演练和恢复到指定秒
## 1. 四件事不能混为一谈

| 名称 | 实际做什么 | 不能做到什么 |
|---|---|---|
| 事务回滚 | 未提交的数据库修改撤销 | 不能撤销已发出的 AI 请求或已支付的钱 |
| 业务冲正 | 用新记录纠正已经提交的扣费或权益 | 不删除原流水，不把真实付款改成未付款 |
| 应用回滚 | 退回兼容旧代码版本 | 不自动把数据库结构和数据退回去 |
| 数据恢复 | 用备份重建数据库或找回特定记录 | 不能自动同步恢复支付平台、Appwrite 和对象存储到同一时刻 |

副本、高可用和同步盘不是历史备份：误删除可能也被同步过去。GitHub 源码也不是用户数据备份。

## 2. 两档备份方案

| 阶段 | 数据库措施 | 恢复能力与候选目标 |
|---|---|---|
| 未收费试运行 | 每日逻辑备份；保存角色权限清单、应用配置清单和 Migration 版本；加密异机保存 | 恢复到某次完整备份；目标 RPO 24 小时、RTO 4 小时，需演练确认 |
| 正式付费或重要业务 | 物理基础备份 + 连续 WAL 归档，另保留周期逻辑备份供逻辑迁移 | 在归档完整范围内恢复到指定时点；候选 RPO ≤ 5 分钟、RTO ≤ 4 小时，不是当前保证 |

WAL 是数据库的变更日志，PITR 是重放这些日志到指定时间。普通 pg_dump 不能配上 WAL 就变成时点恢复，必须有兼容的物理基础备份和连续日志链。[PostgreSQL 16 官方说明](https://www.postgresql.org/docs/16/continuous-archiving.html)

候选保留策略：逻辑备份 14 个日备；付费阶段至少覆盖 14 天的基础备份及所需 WAL。基础备份频率根据恢复时间、数据变化量和成本定，候选每日增量/差异、每周全量需在选定备份工具中验证支持。禁止直接按日志文件年龄删除 WAL；必须保留最早有效基础备份到恢复目标所需的完整链。

低写入时归档也可能滞后，须设置并演练日志切换/归档机制；只看到“上次归档成功”不能证明 RPO 达标。存储、异机副本和演练会产生费用，自建数据库免费不代表备份免费。未确定存储供应商、预算和凭据前不采购或启用收费服务。

## 3. 备份清单：不止 PostgreSQL

| 对象 | 必须保存 | 恢复核验 |
|---|---|---|
| PostgreSQL | 数据、结构、约束、权限/RLS、备份清单、日志链、版本和校验和 | 能启动，约束完整，账务一致，权限隔离有效 |
| Appwrite | 实际部署版本要求的数据库、文件、配置、加密依赖 | 两个真实测试身份可登录并映射到原内部用户；业务库备份不包含它 |
| 对象文件 | 源文件、历史版本、缩略图或可重建规则、对象清单 | object_key/version、大小、checksum 与数据库引用一致 |
| Agent | 尚未入库的历史、附件、技能和配置；在途请求标识 | 线程归属正确，恢复不会重跑已有收费操作 |
| 密钥 | 版本化密钥引用与独立受控恢复材料 | 有密文也有可用的解密手段；不把秘密写进文档/Git |
| 外部副作用收件箱 | 已接收支付/供应商事件与发送请求证据 | 不随业务库倒退而丢失；若未建设独立存储，必须能从提供商取回并核对 |
| 删除与撤权记录 | 对象删除版本、成员撤权、账号封禁的最小记录 | 恢复后先应用，防止恢复旧权限和已删除数据 |

候选副本设计：生产一份、隔离凭据的异机备份一份、关键数据额外异地或不可变副本一份。仅不同文件夹不算异机；仅启用对象版本化也不保证备份账号被攻破后安全。备份清理权限与日常写入权限分离，并保留经过验证的保留锁或离线恢复材料。

## 4. 备份任务怎样证明完成

backup_runs 必须记录 backup_id、scope、started_at、finished_at、status、source_version、schema_version、storage_key、checksum、size_bytes、encryption_key_version、base_backup_id、WAL 范围/时间线（适用时）、expires_at、last_verified_at。秘密不入表。

流程：创建运行记录 → 一致性备份 → 上传独立存储 → 核验文件和日志链 → 标记 verified → 按依赖保留策略清理旧备份。任务退出码成功只算作业成功，未经实际恢复不能标记 restore_tested。

监控最新可恢复时点、WAL 缺口、归档失败、磁盘剩余、上传失败、密钥不可用和演练过期。运行记录也要有异机副本；故障时不能依赖坏掉的业务库查询“备份放哪”。

## 5. 事故处理步骤

| 步骤 | 操作 | 放行条件 |
|---|---|---|
| 1 控制损害 | 确认范围，停止受影响写入、Worker、同步与高风险外部调用；保全原库和日志 | 所有写来源可识别，未覆盖原数据 |
| 2 选方案 | 误删单个租户用旁路恢复；整库损坏才全库恢复；记录 UTC 目标时间与原因 | 恢复点早于坏操作且处于有效备份链中 |
| 3 建隔离环境 | 在新实例/目录恢复，阻断支付、AI、邮件等外发网络与定时任务 | 不能让恢复测试消耗费用或发真实通知 |
| 4 恢复数据 | 逻辑备份恢复到空库，或兼容物理基础备份加 WAL 到目标时点 | 目标确实到达，未因缺 WAL 停在错误时间；核验时间线和恢复报告 |
| 5 业务核对 | 核对身份、租户、余额、冻结、订单、文件、在途任务 | 隔离、关联和账务不变量通过；差异进入清单 |
| 6 外部对账 | 拉取恢复点之后的真实支付、退款和上游请求结果；恢复删除/撤权记录 | 不因库里少记录而再次扣款/生成；无法确定的任务继续核对 |
| 7 切换服务 | 先只读验收，再受控放写；更换恢复代号并废除旧 Worker 租约、旧缓存和危险会话 | 旧实例不能继续写入；每个后台进程接入新环境 |
| 8 观察与结案 | 验证关键流程，持续对账，记录实际损失范围和恢复耗时 | 保存恢复报告和新基线备份；修复根因 |

禁止在生产原库上直接覆盖恢复作为第一步。单租户误删应在隔离库找回相关记录，按依赖、最新版本和删除意图合并；不能回退整库导致其他用户一天的数据消失。不能把历史权限、旧余额直接复制覆盖最新状态。

如果所有备份不可用：保全残存数据、对象版本、供应商和支付记录，逐项重建并注明无法恢复范围。不能捏造缺失历史或宣称零丢失；业务保持维护/受限状态，待账务和隔离安全后再放行。

## 6. 尚需防范的风险与措施

| 风险 | 处理方案 |
|---|---|
| 归档失败导致 WAL 填满磁盘 | 容量告警、归档重试和背压；扩容/清理其他可删数据，禁止手删 pg_wal |
| 备份比坏数据更晚，已被污染 | 多代备份、已知健康时点和异常发现时限；不能只留最新一份 |
| 应用与备份都被同一凭据删除 | 备份独立权限、保留保护、密钥轮换、离线恢复材料 |
| 数据库恢复了但文件已永久删除 | 对象版本或独立副本覆盖数据库恢复窗口；启用回收延迟；缺件明确列出 |
| 恢复回调去重记录后再次消费 | 独立收件箱/平台对账，加稳定业务唯一键；人工重放不生成新事件身份 |
| 恢复的旧 Worker 继续操作 | 隔离旧实例，恢复代号与租约同时验证；上游副作用仍要独立核对 |
| 备份中含旧密钥、旧授权 | 恢复后重新注入现行密钥并重放撤权记录，不重新启用被撤销凭据 |
| 数据量变大导致恢复超时 | 定期按增长数据量复测，调整基础备份频率、下载带宽和恢复资源 |
| 跨区域存储不符合实际要求 | 数据区域和备份所在地纳入部署决策；先明确要求再复制，本文不认定法律合规 |

## 7. 演练与交付门槛

首次正式上线前完成一次全量恢复。建议每月隔离恢复演练；重大结构升级、密钥轮换、存储切换后追加针对性演练。付费前必须演练时点恢复后不重复扣费、不重复发权益和不重发未知 AI 请求。

恢复报告记录事故/演练编号、操作者、备份编号、目标时间、实际恢复时点、应用与数据库版本、文件校验、账务差异、外部对账、实际 RPO/RTO、未恢复范围和放行结论。结果不达标则修正方案并重演，不能只改文档里的目标数字。
