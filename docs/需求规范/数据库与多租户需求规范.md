## 1. 文档目的

这份文档先把“系统要保存什么、谁拥有这些数据、谁能看和改”说清楚，再进入数据库建表。

大白话：数据库不是把所有信息混在一起。每类信息都有自己的归属、权限、保存时间和删除规则。

## 2. 系统边界

### 2.1 目标系统的分工（不代表当前已实现）

| 系统 | 负责内容 | 说明 |
|---|---|---|
| Appwrite | 注册、登录、密码、会话、基础用户身份 | 用户登录密码由 Appwrite 保存，业务库不重复保存明文密码 |
| PostgreSQL | 业务数据、团队、权限、订阅、资产、历史、互动、审计 | 本文规划的主业务数据库 |
| 文件存储 | 图片、视频、源文件、缩略图 | 数据库只保存文件 ID、地址和元数据，不直接塞入大文件 |
| Redis（后续） | 缓存、限流、短期任务状态 | 不是事实数据，丢失后可以重新生成 |

### 2.2 数据归属原则

1. **用户身份由 Appwrite 拥有**。PostgreSQL 只保存对应的 `appwrite_user_id`。
2. **业务事实由 PostgreSQL 拥有**。例如订阅是否有效、资产属于哪个团队、谁有权限。
3. **文件内容由文件存储拥有**。PostgreSQL 记录文件的归属和状态。
4. **前端不能决定权限**。前端只负责显示，最终权限必须由服务端判断。
5. **一个事实只保存一份**。其他页面看到的数据通过查询或事件同步，不能各自复制一套。

## 3. 核心概念

| 术语 | 专业解释 | 大白话 |
|---|---|---|
| Tenant | 租户，数据隔离的最大业务边界 | 一个团队或一个个人空间 |
| Workspace | 工作空间，用户实际工作的容器 | 用户或团队的“房间” |
| RBAC | 基于角色的权限控制 | 先给人分配角色，再由角色决定能做什么 |
| ABAC | 基于属性的权限控制 | 还要看资源属于谁、状态是什么、用户在哪个团队 |
| Aggregate | 聚合，必须一起保证一致性的业务对象 | 一次操作中必须同时正确的一组数据 |
| Soft Delete | 软删除 | 先标记删除，必要时还能恢复 |
| Audit Log | 审计日志 | 记录谁在什么时候做了什么 |
| Idempotency | 幂等 | 用户重复点一次和点十次，结果不能重复扣费或重复创建 |

## 4. 数据隔离模型

系统采用“个人空间 + 团队空间”的模型。

```text
Appwrite User
    └── user_accounts
          ├── personal_workspace（个人空间）
          └── team_memberships → teams → team workspace（团队空间）
```

### 4.1 数据归属字段

空间业务表按下表包含归属字段；用户、组织、平台目录和审计等表按各自领域规则，不强行塞同一个字段。

| 字段 | 类型建议 | 含义 |
|---|---|---|
| `id` | UUID | 这条记录自己的唯一编号 |
| `workspace_id` | UUID | 数据属于哪个个人或团队空间 |
| `owner_user_id` | UUID | 指向内部 user_accounts.id；不混用外部身份 ID |
| `team_id` | UUID，按组织表需要 | 通常由 workspaces 推导，业务表不重复保存；必要冗余必须有一致性约束 |
| `created_at` | timestamptz | 创建时间 |
| `updated_at` | timestamptz | 最近修改时间 |
| `deleted_at` | timestamptz，可为空 | 软删除时间；为空表示没有删除 |
| `version` | integer | 并发修改版本，防止覆盖别人刚改的内容 |

规则：`workspace_id` 是主要隔离字段。任何查询都必须带上当前用户有权访问的 `workspace_id`，不能只按 `id` 查询。

## 4C. 看表字段的统一格式

以后每张表都按下面的表格说明，不直接凭感觉建字段。

| 列名 | 专业含义 | 大白话 | 是否必填 | 关系或限制 |
|---|---|---|---|---|
| `id` | 主键 | 这条数据的身份证号 | 是 | 全局唯一 |
| `workspace_id` | 租户隔离键 | 这条数据属于哪个空间 | 空间业务表必填 | 外键指向 `workspaces.id`；用户、组织、平台表按专用归属规则 |
| `created_by` | 创建者 | 谁创建的 | 业务表必填 | 外键指向用户 |
| `created_at` | 创建时间 | 什么时候产生 | 是 | 服务器统一生成 |
| `updated_at` | 修改时间 | 最近什么时候改过 | 是 | 每次修改自动更新 |
| `deleted_at` | 软删除时间 | 是否被放进回收站 | 否 | 不直接物理删除 |
| `version` | 乐观锁版本 | 防止两个人互相覆盖修改 | 是 | 每次更新加一 |

任何新增表都必须回答：它属于哪个分组、谁拥有、谁能读、谁能写、什么时候删除、是否需要审计。

## 5. 用户与身份模块

### 5.1 `user_accounts` 用户业务档案

Appwrite 负责认证；本表负责业务资料。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 系统内部用户编号 |
| `appwrite_user_id` | varchar(64)，唯一 | Appwrite 用户编号 |
| `email` | text | 展示邮箱；身份唯一性由 Appwrite 确定，不额外依赖 citext 扩展 |
| `display_name` | varchar(100) | 昵称 |
| `avatar_file_id` | UUID，可为空 | 头像文件 |
| `locale` | varchar(16) | 语言，如 `zh-CN` |
| `timezone` | varchar(64) | 时区 |
| `status` | enum | `active`、`suspended`、`deleted` |
| `last_login_at` | timestamptz | 最近登录时间 |
| `created_at` | timestamptz | 首次进入系统时间 |

密码不在 PostgreSQL 保存。不能保存明文密码，也不能把 Appwrite 的密码复制过来。

### 5.2 `user_preferences` 用户偏好

主题、语言、默认模型、通知设置等可修改偏好单独存放，避免把用户主档案做成一张“万能表”。

### 5.3 登录安全

登录会话、密码重置、邮箱验证由 Appwrite 负责。PostgreSQL 只记录必要的业务事件，例如登录时间、封禁状态和安全审计摘要。

## 6. 个人空间、团队与组织

### 6.1 `workspaces` 工作空间

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 空间编号 |
| `type` | enum | `personal` 或 `team` |
| `team_id` | UUID，可为空 | 团队空间对应的团队 |
| `owner_user_id` | UUID，可为空 | 个人空间的用户 |
| `name` | varchar(120) | 空间名称 |
| `status` | enum | `active`、`archived`、`deleted` |
| `created_at` | timestamptz | 创建时间 |

约束：personal 必须有 owner_user_id 且 team_id 为空；team 必须有 team_id 且 owner_user_id 为空。以 CHECK 约束互斥。初期每个用户一个个人空间、每个团队一个团队空间，分别加唯一约束。Tenant 是该隔离边界的概念别名，不另建一套 tenant_id。

### 6.2 `teams` 团队

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 团队编号 |
| `name` | varchar(120) | 团队名称 |
| `slug` | varchar(80)，唯一 | 团队短名称，用于 URL |
| `owner_user_id` | UUID | 团队所有者 |
| `status` | enum | `active`、`suspended`、`deleted` |
| `created_at` | timestamptz | 创建时间 |

### 6.3 `team_memberships` 团队成员关系

一名用户可以加入多个团队，一个团队可以有多个用户。

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | UUID | 成员关系编号 |
| `team_id` | UUID | 团队 |
| `user_id` | UUID | 用户 |
| `department_id` | UUID，可为空 | 所属部门 |
| `job_title_id` | UUID，可为空 | 岗位 |
| `status` | enum | `invited`、`active`、`suspended`、`left` |
| `joined_at` | timestamptz，可为空 | 入职或加入时间 |
| `left_at` | timestamptz，可为空 | 离职或退出时间 |
| `invited_by` | UUID，可为空 | 邀请人 |

唯一约束：(team_id, user_id) 全历史唯一。离职后重入复用成员记录，历史变化另存 membership_events，避免软删除导致重复成员。

### 6.4 `departments` 部门与 `job_titles` 岗位

部门支持 `parent_id`，可以形成“公司 → 设计部 → 视觉组”的层级。岗位只描述职位，不直接等于权限；权限通过角色分配。

### 6.5 入职、离职与邀请

用 `team_invitations` 记录邀请链接、邀请邮箱、有效期、接受人和状态。离职不立即删除历史数据，而是把成员状态改为 `left`，保留历史操作归属。

## 7. 角色与权限

### 7.1 权限分层

权限分三层：

1. **功能权限**：能不能使用某个功能，例如生成图片、删除资产、管理成员。
2. **资源权限**：能不能操作某条具体数据，例如只能改自己创建的资产。
3. **范围权限**：能操作个人数据、部门数据、团队数据，还是全平台数据。

### 7.2 主要表

| 表 | 用途 |
|---|---|
| `roles` | 角色，如 Owner、Admin、Editor、Viewer |
| `permissions` | 原子权限，如 `asset.read`、`asset.delete` |
| `role_permissions` | 角色和权限的对应关系 |
| `role_bindings` | 个人在全局或团队中的角色 |
| `permission_overrides` | 特殊用户的临时允许或禁止 |
| `access_policies` | 资源范围规则，如只能访问本部门 |

建议初始角色：

| 角色 | 大白话 |
|---|---|
| `owner` | 团队老板，可以管理全部内容和成员 |
| `admin` | 管理员，可以管理团队和大部分业务数据 |
| `editor` | 编辑者，可以创建、编辑和分享内容 |
| `viewer` | 查看者，只能查看被允许的数据 |
| `member` | 普通成员，使用团队分配给他的功能 |

权限判断必须在服务端完成：用户是否登录、是否属于团队、角色是否允许、资源是否属于当前范围、订阅是否有效，都要一起判断。

## 8. 订阅、额度与计费

### 8.1 方案与订阅

| 表 | 作用 |
|---|---|
| `plans` | 方案定义，如免费版、专业版、团队版 |
| `plan_features` | 方案能使用哪些功能 |
| `plan_quotas` | 方案包含多少图片、视频、Agent 次数或存储空间 |
| `subscriptions` | 某个用户或团队当前订阅 |
| `subscription_events` | 开通、续期、升级、降级、取消和退款记录 |
| `payment_customers` | 第三方支付平台的客户编号 |
| `orders` | 订单事实 |
| `payments` | 实际支付结果 |

### 8.2 订阅归属

订阅统一归属 workspace_id；用户或团队通过 workspaces 推导，不重复保存两套归属。每个空间同一时刻最多一个基础订阅，变更记录进入 subscription_events。免费权益也通过统一权益服务读取。

### 8.3 使用量

`usage_records` 保存每次实际消耗：用户、团队、空间、功能、模型、数量、单位、请求编号、结果和时间。额度汇总可以缓存，但每次扣减必须有可追溯的原始记录。

防重复：每次消耗带 `idempotency_key`，同一个请求重试不能重复扣额度。

## 9. 生成任务与历史记录

### 9.1 `generation_tasks` 生成任务

| 字段 | 说明 |
|---|---|
| `id` | 任务编号 |
| `workspace_id` | 任务归属空间 |
| `created_by` | 发起人 |
| `task_type` | 图片、视频、音频、文本或 Agent |
| `provider` | 实际调用的模型供应商 |
| `model` | 模型名称 |
| `prompt` | 用户输入；敏感内容需按策略脱敏 |
| `status` | `queued`、`running`、`succeeded`、`failed`、`cancelled` |
| `request_id` | 外部请求幂等编号 |
| `error_code` | 失败原因编号 |
| `started_at` / `finished_at` | 开始和结束时间 |

### 9.2 `generation_outputs` 生成结果

一条任务可以有多个结果。结果表保存文件 ID、缩略图、尺寸、模型版本、生成参数摘要和内容安全状态。

原始提示词和结果文件属于用户隐私，默认只能被有权限的用户看到。

## 10. 资产库与复用

### 10.1 `assets` 资产

资产可以属于个人空间，也可以属于团队空间。分享使用显式授权记录，保持来源所有权。复制为团队独立资产是另一种操作，必须重新授权并创建团队资产版本；详见《数据归属与隔离规范》。

文件唯一关联入口为 asset_files（关联具体 asset_versions 和 file_objects），assets 不再同时维护 file_id。关键字段：`workspace_id`、`created_by`、`asset_type`、`title`、`visibility`、`source_generation_id`、`status`。

### 10.2 分享与复用

| 表 | 作用 |
|---|---|
| `asset_shares` | 把资产分享给团队、部门、指定成员或公开链接 |
| `asset_references` | 记录某个项目或任务复用了哪个资产 |
| `asset_versions` | 记录资产修改版本 |
| `collections` | 用户或团队建立的收藏夹 |
| `collection_items` | 收藏夹中的资产引用 |

复用时保留“来源资产”和“新资产”的关系，后续可以追溯、撤销分享和统计复用次数。

## 11. 点赞、评论与互动

### 11.1 `asset_likes`

唯一约束：同一用户对同一资产只能有一条点赞记录。取消点赞使用删除或软删除，但统计要可重算。

### 11.2 `asset_comments`

支持 `parent_id` 形成回复。字段包括作者、资产、评论内容、审核状态、删除时间和编辑时间。评论删除后保留“已删除”占位，避免破坏回复链。

### 11.3 内容安全

评论、公开资产和分享链接要有 `moderation_status`：`pending`、`approved`、`rejected`。审核结果由服务端保存，前端不能自行绕过。

## 12. API 配置与模型目录

### 12.1 API 供应商配置

`ai_providers` 保存供应商名称、接口地址、启用状态和能力；`provider_credentials` 保存平台管理员配置的加密密钥引用，不在普通查询中返回完整 Key。用户在浏览器中配置的 `ai_channels` 属于用户或团队的业务配置，必须带明确的 `workspace_id`，不能写入平台凭证表。服务端根据权限和路由策略选择可用渠道，不能把用户 Key 变成全平台共享 Key。

### 12.2 模型目录

`ai_models` 保存模型名称、供应商、能力类型、输入输出限制、价格规则和启用状态。模型列表是后台配置产生的业务数据，前端只能读取公开字段。模型调用时还要把 provider、model、model_version、pricing_version 快照写入 generation_tasks，避免目录更新后历史记录含义改变。

密钥读取必须经过后台服务，不能直接返回给浏览器，也不能写入日志。

## 13. 审计、通知与系统记录

### 13.1 `audit_logs`

记录高风险动作：登录、改权限、邀请成员、删除资产、改 API Key、改订阅、退款、导出数据。

字段建议：操作者、团队、动作、资源类型、资源 ID、成功或失败、请求 ID、IP 摘要、User-Agent 摘要、前后值摘要、时间。

### 13.2 `notifications`

保存站内通知和阅读状态，例如邀请、生成完成、评论回复、额度不足和订阅即将到期。

### 13.3 `outbox_events`

业务写入和事件记录放在同一个事务里，避免“数据库写成功但通知没发出去”。后台任务再从 outbox 投递通知、统计或索引。


### 13.4 隐私同意、设备和安全事件

`consent_records` 记录协议版本、同意类型、时间、来源和撤回时间；不能用一个用户表布尔值覆盖多次版本变更。`user_devices` 只保存设备摘要、最近活动、会话撤销版本和风险状态，不保存长期 Token。`security_events` 记录登录失败、密码重置、密钥更换、权限异常、批量导出和风控结果。IP 和 User-Agent 按隐私策略保存摘要或受限字段，并设置保留期限。
## 14. 删除、隐私和生命周期

1. 普通删除先使用 `deleted_at`，保留恢复窗口。
2. 用户注销后，身份由 Appwrite 删除或禁用；业务数据按保留策略匿名化或删除。
3. 团队离职成员的历史生成记录不改作者，保留审计意义；个人隐私数据按策略处理。
4. 文件删除必须先确认数据库没有有效引用，再删除对象存储文件。
5. 订单、支付、额度和审计记录不能因为用户点“删除账号”就直接消失。
6. 生成结果和原始提示词需要设置保留期限，避免无限增长。

## 15. 索引与容量规划

第一批必须有的索引：

- `user_accounts(appwrite_user_id)` 唯一索引；
- `team_memberships(team_id, user_id)` 唯一索引；
- 空间业务表按实际查询配置以 workspace_id 开头的复合索引，避免重复建立单列索引；
- `generation_tasks(workspace_id, created_at)`；
- `assets(workspace_id, created_at)`；
- `asset_comments(asset_id, created_at)`；
- `usage_records(workspace_id, created_at)`；
- `audit_logs(team_id, created_at)`。

大表按月份或时间范围分区要等真实数据量达到阈值后再做，不能一开始就把所有表复杂化。

模型和任务查询还应有 `generation_tasks(workspace_id,status,created_at)`、`generation_outputs(workspace_id,task_id)`、`ai_models(provider_id,status)`；设备和安全事件按 `user_id,created_at` 建索引。具体索引以实际查询计划确认，不把每个字段都建索引。

## 15A. 自建 PostgreSQL 到腾讯云托管 PostgreSQL 的迁移规范

当前数据库是装在轻量服务器上的自建 PostgreSQL。以后迁移到腾讯云托管 PostgreSQL 时，目标是“换数据库位置，不换业务规则”。

### 15A.1 必须保持不变的部分

| 内容 | 要求 |
|---|---|
| 表名和字段名 | 迁移前后保持一致 |
| 主键和外键 | 保持一致，不重新生成业务编号 |
| 枚举和状态 | 保持一致，例如 `active`、`deleted` |
| API 接口 | 前端不需要因为换数据库而改接口 |
| 权限规则 | 不因数据库搬家而改变 |
| 时间和时区 | 统一使用 UTC 存储，展示时转换 |

### 15A.2 必须避免的写法

- 不把业务数据写死在服务器路径中；
- 不依赖某台机器的本地用户名；
- 不使用只在某个环境存在的临时表；
- 不把文件放进数据库二进制字段；
- 不让前端直接连接 PostgreSQL；
- 不把密码、API Key 和数据库连接串提交到 GitHub；
- 不用手工改表代替 Migration；
- 不把 `localhost` 写死在业务代码里，数据库地址必须来自环境变量。

### 15A.3 连接配置标准

应用只读取环境变量，不读取开发电脑上的固定配置：

```text
DB_HOST=
DB_PORT=5432
DB_NAME=qingyu
DB_USER=
DB_PASSWORD=
DB_SSL_MODE=
DB_POOL_MIN=
DB_POOL_MAX=
```

目标是保持业务接口不变；实际迁移还要核验版本、网络、TLS 证书、账号权限、扩展、备份和恢复，不能只改地址。

### 15A.4 迁移步骤

按《迁移与性能验收规范》执行：先恢复演练，再停止所有写入来源、完成最终备份与校验、配置目标库、只读验收，最后开放写入。订单回调、后台任务和 Agent 也必须受停写控制。

### 15A.5 回滚方法

目标库尚未收到业务写入时，确认旧库仍是权威数据后可以回切。目标库已经收到写入时，禁止直接切回旧库；必须先停写，保全新库增量并完成经演练的数据回灌和对账，或在新库修复。恢复不了一致性就维持维护状态，不能为了恢复页面而丢订单或作品。

## 15B. PostgreSQL Migration 文件规范

每次表结构变更必须有版本化文件，例如：

```text
database/migrations/
├── 0001_create_users_and_workspaces.sql
├── 0002_create_teams_and_memberships.sql
├── 0003_create_roles_and_permissions.sql
├── 0004_create_billing_and_usage.sql
├── 0005_create_generations_and_assets.sql
└── 0006_create_audit_and_outbox.sql
```

Migration 必须满足：

1. 可以在一台空 PostgreSQL 上从零执行；
2. 同一版本不能重复执行；
3. 失败时能定位是哪一步；
4. 生产环境执行前先在测试库演练；
5. 高风险变更要有回滚或兼容期；
6. 不把真实用户数据写进 Migration 文件。

## 15C. 数据库环境分层

| 环境 | 用途 | 数据要求 |
|---|---|---|
| `local` | 开发者电脑 | 测试数据，可随时重建 |
| `staging` | 上线前验证 | 脱敏数据，模拟生产配置 |
| `production` | 正式用户 | 真实数据，必须备份和审计 |

不同环境至少使用不同数据库名、不同账号和不同密码。开发环境不能连接生产数据库。

## 16. 必须确认的产品规则

下面这些问题在正式建表前必须确认：

1. 一个用户最多可以创建几个个人或团队空间？
2. 一个用户能否同时拥有多个团队？
3. 团队订阅由团队所有者购买，还是成员也能购买？
4. 成员离职后，他创建的资产归个人、归团队，还是按创建时选择决定？
5. 团队资产是否默认所有成员可见？
6. 公开分享链接是否允许匿名访问？是否需要过期时间？
7. 点赞和评论是否需要审核？
8. 生成结果和提示词保存多久？
9. 用户注销后，订单、审计和团队历史保留多久？
10. 图片、视频和源文件存在哪个对象存储？

## 17. 实施顺序

### P0：先保证核心闭环

用户档案、空间与成员隔离、角色权限、API 配置、模型目录、生成与资产持久化、基本审计、额度原子预占和幂等、可恢复任务，以及自动备份和恢复演练。使用异步投递时同步落地 Outbox 重试，不能留到 P2。

### P1：补齐业务运营

订阅商业化、订单与支付、团队邀请、部门岗位、收藏、点赞、评论、通知和分享链接。正式收费前必须通过支付验签、重复回调、额度结算、退款和对账验收；这些不是收费后的补丁。

### P2：增强规模能力

Redis 扩展、独立消息队列、全文搜索、分区表、数据仓库、报表和高可用架构。只有监控证明确有瓶颈才引入。基础持久化、任务恢复和备份从 P0 开始。

## 18. 验收标准

这份需求通过后，至少应能回答：

- 每一条数据属于哪个用户、团队和空间；
- 一个用户能否读取这条数据；
- 谁可以创建、修改、分享和删除它；
- 重复请求是否会重复扣额度或重复创建；
- 用户离职、团队删除和账号注销后数据怎么处理；
- PostgreSQL、Appwrite、文件存储各自保存什么；
- 后续升级到 10 万用户时，哪些部分可以扩容，哪些部分需要拆分。

本规范确认前，不创建正式 Migration，不迁移 SQLite 数据，也不修改线上服务连接方式。


## 19. 根据当前代码反查出的数据清单与证据边界

本节基于本地源码检索和关键调用链复核，不等于逐行审计全部代码，也不证明线上已部署相同版本或各接口已成功落库。前端入口、后端实现、持久化完成必须分别取证。检查范围包括：

- 前端 `src/` 下的页面、状态仓库、API 客户端、画布、生成、资产、Agent、配置和同步代码。
- `qingyu_server/src/` 下的 SQLite schema、用户、计费、管理员、API 代理和调用统计代码。
- `canvas-agent/src/` 下的 Agent 会话、线程、消息、工具调用、审批、技能、工作区和事件代码。

### 19.1 代码中已经存在、但原始需求没有明确写出的数据

| 代码里实际存在的数据 | 当前保存位置 | 未来正式归属 | 大白话 |
|---|---|---|---|
| 画布项目、画布节点、节点连接线、视口、背景和聊天会话 | 浏览器 IndexedDB/localforage | `canvas` 模块的 PostgreSQL 表 + 文件存储 | 用户在画布上摆了什么、怎么连起来、看到哪一块 |
| 项目删除标记和恢复所需信息 | 浏览器 IndexedDB/localforage | `canvas_projects`、`canvas_project_deletions` | 删除后先留痕，避免同步时又被“复活” |

| 用户反馈 | 前端发起 /api/feedback；所查后端未见挂载，前端失败也显示成功，不能视为已保存 | `feedback`、`feedback_replies`、`feedback_attachments` | 反馈要能关联用户、页面、版本和处理状态 |
| 版本检查、更新公告和变更记录 | 远程 JSON/Markdown | `app_releases`、`release_notes`（可选） | 用户看到的版本和后台发布记录要能对应 |
| 页面访问和分析事件 | 第三方统计脚本/浏览器事件 | `analytics_events` 或外部分析平台 | 统计数据和业务事实分开，不能反过来影响业务权限 |
| 语言、主题、面板宽度、快捷工具设置 | 浏览器 localStorage | `user_preferences`，浏览器保留缓存 | 这是偏好，不是团队业务数据 |
| 登录 Token、Agent Token、API Key 输入框值 | 浏览器 localStorage | 服务端短期会话或密钥管理器 | 不能把长期密钥明文放在可被脚本读取的 localStorage |

### 19.2 画布数据的逻辑层次与适度拆表

项目、节点、连接、文件是不同逻辑对象。初期节点配置可用 canvas_nodes.config JSONB，加 schema_version 和大小限制；只有配置独立查询、权限或更新频率确有需要才拆 canvas_node_configs。允许有版本的项目快照用于恢复，但不能让它与节点表同时成为可写权威。

| 层 | 建议表 | 保存什么 | 不保存什么 |
|---|---|---|---|
| 项目层 | `canvas_projects` | 项目名称、所属空间、创建人、状态、版本 | 不把所有节点都塞成一列大 JSON |
| 节点层 | `canvas_nodes` | 节点类型、坐标、尺寸、标题、业务状态、排序 | 不把文件二进制直接放进节点 |
| 节点配置层 | canvas_nodes.config；canvas_node_configs 为可选拆分 | 各类型节点的参数快照、schema_version | 不让不同节点共用一套互相污染的字段 |
| 关系层 | `canvas_connections` | 起点节点、终点节点、端口、关系类型 | 不用前端数组下标当永久 ID |
| 结果层 | `generation_tasks`、`generation_outputs` | 请求、状态、模型、耗时、错误、结果文件 | 不把“正在生成”的临时状态当最终结果 |
| 会话层 | `canvas_chat_sessions`、`canvas_chat_messages` | 项目内问答历史和引用节点 | 不与全局 Agent 线程混成一张消息表 |
| 展示层 | `canvas_views` 或项目字段 | 视口、背景、显示选项 | 不让展示偏好决定业务归属 |

### 19.3 未来加新功能时的固定接入方式

新增功能必须先归入一个业务模块，再决定它依赖哪一个已有聚合。不能直接在任意表里加几个字段。

```text
新功能
├── 先判断归属空间：个人 workspace / 团队 workspace
├── 再判断业务模块：canvas / asset / generation / billing / agent / admin
├── 优先复用既有实体；有独立业务事实时才新增主表
├── 通过外键关联已有主表：例如 workspace_id、user_id、asset_id、task_id
├── 需要跨模块通知时：写 outbox_events，不直接互相改表
├── 需要统计时：用独立分析事件；计费消耗才写 usage_records
└── 需要大文件时：写 file_objects 元数据，文件放对象存储
```

新增表必须回答五个问题：

1. 这条数据的唯一事实来源是哪张表？
2. 它属于哪个 `workspace_id`，个人还是团队？
3. 谁能读、谁能改、谁能删除？
4. 删除后要不要保留审计、账务或合规记录？
5. 查询最常用的条件是什么，是否已经有对应索引？

### 19.4 保持整洁、避免串数据和避免变慢的硬规则

| 规则 | 具体要求 | 解决的问题 |
|---|---|---|
| 模块边界 | 初期采用单数据库、应用模块目录分组；不要求每个模块建立独立服务或 schema。领域包括：`identity`、`workspaces`、`iam`、`canvas`、`generation`、`asset`、`billing`、`agent`、`admin` | 新功能有固定位置，不会随便塞表 |
| 归属必填 | 空间业务表带 workspace_id；用户偏好带 user_id，组织表带 team_id，全局模型目录由平台管理；不能强塞同一字段到所有表 | 防止 A 用户看到 B 用户数据 |
| 外键和唯一约束 | 所有关系用外键；业务幂等键、成员关系、点赞关系、订单号加唯一约束 | 防止重复数据和孤儿数据 |
| 查询权限 | 服务端每次查询先确定当前用户可访问的 workspace 集合，再查询业务记录 | 防止只按 ID 查询造成越权 |
| 事务边界 | 创建订单、扣额度、生成任务、写结果等操作用短事务；大文件上传不占事务 | 防止半成功和锁表太久 |
| 不把实时状态写库 | 并发数、SSE 连接、Agent 在线状态放进程内存/Redis；只定时写汇总 | 防止每个请求都打 PostgreSQL |
| 大字段分离 | 画布快照、原始响应、长文本、文件正文放对象存储或分表；主表保留摘要和引用 | 防止列表查询被大字段拖慢 |
| 分页和索引 | 所有列表接口必须分页；按 `workspace_id + updated_at`、`workspace_id + status` 建索引 | 防止用户一多就全表扫描 |
| 乐观并发 | 记录 `version`；更新时带旧版本条件，不一致就返回冲突 | 防止两个人互相覆盖数据 |
| 事件解耦 | 普通跨模块动作由应用服务同步编排、模块各自写入；需要异步可靠投递时才使用 outbox_events，并实现消费去重 | 防止互相调用导致循环和脏数据 |
| 统一命名 | 表名复数 snake_case，外键统一 `_id`，时间统一 `timestamptz`，状态使用受控值 | 以后看表就知道是什么 |
| 禁止隐式 JSON | JSONB 只用于确实会变化的配置或原始快照；可查询、可关联、可统计的字段必须独立列 | 防止“什么都能放但什么都查不清” |
| 机密分离 | API Key、WebDAV 密码、Agent Token 只保存密文/引用，业务表不返回明文 | 防止后台泄密 |
| 可迁移 | 目标结构不使用 SQLite 专有语法；扩展仅在源库和目标库均验证支持后使用，不依赖云厂商私有业务格式 | 以后迁移到腾讯云托管 PostgreSQL 不重写业务 |

### 19.5 当前实现与目标架构的差距清单

| 当前情况 | 风险 | 目标改法 |
|---|---|---|
| 画布、资产和生成日志主要在浏览器本地 | 换设备看不到；清缓存可能丢数据；团队无法共享 | 登录后以 PostgreSQL 为主，浏览器只做缓存和离线草稿 |
| qingyu_server 仍使用 SQLite 用户、画布和 API Key 表 | 当前表结构和身份链路未形成完整多租户约束；不能仅凭 SQLite 名称判断是否安全 | 新接口直接按 PostgreSQL 目标模型实现，不继续扩展 SQLite schema |
| 所查 http.ts 主入口创建单个 CanvasSession；tenant-manager.ts 的 token 前缀逻辑未证明已接入主入口 | 重启、扩容和多实例时状态可能不一致 | 按内部 workspace_id、user_id、thread_id 验权和隔离；持久化任务与审批，实时连接可按规模使用 Redis；禁止 token 前缀充当身份 |
| Appwrite 同时承担身份和团队列表 | 业务团队权限若分散在两处，容易出现权限不一致 | Appwrite 只认身份；团队、岗位、权限以 PostgreSQL 为唯一事实来源 |
| API Key 实时统计在单进程内存 | 多实例统计会分叉，重启会丢 | Redis 做实时计数，PostgreSQL 做按日汇总 |
| 前端 localStorage 保存多种 Token 和 API 配置 | 容易泄露，也无法统一撤销 | 生产环境改成 HttpOnly 会话和服务端密钥引用；本地配置仅用于开发 |
| 远程提示词、插件和 WebDAV 数据可能直接覆盖本地数据 | 同步时会覆盖新数据或产生混合版本 | 使用版本号、内容哈希、同步批次和冲突记录，默认不静默覆盖 |

### 19.7 以“新增一个功能”为例

假设以后增加“团队模板市场”：

1. 模板本身属于 `asset`，建立 `asset_templates`，带 `workspace_id` 和发布状态。
2. 模板引用的图片、视频仍通过 `asset_files` 关联，不复制文件。
3. 购买或额度扣减属于 `billing`，建立订单和额度流水，不在模板表里加余额字段。
4. 购买成功通知属于 `collaboration/governance`，通过 `outbox_events` 发送。
5. 模板市场的搜索统计属于分析数据，不把访问次数不断写回模板主表。

这样增加功能时，每个数据仍然有固定位置，模块之间通过明确的 ID 和事件连接，后续迁移时分别核验 PostgreSQL、文件、Appwrite 身份和 Agent 历史依赖；只换数据库位置不等于搬完全部系统。

## 20. 本次代码审计后的结论

当前系统不是只有“用户、团队、订阅、资产”四类数据。实际还包含画布结构、生成过程、模型目录、密钥路由、插件、提示词、Agent 工作流、同步、文件、计费流水、运营后台和本地缓存等数据。

数据库设计的核心不是把字段列得越多越好，而是让每条数据只有一个明确的主人：身份归 Appwrite，业务事实归 PostgreSQL，文件归对象存储，实时状态归 Redis，浏览器只保存缓存和草稿。这只是隔离和扩展的设计基础；是否真正防串数据，要以实现后的越权、并发、缓存、文件和消息测试为准。

本节完成后，下一步才是把 P0 范围收窄，逐表确认字段、索引、约束和接口，再编写 PostgreSQL migration。当前不应直接照本节一次性建完所有表。
